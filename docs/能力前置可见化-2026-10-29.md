## §1 原来错在哪

### 1.1 `load_tools` 是 100% 坏的

`src/orchestrator.js` 里 `ctx` 是个对象字面量，两个方法写成了**方法简写**：

```js
const ctx = {
  enablePack(packs) {          // ← this 指向 ctx，不是 Orchestrator
    for (const d of this.toolDefs) { … }   // this.toolDefs === undefined → TypeError
  },
  escalateModel(reason = '') {
    this.emit('log', …)        // this.emit === undefined → TypeError
  }
};
```

实测 `data/sessions/` 1000 份会话：

- `load_tools` 被调 **3 次，失败 3 次**，错误全是 `错误：this.toolDefs is not iterable`；
- `escalate_reasoning` 被调 **0 次** —— 所以那个坏法一直没暴露，但只要主人一开路由就会炸，
  而且是在**已经切了模型、改了 `maxRounds` 之后**炸，属于"坏在半路"。

语法完全合法，`node --check` 也不会报，所以只能靠"真的调一次"才发现。

### 1.2 表情的失败 97% 是必然的

`send_sticker` 的三道闸门（本轮张数 / 会话冷却 / 分钟额度）都只在 **execute 里**判。
模型看到动作集里写着"发表情包（表情库可用）"，就去调，撞墙，拿错误，再花一整轮改口。

实测失败原因分布：

| 原因 | 次数 | 能否提前知道 |
|---|---|---|
| 刚发过表情（冷却中） | 16 | ✅ 能 |
| 这一分钟发得太多了 | 14 | ✅ 能 |
| 今天已经发过 N 次 | 1 | ❌ 不能（要扫全部会话） |
| **合计** | **31** | **30 / 31 = 97%** |

代价：**28 个轮次**只调了一次 `send_sticker` 而且失败，合计约 **412,806** prompt tokens ——
什么都没发出去，还得再补一轮。而那些轮次的下一轮是：纯文本收尾 19、`finish` 5、`send_message` 4。

## §2 借鉴了什么

### 2.1 MaiBot 的「动作集」而不是「试错」（`src/maisaka/` ActionSet，GPL-3.0，只取设计）

MaiBot 把"这一轮能做什么"作为**提示词的一部分**下发，而不是让模型去调、去撞、去改口。
我们其实已经有 `src/action-planner.js` 的动作集 —— 只是表情那一格一直只填
"库里有图吗"（`hasSticker`），从没填"现在能不能发"。

**借鉴的是这一格**，不是整个架构。

### 2.2 AstrBot / LangBot 的「阶段前置」

两者的限流都在**入站阶段**判（AstrBot 的 `RateLimitStage`、LangBot 的 `ratelimit` 阶段），
从不为一轮注定失败的对话付模型钱。第 3 轮已经把这条用在**文字额度**上，
这一轮把它用在**表情**上 —— 同一个思路，另一套桶。

### 2.3 故意**没有**借鉴的

- **不复制 MaiBot 的 `ActionSet` 类层次**：它靠继承和多态扩展动作，我们只有十来个动作，
  引入类层次换来的是"加一个动作要改三处"。
- **不学它们把"能不能发"做成硬拦截**：我们只**告诉**模型，工具侧照旧兜底。
  少一层拦截就少一处会跟配置漂移的规则副本 —— 第 3 轮 `resolveMinuteLimit` 单点化
  就是这个教训。

## §3 改了什么

### 3.1 新模块 `src/sticker-quota.js`（145 行，纯函数）

```js
export const STICKER_SCOPE_SUFFIX = '|sticker';
export function scanOwnStickers(ownRecent, parseId)   // → {lastStickerAt, recentStickerIds}
export function assessSticker({sentThisRun, maxPerRun, cooldownMs, lastStickerAt,
                               minuteLimit, stickerTimes, now})
                                       // → {canSend, kind, reason, waitMs, remaining}
export function describeSticker(state)                // → 一句话摘要（能发时返回空串）
```

三道闸门，**顺序与 `send_sticker` 的 execute 完全一致**：

1. 本轮张数（`kind: 'run'`，`waitMs: 0` —— 等一等也不会解除）
2. 会话冷却（`kind: 'cooldown'`，`waitMs` = 剩余冷却）
3. 分钟桶（`kind: 'minute'`，`waitMs` = 最早那条滑出窗口的时间）

顺序必须一致：**先撞哪道闸门决定了模型看到哪句理由**。不一致就会出现
"提示词说冷却中、真发的时候报的是额度满"这种自相矛盾。

### 3.2 `src/sender.js` 新增只读方法 `stickerQuotaFor()`

```js
stickerQuotaFor(chatKey, { now = Date.now() } = {}) {
  const key = String(chatKey) + STICKER_SCOPE_SUFFIX;
  return quotaFrom({ times: this.minuteTimes.get(key) || [], limit: this.#stickerMinuteLimit(), … });
}
```

走的是 `#checkRate` 里那个 `|sticker` 后缀的**独立桶** —— 表情不占文本名额。
只读，不往桶里写（有测试守着）。

### 3.3 `src/orchestrator.js` 新增 `stickerState(chatKey, {cfg, stickerEntries})`

返回 `{canSend, kind, reason, waitMs, remaining, available}`，`kind` 多两种：

- `'empty'` —— 库里一张能发的都没有（**说"没图"而不是"冷却中"，理由不能骗人**）
- `'off'` —— 表情功能关掉了

接线到 `planActions({ …, sticker: this.stickerState(chatKey, {cfg, stickerEntries}) })`。

### 3.4 `src/action-planner.js`

```js
const stickerOk = hasSticker && (!stickerState || stickerState.canSend !== false);
const stickerBlocked = hasSticker && stickerState?.canSend === false;

if (stickerOk) add(ACTIONS.STICKER, '发表情包', '表情库可用');
…
sticker: stickerOk ? 1 : 0,
…
if (stickerBlocked) {
  const why = String(stickerState.reason || '').trim() || '这轮发不了表情';
  note = (note ? `${note} ` : '') + `${why}，这轮用文字，别试图发表情。`;
}
```

`sticker` 缺省为 `null` → 视为"能发"，**既有调用方行为完全不变**。

### 3.5 `enablePack` / `escalateModel` 改成箭头函数

```js
enablePack: (packs) => {          // this 回到 Orchestrator
  …
  for (const d of [...allAllowed]) {   // ← 顺手修了第二个 bug
    if (toolDefs.includes(d)) continue;
```

**顺带发现的第二个 bug**：原来遍历的是 `this.toolDefs`（就算 `this` 指对了），
而 `if (toolDefs.includes(d)) continue` 判的是**已经裁过**的 `toolDefs` ——
遍历全集、用子集判重，`includes` 对每个元素都可能是真/假混杂，
但真正的问题是 `this.toolDefs` 是全集、`toolDefs` 是子集，逻辑上"想加回被裁掉的包"
和"遍历全集"根本不是一回事。改成遍历 `allAllowed`（开关过滤后的全集）才正确。

`switchAllowed` 那道重复检查删掉了 —— `allAllowed` 已经过它。

## §4 踩到的坑

### 4.1 接线测试里 `assert` 忘了 import

第一版 `test-sticker-quota-wire.mjs` 里写了 9 个 `assert.equal`，但文件头只 import 了
`fs / os / path`。9 个用例全部报 `assert is not defined` —— 而不是报"逻辑不对"。

**教训**：`assert is not defined` 和"断言失败"看起来完全不同，但都表现为"用例红了"。
写新测试时先跑一次，看红的是不是"你想红的那一条"。

### 4.2 假数据过不了 `isStickerSendable`

`{ id: 's1', file: 'x.png', usable: true }` 被判为"不可发送"，因为
`isStickerSendable` 要求**有本地副本或 http(s) 地址**：

```js
export function isStickerSendable(entry) {
  if (!entry || entry.disabled) return false;
  if (stickerLocalCopy(entry)) return true;
  return /^https?:\/\//i.test(String(entry.url || ''));
}
```

于是 `stickerState` 返回 `kind: 'empty'`（"库里没有能发的图"），
和用例期望的 `'cooldown'` 差了十万八千里。改成 `{ id: 's1', url: 'https://example.com/a.png' }`。

**这个"失败"其实证明了 `empty` 分支是对的** —— 假数据的错，不是代码的错。

### 4.3 桶传空数组 = 永远还能发

第一版 `stickerState` 把分钟桶判据传给 `assessSticker`：

```js
minuteLimit: quota.unlimited ? 0 : quota.limit,
stickerTimes: [],          // ← 空数组
```

`assessSticker` 里 `used = ts.length = 0`，于是 `remaining = limit - 0 = limit > 0`，
**永远返回"能发"** —— 额度那道闸门形同虚设，而单测是绿的（因为单测直接调
`assessSticker` 并传了真实时间戳，压根没走这条接线）。

改成：`minuteLimit: 0`（让 `assessSticker` 只判前两道），第三道用 sender 算好的
`quota.remaining` 单独判。**这就是"接线测试"存在的理由** —— 规则测过了，接线可能还是断的。

### 4.4 变异验证：两次都抓到了

| 变异 | 结果 |
|---|---|
| `stickerOk` → `hasSticker`（退回旧行为） | `test-sticker-quota-wire.mjs` **EXIT=1**，8 通过 / 1 失败 |
| `enablePack: (packs) => {` → `enablePack(packs) {`（退回方法简写） | `test-enable-pack-binding.mjs` **EXIT=1**，2 通过 / 2 失败 |

两次都还原并重跑绿色。

## §6 残留问题

1. **"同一张图今天发过"没提前判**。要扫全部会话的消息存档（`listChats` × 1000 条），
   每轮都扫一遍不值当，而且只占 1/31 的失败。工具侧仍然照旧兜底。
2. **`stickerState` 每轮都算一次，扫的是最近 40 条消息**（`sticker.recentWindow`，可配）。
   群很吵的时候 40 条可能不够覆盖到上次表情 —— 那就退回"看起来能发"，
   由工具侧的冷却兜底。**宁可漏判也不能误判**：误判会把正常表情削掉。
3. **`escalateModel` 的修复没有被真实场景验证过**。`escalate_reasoning` 在 1000 份会话里
   被调 0 次，所以"修好了"目前只有静态断言（源码形态 + `this.emit` 可派发）撑着，
   没有一次真实的升级流程跑通。要等主人真的开路由用一次。
4. **`available` 字段算了但没用**。`stickerState` 会数"库里有多少张能发的"，
   目前只用于判断 `empty`，没有写进提示词。理论上"只有 1 张可发"和"有 40 张可发"
   该给不同的建议，但没实测数据支撑，先不写。
5. **`load_tools` 修好之后的行为没有端到端验证**。它现在真的能加回定义了，
   但"加回来之后下一轮能不能调"没有真跑过一次（要起一个真模型 + 一个被裁场景）。
   静态上 `toolDefs.push(d)` 之后 `openAiTools` 会重建，`executeTool(toolDefs, …)`
   读的也是同一个数组，逻辑上通；但没有实测。
6. **面板没有 `sticker-quota` 的可视化**。`noteSkip` 的 stage 表里没有新增条目
   （这一轮不涉及 skip 阶段，表情是"提示词字段"而不是"整轮跳过"），
   所以面板上看不到"这一轮为什么没发表情" —— 只能从提示词快照里看。
