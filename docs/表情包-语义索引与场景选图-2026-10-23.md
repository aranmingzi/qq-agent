# 表情包：语义索引与场景选图（2026-10-23）

## 一句话

表情发得不准，根因不是"库里没有表情"，而是**它不知道这张图表达的是什么态度、什么场合该用**。
这次把《大肥鱼 × DeepSeek 鲸鱼娘》整套（589 张去重后）逐张读图做了语义标注，并把"选图"从
"凭备注瞎猜"改成"按场景检索"。

## 数据形状

`data/stickers.json` 每条的字段（`src/stickers.js::normalizeStickerEntry` 是唯一入口）：

| 字段 | 说明 |
| --- | --- |
| `id` | 本次导入的条目是 `dfy_<md5前10位>`；早期手工库是 `dayu_*`；QQ 收藏同步来的是原 resId |
| `localPath` | 本地副本，**发送只认它**（`data/sticker-files/<md5>.jpg\|gif`） |
| `desc` | 画面一句话（≤30 字），检索与提示词展示用 |
| `localNote` | `图上字：…｜用法：…`，图上文字往往是这张图的真意 |
| `tags` | 场景词（来自固定词表）+ 情绪词；早期条目还留着"涨价/傲娇"这类自由词，关键词检索仍可用 |
| `usage` | 什么场合发（≤22 字） |
| `source` | `qq`（收藏同步）/ `manual`（早期整备）/ `ai`（本次导入与 AI 收藏） |

**硬约束**：`sender.js::#stickerSource` 只把 **≤4MB** 的本地副本转 base64，超了就退回 `url`（本次导入的条目 url 为空）→ 直接发不出去。
所以所有入库图都必须压到 4MB 以内，最大 600px。

**来源过滤红线**：`mergeStickerLibrary()` 末尾会把 `source==='qq'` 且本次没同步到的条目删掉。
所以非 QQ 来源的条目**不能**把 source 写成 `qq`（写 `ai`/`manual` 才活得下来）。

## 场景词表（30 个，单一真源）

`src/stickers.js::STICKER_SCENES`：

```
夸赞 自夸 嘲讽 怼人 无语 大笑 开心 害羞 撒娇 委屈
哭 震惊 疑惑 拒绝 同意 鼓励 摆烂 困 吃瓜 害怕
打招呼 道别 道谢 道歉 吐槽 AI话题 穷 催促 装傻 嫌弃
```

- 词表改动后必须重跑导入/补标注，否则库里出现"词表外的标签"，场景索引统计不到。
- 区分要点（写进识别提示词了）：嘲讽＝调戏阴阳（"杂鱼♡""就这"）；怼人＝直接凶骂；
  无语＝翻白眼/不想说话；摆烂＝累/躺平/不想努力。
- `AI话题` 是唯一的话题类标签：这套包大半是模型梗（涨价、GA、跑分、GPT 酱），
  没有它这些图只能靠关键词碰运气。

### 词表外的自由标签靠别名表兜住

识图模型自然吐的是"得意/自信/笑死/绷不住"这类词，和 30 个场景词对不上。
早期做法是让 `sticker-retag.mjs` 事后补，但它只处理"一个场景词都没有"的条目，
而且补完再来一批新包又会漏——本次就漏了 7 张（标签全是`得意`）。

现在改成**读取侧归一**：`src/stickers.js::SCENE_ALIASES` 把常见自由词收敛到场景词，
`canonicalScenes(tags)` 在 `buildStickerContext`（统计/索引）和 `formatStickerList`（检索打分）
两处统一调用。好处是**写库不用动、老数据和新包一并生效**，模型搜"自夸"能搜到标签写着"得意"的图。

```js
得意/自信/骄傲/炫耀/最强 → 自夸      高兴/快乐/兴奋 → 开心
笑死/绷不住 → 大笑                    讽刺/阴阳怪气/嘲笑 → 嘲讽
困惑/懵逼/问号 → 疑惑                 流泪/泪目/崩溃 → 哭
恐惧 → 害怕                           感谢/谢谢 → 道谢
```

新增包若出现新自由词，优先往 `SCENE_ALIASES` 加一行，而不是改词表（改词表要全库重跑）。
当前归一后：596/596 有场景词，`自夸` 从 79 涨到 126。

## 三件套脚本

### 1. 整包导入 `scripts/import-sticker-pack.mjs`

```bash
node scripts/import-sticker-pack.mjs --dir "<表情包目录>"          # 全流程
node scripts/import-sticker-pack.mjs --dir ... --dry-run          # 只清点
node scripts/import-sticker-pack.mjs --dir ... --force            # 应用在跑也强制写盘（危险）
```

流程：扫描 → md5 去重 → 规范化到 `data/sticker-files` → **感知去重** → 逐张识图 → 合并进 `stickers.json`。

- 识别结果逐行追加到 `work/sticker-pack-cache.jsonl`（`--cache` 可改），重跑命中的 md5 直接复用，不重复烧 token。
- 识图走 `config.vision.qwen`（硅基流动 Qwen3-VL），输出 `text/desc/emotion/scene/usage` 严格 JSON。
- 三视图/设定图（`三视图|设定图|角色卡|立绘|参考图|线稿`）照样入库但**直接停用**——它们不是反应图，发出去只会让人莫名其妙。

### 2. 旧条目补场景 `scripts/sticker-retag.mjs`

```bash
node scripts/sticker-retag.mjs            # 只补"没有任何场景词"的条目
node scripts/sticker-retag.mjs --dry-run
```

纯文本归类（用主模型，不用重新看图），把 `dayu_*` / `qq` 那批自由标签对齐到场景词表，
原有标签保留（关键词搜索要用）。本次补了 170 条。

### 3. 索引画廊 `scripts/sticker-gallery.mjs`

```bash
node scripts/sticker-gallery.mjs --out "路径/表情包索引.html"
```

生成单页 HTML（缩略图内嵌 base64，可拷走），可按场景筛选、按文字搜索。
**人工校对就靠它**：表情发错九成是备注写错，而不是检索错。

## 提示词侧改了什么

1. `buildStickerContext()`（`src/stickers.js`）：库小的时候仍然列清单；库大了（本次 596 张）
   改成**场景索引**——只给"场景=可发张数"一行 + 6 条"常用" + 取用方法，约 475 字。
   之前那版按 useCount 取 top10，在 800 条库里等于随机，且没有场景概念。
2. `list_stickers` 的排序（`formatStickerList`）：场景标签精确命中 > 标签包含 > 正文命中，
   同分再按使用次数、最近没用过的排。不加排序＝随机返回，模型只能瞎挑。
   返回字段做了瘦身（`localNote` 截 80 字），24 条不至于撑爆上下文。
3. `buildStickerStrategyHint()`：明确"先定此刻情绪 → 按场景词查 → 看 usage 挑 → 不确定就 `get_sticker_image`"，
   并强调**带字的表情以图上文字为准**（反讽别当夸奖用）。

### 第二轮：为什么上线后还是几乎不发（2026-10-23 下午）

上线几小时后统计：自发消息 4250 条，带表情只 **61 条（1.4%）**；启用 596 张里只用到 **14 张，
全是旧 `dayu_*`**，新导的 **359 张 `dfy_` 一次都没发**。

先排除的三个假设（都有数据）：
- 提示词没缺：301 个会话里 190 个 userPrompt 有【表情包】段（段在 userPrompt 不是 system，别搜错地方）。
- 不是被拦：`skip-log.jsonl` 175 条里 0 条与表情有关；"发送频率超限"整份日志只出现 1 次。
- 冷却不是主因：`cooldownMs=600000` 只把上限压到 272 个"10 分钟槽位"，实际用 61 个（22.4%）。

真因两条，都在"模型愿不愿意动手"这一侧：

1. **「常用」是正反馈自锁**：`favorites` 按 `useCount` 排序取前 6 → 用过的永远占位，
   新图 `useCount=0` 永远进不去。模型看到的**现成 id 只有那 6 张旧图**，61 次全落在这里。
   这不是"模型偏爱旧图"，是它只认识这 6 个 id。
2. **其余 590 张要两步**：`list_stickers` 查 → `send_sticker` 发，比直接 `send_message` 多一次工具往返；
   策略提示又写成"普通闲聊不用每条都配、3~5 轮一张够了"（读起来是上限，不是动机）。模型理性选择打字。

### 改法（本次已上线）

- `buildStickerContext()`：候选池改成 **常用 3 张（稳定发得准）+ 新面孔 5 张（`useCount=0`，每轮随机轮换，
  标注多的优先）**，一共 8 个 id 直接摆出来；指令改成"id 可直接 send_sticker，不用先查"。
  段长 475 → 620 字。轮换用 Fisher-Yates，实测两次调用候选不同。
- `buildStickerStrategyHint()`：删掉"3~5 轮一张"这种上限措辞，改成"这些时候配一张比纯文字更像真人"，
  并把"两步流程"降级为兜底（候选都不合适才查）。
- `sticker.cooldownMs`：600000 → **180000**（3 分钟）。默认值在 `src/config.js`，运行值用
  `POST /api/config` 热更新（走 app 自己写盘，避免被回写覆盖）。

先看效果：目标把 1.4% 拉到 4~6%，同时让 `dfy_` 那 359 张真正开始被用。

## 踩过的坑（都是本次实测）

- **动图重编码会变大**：4.8MB 的 78 帧 gif，直接 `-vf scale` 出来 16.9MB。
  必须 `fps=12 + palettegen/paletteuse`，而且 `split[a][b]` 有两个输出，只能用 `-filter_complex`，
  写成 `-vf` 会直接失败（被 catch 吞掉，看起来像"静默退化成静帧"）。压不到 4MB 就退化成静帧 jpg。
- **`force_original_aspect_ratio=decrease` 会放大**：目标写 600:600 时，300×327 的图被放大到 550×600，
  体积反而翻倍。正确做法是先 probe 出源尺寸，目标框用 `min(1, 600/max(w,h))` 算，绝不放大。
- **透明底直接 `format=rgb24` 会出黑边**：必须先 overlay 到白色画布（画布尺寸=目标尺寸，否则又变成大留白）。
- **md5 只能抓字节级重复**：旧库 `364.webp` 和新包同名图 jpg 字节不同，md5 抓不到。
  改用 16×16 dhash（ffmpeg `scale=17:16,format=gray` 读 272 字节）：同一张图重压缩距离 17，
  不同图 ≥110，阈值取 40。本次靠它跳过 230 张重复。
- **应用运行时写盘会被回写覆盖**：`StickerManager` 构造时载入 `stickers.json`，同步后 `saveStickerStore` 整份回写。
  本次被覆盖过一次（写完 608 条，几十秒后变回 838 条）。
  正确顺序：**退出应用 → 写盘 → 再确认一次文件 → 重启应用**。
  杀进程要杀命令行不含 `--type=` 的 electron 主进程（`taskkill /F /T /PID`）。
  沙箱里 `schtasks` 被黑名单挡住，只能用后台任务方式起来。
- **别把各场景张数相加当"已标注数"**：一张图有 2~3 个标签，相加会得出比总数还大的数。

# 第三轮：从"用得多"到"用得散"（2026-10-26）

## 现象

"常用 3 + 新面孔 5"上线几天后统计：610 张库里只有 25 张被发过，
而前 3 张吃了 **68/90 次**（36 / 21 / 11 次），第 4 名直接掉到 5 次。
候选固定是那 3 张 + 5 张随机新图 —— 模型每次都看见那 3 个 id，就每次都挑它们。

结论：**"别总用同一张"这种提示词永远无效**（同 phrase-guard 的教训），
模型不"偏爱"旧图，它只是**只认识摆在眼前的 id**。只要一张图随时可用，就会被反复选。

## 改法：把发过的图先藏起来

`pickStickerCandidates()`（`src/stickers.js`）成为候选的唯一来源，三道闸：

1. **冷却**：`candidateCooldownMs`（默认 6 小时）内发过的不进候选；`dailyPerIdCap=1` 时
   "今天发过的"也直接排除（和发送闸对齐 —— 不对齐会出现"候选里有它、真发却被拦"）。
   库小/全在冷却期时三级放宽，宁可复用也不让候选空着（空着模型只能打字）。
2. **三档配额**：老手（≥10 次）1 张、半熟（1~9 次）3 张、全新 4 张；老手位有一半轮次
   干脆不给（只有三五张图，占满了就是第二块招牌）。补齐顺序 fresh → known → veteran。
   档内用**加权随机**（有 `usage` / 多标签的更容易被抽），不是按标注全序排 ——
   那样 22 张半熟图里"标注最全的 5 张"会永远排前面，等于换一批熟客继续自锁。
3. **场景分散**：同一场景最多 ⌈limit/3⌉ 张，一张图的所有场景标签都占额度。
   否则 10 个候选全落在"无语"里，模型照样找不到贴题的那张。

配套改动：

- `formatStickerList()` 同分档内改成 `有用法说明 → 用得少 → 最久没发`（原来按次数降序，
  主动查询也全是老脸）；返回字段**删掉 useCount** 换成 `fresh` —— 次数一露出来，
  模型就把它当推荐指数，自锁绕一圈又回来。
- `rankStickerAlternatives()` 换发兜底去掉 useCount 正向权重（换发的意义就是别再糊同一张）。
- 候选行尾标 `｜没发过`：不标出来模型对陌生图会犹豫，宁可退回熟悉的。
- `sticker.dailyPerIdCap` 2 → **1**；新增 `sticker.candidateCooldownMs`（默认 21600000）。
- 候选 8 → 12 张（段长 620 → 987 字，每轮多约 0.37K tokens，换覆盖率值）。

## 实测（610 张库，40 轮候选）

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 40 轮出现过的不同表情 | ~15 | **208** |
| 相邻两轮候选重叠 | 6~8 / 10 | **1.2 / 10** |
| 老招牌出现在候选的轮次 | 40 / 40 | 19 / 40 |
| 候选里"没发过"的占比 | 5 / 8 | 8~9 / 12 |

## 测试

`test/test-sticker-pick.mjs`（15 项，已进 `npm test`）。五道闸各自做过 A/B：
拆掉冷却 / 今日排除 / 老手位概率 / 排序去偏 / 场景分散，测试**都会红**。

⚠️ 写这类用例的两个坑（本次都踩了）：
- **同一判据写两遍会互相兜底**：6h 冷却和"今日排除"范围重叠，拆一个另一个还挡得住，
  测试全绿。所以"6h 冷却"用例特意放在**凌晨**（上次发送是昨晚，跨天、只过 3 小时），
  "今日排除"用例放在**深夜**（当天凌晨发的，过了 6h）—— 互不重叠。
- **池子太小会触发放宽**：`usable.length < limit` 时三级兜底把被挡的图放回来，
  拿小池测闸永远是绿的。用例池子要 ≥ limit，且扫 20 个 seed
  （单跑一次"随机没抽到"也是假绿）。
