# 语音通话（控制台内）· 2026-10-29

> 目标：让 QQagent 能「打电话」—— 按一下开始，说话，它听懂、按人设回话、用配置的音色念出来，它说话时你一开口就被打断。
>
> 边界：**不是**在 QQ 客户端里接电话。协议层做不到（下面有证据），所以做在控制台里。

---

## 0. 先说清楚「为什么不能在 QQ 里打」

这一条必须先讲，否则后面所有设计都像绕路。

| 来源 | 结论 | 证据 |
|---|---|---|
| NapCat（`snowluma/napcat.mjs`） | 动作表里**没有任何**通话/RTC 端点 | `send_*` 共 23 个（`send_ark_share` … `send_uid`）、`get_*` 含 `get_record`/`get_clientkey` 等；`grep -ci "avsdk\|voice_call\|video_call"` → **0** |
| Lagrange.Core | 语音通话 🔴、私聊语音通话 🔴 | [README_zh.md 功能表](https://github.com/LagrangeDev/Lagrange.Core/blob/0077972f860f84922ea9fdefcd56b59399322791/README_zh.md) |
| 腾讯技术文章 | QQ 音视频走闭源 AVSDK → NTRTC | <https://cloud.tencent.com/developer/article/2433985> |
| QQ 官方机器人 API | 只有 QQ **频道**语音子频道，且**只能播不能收** | [`audio_control`](https://bot.q.qq.com/wiki/develop/nodesdk/audio/audio_control.html) 的 `postAudio(channelID, {audio_url, text, status})`、`botOnMic`/`botOffMic`；QQagent 没有 guild 层 |

所以「在 QQ 里接电话」只有两条非协议路径：Android root + adb 自动接听（如 `AndroidMsky/RootPlay`）、
桌面端虚拟声卡 + UI 自动化。两条都脆弱且需要用户额外配置，**不适合做进产品**。

**决策**：做在控制台里，链路全在本机，不经过 QQ 服务器。

```js
voice: {
  enabled: true,          // 关掉就整页不可用

  maxTurns: 40,           // 单次通话上限 40 轮

  vadMinSpeechMs: 250,    // 连续有声多久才算「开始说话」
  vadSilenceMs: 700,      // 连续无声多久才算「说完了」

  idleTimeoutMs: 60000

```

## 2. 借鉴来源

| 来源 | 借了什么 | 怎么落的 |
|---|---|---|
| [Pipecat](https://github.com/pipecat-ai/pipecat)（BSD-2） | Frame → FrameProcessor → Pipeline 的**分层**思路 | `pcm.js`（纯数据）→ `vad.js`（纯状态机）→ `voice-turn.js`（纯对话）→ `voice-gateway.js`（IO 编排）。每层可单独注入、单独测，没有一个函数同时碰网络和音频 |
| [xiaozhi-esp32 协议文档](https://github.com/MiLusheep/xiaozhi-esp32/blob/main/websocket.md) | 「**二进制帧传音频、文本帧传控制**」 | `voice-gateway.js` 的帧约定；理由是音频 base64 会胖 33% 且两头都要解析 |
| [LiveKit Agents](https://github.com/livekit/agents)（Apache-2.0） | 语义断句 / 打断检测（v1.5 在 500ms 重叠下 86% 准确率） | **只借了「要能打断」这个结论**，没借实现。本轮用能量 VAD + `interrupt` 消息；语义断句留给下一轮 |
| DashScope realtime 文档 | **反例**：run-task 之后必须发**裸二进制 PCM 帧**，包在 `continue-task` 里会静默失败（不报错、也不出结果） | 因此本轮**不做流式 ASR**，走已验证的「WAV → HTTP `transcribeSpeech`」。见 §5 |

MaiBot / AstrBot / LangBot 在这一轮没有贡献（它们的通话能力同样是零）。

### 3.3 真实链路冒烟（临时脚本，已删除）

起真正的 `createApp()` + `app.start()`，用真正的 `ws` 客户端连 `ws://127.0.0.1:<port>/voice/ws`：

```
握手结果: { "ok": true, "ready": { "type": "ready", "vad": "energy",
           "asrModel": "qwen3-omni-flash", "ttsFormat": "mp3", "sampleRate": 16000 } }
错路径:  rejected: socket hang up
```

这一步抓到了一个真实 bug：**第一版把 `ensureVoiceGateway()` 放在 `server` 创建之后，但那时还没人调用它** ——
`/api/voice/status` 里才调用，于是「没打开过状态接口就直接连 ws」会 404。
改成在 `start()` 里挂载（而不是构造期）后修复：既保证真实启动一定有钩子，也不会让每个测试进程多一个常驻监听者。

## 4. 状态机与帧约定

```
idle → listening → transcribing → thinking → speaking → listening
```

- 客户端 → 服务端：二进制 = 16k/16bit/单声道 PCM；文本 = `{type:'start'|'stop'|'interrupt'|'ping'}`
- 服务端 → 客户端：二进制 = 合成音频；文本 = `{type:'ready'|'state'|'asr'|'reply'|'error'|'dropped'|'stop-playback'|'closed'}`
- **绝不静默**：识别失败、合成失败、合成结果为空、音频太短、非法 JSON、未知消息类型 —— 每种都有明确的
  `error` 或 `dropped`，且连接不断、状态回到 `listening`。

## 5. 残留问题（下一轮候选）

1. **ASR 不是流式**，一次识别要等整段说完 + 一次 HTTP 往返，实测延迟约 1~2 秒。
   下一轮换 `paraformer-realtime-v2` 可以直接把这 1~2 秒压掉大半。
   **踩坑记录**：DashScope realtime 要求 run-task 之后发**裸二进制 PCM 帧**，
   把 PCM 包进 `continue-task` 会**静默失败** —— 不报错、也不出结果，排查会非常久。这一轮因此没动它。
2. **没有 AEC**。它说话时麦克风仍然在收，扬声器外放会被自己听到。
   当前缓解：客户端 `echoCancellation: true` + 播放期间保持较高 VAD 阈值。真要做到稳，需要 WebRTC 那套回声消除。
3. **能量 VAD 在吵的地方会误触发**。阈值可配，页面上有音量条能看出麦克风状态，但吵的环境下体验会掉。
   Silero ONNX 是更稳的替代，代价是引入 `onnxruntime-node` 原生依赖 —— 本轮明确不做。
4. **单会话**。一个连接一次通话，没有多方、没有转接。
5. **通话内容不进长期记忆**。这是有意的（避免把口语碎片塞进记忆库），但如果用户期望「它记得刚才电话里说的」，
   需要下一轮加一个显式的「这通电话要不要记」。
6. **`/api/voice/status` 的 `stats` 是进程内计数**，重启清零。做长期观测需要落盘。

---

## 6. 一句话总结

协议层不让在 QQ 里接电话，那就把整条语音链路搬进控制台：
**麦克风 → 16k PCM → 能量断句 → 复用已有 `transcribeSpeech` → 轻量人设对话 → 复用已有 `synthesizeSpeech` → 播放**，
传输复用已有 http server 的 `upgrade`（`ws` 本来就装了），不加依赖、不新开端口、不碰 QQ 消息链路。
