# 异步点歌队列：方案与接口规范

> 针对「Node 同步等 Python 渲染 20–180s → HTTP 超时 / 事件循环被占」的改造方案。
> 本文给两套实现的对照：**A. 本仓库已落地**（进程内队列 + 子进程 + SSE），
> **B. 独立推理服务**（FastAPI + Redis + Celery + WebSocket），用于多机/多 worker 场景。
> 先看结论，再决定要不要读 B 的代码。

---

## 0. 先说三个结论

**① 你的瓶颈不是「HTTP 超时」，是「把渲染当成请求的一部分」。**
把超时从 180s 调到 600s 只是把失败往后推，队列里排三首照样爆。
正确的切分是：请求只负责「登记意图」，渲染是另一条生命线。这一点与用不用 Redis 无关。

**② 在你这台机器上，Redis + Celery 是负收益，不是升级。**
- 显存 4GB，Demucs + RVC + ONNX 不能并存 → worker 并发只能是 **1**；
- 队列并发 1 时，Celery 的 broker、结果后端、序列化、进程池全部是纯开销；
- 更关键的是 **CUDA 不能 fork**：`prefork` 池里初始化 torch 会直接报
  `Cannot re-initialize CUDA in forked subprocess`，必须 `-P solo`——
  而 solo 池 + concurrency 1，和一个进程内队列的能力完全等价。
- 真正值钱的是**阶段缓存**（同一首歌第二次 0.78s）和**内容寻址去重**，
  这两样跟 Redis 没关系，已经实现了。

**③ 什么时候该上 B 方案**：需要多台机器跑、需要 Worker 独立重启不影响 QQ 连接、
或者有外部系统（Web 面板 / 其他机器人）要调这个能力。触发条件写在 §6。

## 1. 架构

### 1.1 已落地：单进程编排（`src/job-queue.js` + `song-jobs.js`）

```
QQ 群
  │  @机器人 点歌
  ▼
┌──────────────────────────── Node（QQ Agent） ────────────────────────────┐
│  Orchestrator                                                            │
│    └─ tools.js  sing_lyrics / sing_cover                                 │
│         └─ song-router.js  有原曲？有旋律？→ 决定路线                     │
│              └─ song-jobs.js  submitSing / submitCover                   │
│                   └─ JobQueue（进程内，concurrency=1）                    │
│                        ├─ 内容寻址 key（同参数直接复用成品）              │
│                        ├─ data/jobs.jsonl（重启恢复 + 僵尸清理）          │
│                        └─ 心跳 240s，超时判死                             │
│                                                                          │
│  入队即返回（实测 2–11ms）──► 模型回一句 ──► 群友该干嘛干嘛               │
│                                                                          │
│  作业线程（仍是 Node，单飞）：                                            │
│    ├─ melody-auto.js → melody_extract.py（Demucs→CREPE→melody v2）       │
│    ├─ sing-song.js   → sing_engine.py（DiffSinger）                      │
│    └─ cover-song.js  → route_a.py（Demucs→F0→RVC→HF→mix）                │
│         ↑ 全部 async spawn，stdout 逐行喂进度（`[1/5]` 做锚点）          │
│                                                                          │
│  完成 ──► song-deliver.js ──► 语音条 / 44.1k 文件 ──► 原会话             │
│  进度 ──► /api/events（SSE，job.queued / job.stage / job.done）          │
└──────────────────────────────────────────────────────────────────────────┘
                                   │ 子进程
                                   ▼
┌──────────────────── Python 推理（两个 venv） ────────────────────────────┐
│ diffsinger-env (Py3.12, torch cu126, ORT-GPU)  ── DiffSinger / 解码      │
│ rvc/py310      (Py3.10, torch cu121)           ── Demucs / RVC / CREPE   │
│                                                                          │
│ cache/stages/  decoded / stems / f0 / rvc / hf / final   ← 四级命中      │
└──────────────────────────────────────────────────────────────────────────┘
```

要点：
- **没有 HTTP 参与渲染**。Node 直接 spawn Python，stdout 就是进度通道；
  进程退出码 + 产物文件就是结果，不需要结果后端。
- **队列只做三件事**：限并发（GPU 串行）、去重（key）、可观测（jsonl + SSE）。
- 任务失败重试有上限（`maxAttempts=2`），且翻唱类错误标记 `retryable=false`
  （音频坏了重跑只会再烧一遍 GPU）。

### 1.2 方案 B：独立推理服务（多机 / 多 worker）

```
                 ┌──────────────┐
   QQ 群 ───────►│ Node 机器人  │
                 │  (无状态)     │
                 └──┬────────┬──┘
        POST /songs │        │ WS /ws/tasks/{id}
        (202 + id)  │        │ (或 1s 轮询 GET /tasks/{id})
                    ▼        ▲
              ┌─────────────────────┐
              │ FastAPI (API 层)     │
              │  只做参数校验/鉴权/   │
              │  写 Redis/发布事件    │
              └──────┬───────┬──────┘
                     │       │
             LPUSH   │       │ PUBLISH task:{id}:events
                     ▼       │
              ┌──────────┐   │
              │  Redis   │───┘
              │ queue +  │
              │ 状态 hash │
              └────┬─────┘
                   │ BRPOP / Celery
                   ▼
        ┌────────────────────────┐
        │ Worker（GPU 机器，×1）  │
        │  Demucs → RVC → 混音    │
        │  每阶段 HSET 进度       │
        └────────────────────────┘
```

数据流：
1. `POST /songs` → 生成 `task_id`（= 内容 hash，天然幂等）→ `LPUSH queue` → `HSET task:{id}` → 202。
2. Worker `BRPOP` → 更新 `status=running` → 逐步 `HSET stage/progress` + `PUBLISH`。
3. 完成 → `HSET status=success result_path=...` → `PUBLISH` → API 层 WS 把它推给 Node。
4. Node 收到 `success` → 读音频 → 发群。

### 2.2 接口规范

| 方法 | 路径 | 入参 | 返回 | 说明 |
|---|---|---|---|---|
| POST | `/songs` | `{kind, src?, name?, lyrics?, start?, dur?, voice?, params?}` | `202 {task_id, deduped, position, eta_sec}` | 立即返回，绝不等渲染 |
| GET | `/tasks/{id}` | — | `{status, stage, progress, eta_sec, result?, error?}` | 轮询兜底 |
| POST | `/tasks/{id}/cancel` | — | `{ok}` | queued 直接删；running 置标记 |
| GET | `/health` | — | `{ok, gpu, queue_len, worker_alive_at}` | 给 Node 做熔断 |
| WS | `/ws/tasks/{id}` | — | 事件流 | `queued/running/stage/success/failed` |

状态机：`queued → running → success | failed | canceled`（终态不可逆）。

### 2.3 API 层（`app/main.py`）

```python
import json, time, uuid, hashlib
from fastapi import FastAPI, HTTPException, WebSocket, WebSocketDisconnect, Header
from redis import Redis
from .config import REDIS_URL, QUEUE_KEY, API_TOKEN
from .schemas import SongRequest, TaskView
from .store import TaskStore

app = FastAPI(title="QQ Song Render Service")
rds = Redis.from_url(REDIS_URL, decode_responses=True)
store = TaskStore(rds)


def content_id(req: SongRequest) -> str:
    """内容寻址：同一首歌同一段参数 → 同一个 task_id，天然去重。"""
    raw = json.dumps(req.model_dump(exclude_none=True), sort_keys=True, ensure_ascii=False)
    return hashlib.sha1(raw.encode()).hexdigest()[:16]


@app.post("/songs", status_code=202)
def submit(req: SongRequest, x_token: str = Header(default="")):
    if API_TOKEN and x_token != API_TOKEN:
        raise HTTPException(401, "bad token")

    tid = content_id(req)
    # 已有成品：直接返回终态，不发音频（让 Node 自己按 result_path 发）
    prev = store.get(tid)
    if prev and prev["status"] == "success":
        return {"task_id": tid, "deduped": True, "position": 0, "eta_sec": 0,
                "status": "success", "result": prev["result"]}

    # 同一任务已在队列里：不要重复 LPUSH
    if prev and prev["status"] in ("queued", "running"):
        return {"task_id": tid, "deduped": True,
                "position": store.position(tid), "eta_sec": prev.get("eta_sec", 0)}

    store.create(tid, req.model_dump())
    rds.lpush(QUEUE_KEY, tid)          # 队列只存 id，参数在 hash 里
    return {"task_id": tid, "deduped": False,
            "position": store.queue_len(), "eta_sec": store.estimate(req)}


@app.get("/tasks/{tid}", response_model=TaskView)
def status(tid: str):
    t = store.get(tid)
    if not t:
        raise HTTPException(404, "task_not_found")
    return t


@app.post("/tasks/{tid}/cancel")
def cancel(tid: str):
    t = store.get(tid)
    if not t:
        raise HTTPException(404, "task_not_found")
    if t["status"] in ("success", "failed", "canceled"):
        return {"ok": False, "reason": t["status"]}
    store.set_cancel(tid)              # worker 在每个阶段边界检查这个标记
    return {"ok": True}


@app.websocket("/ws/tasks/{tid}")
async def ws_task(ws: WebSocket, tid: str):
    await ws.accept()
    pub = rds.pubsub()
    pub.subscribe(f"task:{tid}:events")
    # 先补一帧当前状态（客户端可能连晚了）
    cur = store.get(tid)
    if cur:
        await ws.send_json({"event": "snapshot", **cur})
    try:
        while True:
            msg = pub.get_message(ignore_subscribe_messages=True, timeout=5.0)
            if msg:
                await ws.send_json(json.loads(msg["data"]))
                if json.loads(msg["data"]).get("status") in ("success", "failed", "canceled"):
                    break
            else:
                await ws.send_json({"event": "ping", "ts": int(time.time())})
    except WebSocketDisconnect:
        pass
    finally:
        pub.close()
        await ws.close()
```

### 2.4 状态存储（`app/store.py` 核心）

```python
import json, time

class TaskStore:
    def __init__(self, rds):
        self.r = rds

    def _k(self, tid): return f"task:{tid}"

    def create(self, tid, payload):
        self.r.hset(self._k(tid), mapping={
            "id": tid, "status": "queued", "stage": "queued", "progress": 0,
            "created_at": int(time.time()), "payload": json.dumps(payload, ensure_ascii=False),
            "eta_sec": self.estimate_raw(payload),
        })
        self._publish(tid, {"event": "queued", "status": "queued", "progress": 0})

    def get(self, tid):
        h = self.r.hgetall(self._k(tid))
        if not h: return None
        h["progress"] = int(h.get("progress", 0))
        h["eta_sec"] = int(h.get("eta_sec", 0))
        if h.get("result"): h["result"] = json.loads(h["result"])
        if h.get("error"):  h["error"]  = json.loads(h["error"])
        return h

    def update(self, tid, **fields):
        self.r.hset(self._k(tid), mapping={k: str(v) for k, v in fields.items()})
        self._publish(tid, {"event": "stage", **fields})

    def finish(self, tid, result):
        self.r.hset(self._k(tid), mapping={
            "status": "success", "progress": 100,
            "result": json.dumps(result, ensure_ascii=False),
            "finished_at": int(time.time())})
        self._publish(tid, {"event": "done", "status": "success", "result": result})

    def fail(self, tid, code, message):
        self.r.hset(self._k(tid), mapping={
            "status": "failed", "error": json.dumps({"code": code, "message": message}, ensure_ascii=False),
            "finished_at": int(time.time())})
        self._publish(tid, {"event": "done", "status": "failed", "error": {"code": code, "message": message}})

    def _publish(self, tid, payload):
        self.r.publish(f"task:{tid}:events", json.dumps(payload, ensure_ascii=False))
```

### 2.5 Worker（两种写法，选一种）

**RQ 风格手写循环**（依赖最少，推荐 GPU 单机）：

```python
# app/worker.py
import json, os, signal, time
from redis import Redis
from .config import REDIS_URL, QUEUE_KEY
from .store import TaskStore
from .pipeline.cover import run_cover
from .pipeline.sing import run_sing

rds = Redis.from_url(REDIS_URL, decode_responses=True)
store = TaskStore(rds)
HEARTBEAT = "worker:alive"

def handle(tid):
    t = store.get(tid)
    if not t: return
    if rds.exists(f"task:{tid}:canceled"):
        store.update(tid, status="canceled"); return

    store.update(tid, status="running", stage="start", progress=1)
    p = json.loads(t["payload"])
    try:
        if p["kind"] == "cover":
            out = run_cover(p, on_stage=lambda **kw: store.update(tid, **kw))
        else:
            out = run_sing(p, on_stage=lambda **kw: store.update(tid, **kw))
        store.finish(tid, out)
    except Exception as e:            # 不让一个坏任务带走 worker
        store.fail(tid, getattr(e, "code", "ENGINE_ERROR"), str(e)[:300])

def main():
    while True:
        rds.set(HEARTBEAT, int(time.time()), ex=30)
        item = rds.brpop(QUEUE_KEY, timeout=3)     # 阻塞 3s，顺便当心跳节拍
        if not item: continue
        handle(item[1])
```

## 3. Node.js 端实现

### 3.1 提交后立刻回群

```js
// src/remote-singer.js
const PY = process.env.SONG_API || 'http://127.0.0.1:8000';

export async function submitSong(payload, { timeoutMs = 3000 } = {}) {
  const ac = new AbortController();
  const timer = setTimeout(() => ac.abort(), timeoutMs);   // ★ 3 秒，不是 600 秒
  try {
    const r = await fetch(`${PY}/songs`, {
      method: 'POST',
      headers: { 'content-type': 'application/json', 'x-token': process.env.SONG_TOKEN || '' },
      body: JSON.stringify(payload),
      signal: ac.signal,
    });
    if (!r.ok) throw new Error(`render service ${r.status}`);
    return await r.json();       // {task_id, position, eta_sec}
  } finally {
    clearTimeout(timer);
  }
}
```

工具里（`tools.js`）：

```js
const sub = await submitSong({ kind: 'cover', src, name, start, dur });
return ok({
  queued: true,
  jobId: sub.task_id,
  etaSec: sub.eta_sec,
  note: `排上了，前面还有 ${sub.position} 首，预计 ${Math.round(sub.eta_sec / 60)} 分钟。`
      + '成品好了会自动发到本会话，你不用等。',

```

**关键：这里绝不能 `await` 到渲染结束**，也绝不能把 600s 花在 fetch 超时上。
3 秒拿不到 task_id 就说明服务不健康，直接告诉用户「渲染服务暂时不可用」。

### 3.2 完成后推回 QQ

WebSocket 优先，断线自动退化为轮询：

```js
import WebSocket from 'ws';

export function watchTask(taskId, { onEvent, onDone, onFail }) {
  let closed = false;
  let pollTimer = null;

  const startPolling = () => {
    if (closed) return;
    pollTimer = setInterval(async () => {
      try {
        const r = await fetch(`${PY}/tasks/${taskId}`);
        const t = await r.json();
        onEvent?.(t);
        if (t.status === 'success') { stop(); onDone?.(t.result); }
        if (t.status === 'failed') { stop(); onFail?.(t.error); }
      } catch { /* 服务重启中，下轮再试 */ }
    }, 1500);
  };

  const ws = new WebSocket(`${PY.replace('http', 'ws')}/ws/tasks/${taskId}`);
  ws.on('message', (buf) => {
    const e = JSON.parse(String(buf));
    if (e.event === 'ping') return;
    onEvent?.(e);
    if (e.status === 'success') { stop(); onDone?.(e.result); }
    if (e.status === 'failed') { stop(); onFail?.(e.error); }
  });
  ws.on('error', () => { /* 由 close 统一兜底 */ });
  ws.on('close', () => { if (!closed && !pollTimer) startPolling(); });   // ★ 断线降级

  function stop() {
    closed = true;
    if (pollTimer) clearInterval(pollTimer);
    pollTimer = null;
    try { ws.close(); } catch { /* ignore */ }
  }
  return stop;
}
```

发送回群（复用现有投递逻辑）：

## 4. 防踩坑

### 4.1 单用户 / 单群并发

三档防线，缺一不可：

| 层 | 规则 | 实现 |
|---|---|---|
| 会话级 | 同一群同时最多 2 首 | `queue.list({group}).filter(queued\|running).length` |
| 用户级 | 同一 QQ 号 10 分钟内最多 3 次 | Redis `INCR user:{uin}:hour` + `EXPIRE` |
| 全局 | 队列长度 > 20 时拒绝新任务 | `LLEN queue`，回「太挤了，过会儿再来」 |

本仓库已实现第一档（`MAX_ACTIVE_PER_CHAT = 2`，`guardFlood()`）。
用户级需要 `ctx.userId`（当前 ctx 只有 chatKey），或在 OneBot 事件里带 sender id 透传。

### 4.2 Worker 崩溃

三种崩法，三种处理：

| 场景 | 现象 | 处理 |
|---|---|---|
| 进程被 OOM / 手动 kill | 任务永远 `running` | 心跳：worker 每 10s `SET worker:alive EX 30`；API 的 `/health` 或独立 watchdog 发现过期 → 把 `running` 且 `started_at` 超过 5 分钟的置 `failed(WORKER_LOST)` |
| Celery visibility timeout 重投 | 同一任务被跑第二遍 | 执行前写 `attempt=1`，重投时发现 attempt>0 → 直接判失败（GPU 任务重跑成本太高，不如报错） |
| 子进程（Demucs/RVC）挂了但 Python 没挂 | 任务卡住不前进 | `subprocess.run(timeout=...)` + 阶段级超时；`progress` 30 分钟不动 → 判死 |

本仓库的实现：`JobQueue` 心跳 240s + `maxAttempts=2` + jsonl 恢复，
外加 `stage_cache` 让重试能从上一次成功的阶段继续，而不是从头再来。

### 4.3 其他必踩的坑

- **别在 `fetch` 上等 600s**：HTTP 层只等 3s。渲染时长是队列的事，不是网络的事。
- **别把大文件塞进 Redis**：任务里只放参数和产物路径；音频走文件系统或对象存储。
- **别让 worker 并发 > 1（在 4GB 卡上）**：Demucs 峰值 ~2.6GB，RVC ~1.8GB，两个一起必 OOM。
- **别用 `os.replace` 原子换目录而不重试**：Windows 上杀软持有句柄会报 `WinError 5`（本仓库已改成重试 5 次 + 退化为逐文件拷贝）。
- **别在 worker fork 后初始化 CUDA**：见 §2.5。
- **进度要「假」一点**：Demucs 一分多钟不吐日志，纯真实进度会让用户以为死了。
  用指数曲线兜底（`pct = base + span * (1 - exp(-t/est))`），阶段日志到达时校正。

## 6. 迁移路径（什么时候从 A 换到 B）

| 触发条件 | 动作 |
|---|---|
| 一台机器够用、并发 1 | **留在 A**。加 `/api/jobs` 观测 + 用户级限流即可 |
| 需要 2 台以上 GPU 机器 | 上 B。Worker 无状态化，任务按 GPU 空闲度分发 |
| 需要 Worker 独立重启（不重启 QQ） | 上 B。A 的队列跟着 Node 进程一起死 |
| 外部系统要调这个能力 | 上 B。先加 FastAPI 薄壳，内部仍调本机脚本 |
| 单机但任务量 > 50 首/天 | 先加 A 的缓存与配额；不够再上 B |

**本仓库当前状态**：A 已完整落地（队列 / 缓存 / SSE / 作业查询与取消 / 防刷屏），
B 的代码在本文件 §2–§3，可直接照抄成独立服务。
