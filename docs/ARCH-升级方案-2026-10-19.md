## 0. 结论摘要（先看这页）

三个痛点里有两个的真因和表面描述不一样，先纠正：

| 痛点 | 表面症状 | 真因 | 对策（本方案的核心判断） |
|---|---|---|---|
| 无旋律 | 曲库只有 2 首，其余瞎编调 | **缺的是曲库（音频/谱），不是算法** | 有原曲音频 → 走 RVC（已有，天生音准节奏完美）；只有歌词 → 才用 SVS。**把 DiffSinger 从主路径降级为兜底** |
| 超时体验 | 渲染 20–180s，同步等 | **不是慢，是同步阻塞 + 零反馈** | 进程内串行队列 + 3 秒回执 + 里程碑播报 + **90 秒发 Hook 试听**。不需要 Celery/Redis |
| 音质窄暗 | RVC 人声发闷 | 40k 模型上限 + **多次重采样累积损伤** | 48k 模型 + soxr 单次重采样 + 原唱高频嫁接 + 动态 EQ |

另外两个必须现在就做的判断：

1. **不要把 `melodies/*.json` 的「绝对秒」继续扩展下去。** 它正是 BPM 95.7 对不齐的根因：时长按秒存，BPM 一偏，误差随播放时间线性累积，唱到第 30 秒能漂掉一整拍。必须升级成「节拍网格坐标 + bpm」的 v2 格式（见 §4.2），这不影响现有两首歌的兼容。
2. **单机单卡（4GB）上谈「分布式队列」是过度设计。** 队列的本质只有三件事：互斥（GPU 一次只能跑一个）、优先级、持久化。这三件事一个进程内的 `await` 循环 + 一个 JSONL 日志文件就能做到，加 Redis 只是增加运维面。真正需要 Redis 的时机在 §3.2 末尾。

## 1. 目标架构蓝图

```
┌──────────────────────── 接入层（Node, 单进程） ────────────────────────┐
│  OneBot WS  ──►  intent 识别  ──►  tool call (sing_lyrics / cover_song) │
│                                        │                                │
│                                  ① 3s 内回执「已排队 #7」              │
│                                        ▼                                │
│  ┌──────────────────────── JobQueue（进程内） ──────────────────────┐  │
│  │  priority: 点歌 > 闲聊     dedupe: cacheKey 合并同一首歌          │  │
│  │  fairness: 按群轮转        persist: data/jobs.jsonl (append-only) │  │
│  │  concurrency: GPU=1  CPU=2                                        │  │
│  └──────────────────────────────┬───────────────────────────────────┘  │
│                                 │ ② spawn 子进程，stdin 传 job         │
└─────────────────────────────────┼──────────────────────────────────────┘
                                  ▼
┌──────────────────── 执行层（Python worker，按阶段可缓存） ─────────────┐
│                                                                         │
│  resolve ──► separate ──► [transcribe] ──► melody ──► synth ──► convert │
│   曲库/上传   Demucs GPU    歌词时间戳     扒谱/F0     DiffSinger  RVC   │
│                                                                         │
│  ──► mix ──► master ──► deliver                                         │
│      侧链避让  -14LUFS   上传 → 回传 Node                               │
│                                                                         │
│  每个阶段: stdout JSONL 上报 {ev:"progress", stage, pct, etaMs}         │
│  每个阶段: 产物落盘并记 hash，命中则整段跳过                            │
└─────────────────────────────────┬───────────────────────────────────────┘
                                  ▼
┌──────────────── 资产层（磁盘，按 hash 寻址） ──────────────────────────┐
│  work/<songHash>/vocals.wav  inst.wav  f0.json  melody.json             │
│  work/<renderHash>/vocal_rvc.wav  mix.wav                               │
│  缓存键 = hash(音频) + 模型版本 + 参数；模型换版本自动失效              │
└─────────────────────────────────────────────────────────────────────────┘
```

**关键设计原则**

- **阶段化（stage）+ 内容寻址**：一首歌被拆成 9 个可独立复用的阶段。热门歌第二次点，`separate` / `melody` 全部命中缓存，只剩 `convert` + `master`，30 秒内出结果。这是最大的性能杠杆，比换模型有效得多。
- **GPU 独占**：Demucs、RVC、DiffSinger(ONNX) 在 4GB 显存上不能同时驻留。所有 GPU 阶段进同一个串行队列，配上显存看门狗（`torch.cuda.mem_get_info()` < 400MB 时先卸载再跑）。
- **进度即产品**：每个阶段都必须能吐出 `pct` 和 `etaMs`。没有进度的长任务，用户感受到的等待时间会被主观放大 2–3 倍。

## 2. 任务 1：解决「随便点一首歌」的旋律获取

### 2.1 先厘清：这是三个不同的问题

很多方案对比会在这里跑偏，因为它们解决的不是同一件事。

| 场景 | 用户说的话 | 真正需要的能力 | 推荐引擎 |
|---|---|---|---|
| **S1** 有原曲音频，歌词不变 | 「来一首反方向的钟」 | 音色迁移（SVC），不需要旋律 | **RVC**（已有，`route_a.py`） |
| **S2** 有原曲音频，要改歌词/改调 | 「用这首歌的调唱这段词」 | 扒谱（旋律 + 字音对齐）→ SVS | crepe + beat + 对齐 → **DiffSinger** |
| **S3** 只有歌词/歌名，无音频 | 「唱：今天天气不错」 | 生成/检索旋律 → SVS | **LLM 生成旋律** / 算法旋律 |

**当前系统把所有请求都塞进了 S3**，这是体验差的根源。S1 是最高频、效果最好、成本最低的场景，而它已经实现了 —— 只是没有被优先路由。

> 结论：`sing_lyrics` 与 `cover_song` 之间需要一个**路由器**，而不是两条独立的工具让模型自己瞎选。

### 2.2 方案 A：自动扒谱（Audio → Melody）

**这是 S2 的正解，也是「自动获取旋律」唯一真正可落地的方式。** 但要清楚它的真实难度曲线：**F0 提取只占 20% 工作量，剩下 80% 是「字↔音符」对齐。**

#### 推荐链路

```
原曲.wav
  ├─(1) Demucs ─────────► vocals.wav            [已有，GPU 3.1×]
  ├─(2) beat_this ──────► bpm / beats / downbeats
  ├─(3) torchcrepe ─────► f0 10ms 逐帧          [GPU，已装]
  ├─(4) 音符切分 ───────► [{midi, start_beat, dur_beat}]
  ├─(5) 歌词时间戳 ─────► [{char, t0, t1}]
  └─(6) 字-音对齐 ──────► melody v2 JSON ──────► DiffSinger
```

#### 各环节选型与理由

| 环节 | 候选 | 选它 / 不选它的理由 |
|---|---|---|
| F0 提取 | **torchcrepe** | `rvc/py310` 已装（v0.0.24）。`full` 模型 GPU 上比 `librosa.pyin` 快 15–25×，且对气声/假声的八度跳变更稳。**首选** |
| | librosa.pyin | `diffsinger-env` 已有，`pitch_track.py` 在用。CPU 上 3 分钟歌要 40s+，只做 fallback |
| | RMVPE | RVC 内置，为「唱歌」调过，音准最贴唱腔；但只出量化后的 cents 曲线，接口不通用。可用于**交叉校验** |
| 音符切分 | **自研（推荐）** | onset（librosa）+ F0 稳定段合并 + 最短音长约束（≥80ms）+ 滑音吸附。可控，能按本项目需求调 |
| | basic-pitch | 直接出 MIDI note events（含 pitch bend），省事。但只吃 16k 单声道，对混响/和声敏感，中文流行歌的转音会被切碎。适合做**交叉验证**，不适合当唯一来源 |
| 节拍 | **beat_this** | 2025 SOTA，`pip install beat-this`，对流行乐明显强于 librosa。**首选** |
| | librosa.beat | 零依赖，fallback；半/倍频错误率高 |
| 歌词时间戳 | **ctc-forced-aligner** 或 **MFA 3.x** | 见下方「关键坑」—— **唱段不能用 ASR** |
| | WhisperX / Paraformer | 只适合**说话**场景。唱段上会漏字、串词、时间戳整体偏移 |

#### 关键坑（很多人在这里翻车）

**不能用 ASR 去给唱段打时间戳。** Whisper 类模型在长音、拖腔、颤音上会静音幻觉（把 4 秒的「啊——」识别成 0 个字，或者凭空补词），时间戳误差可达数百毫秒，直接毁掉字-音对齐。

正确做法是**反向的强制对齐**：歌词文本已知（用户提供 / 曲库带 / 歌词 API 取），让对齐器把**已知文本**贴到音频上。

- `ctc-forced-aligner`：pip 直装、纯 torch、支持中文、自带 singing 友好参数，**推荐**
- `MFA 3.x`：`pip install montreal-forced-aligner`（不再需要 conda），精度更高，但要下 1GB+ 声学模型，且中文需自行准备词典。**值得接，但放 Phase 2**

#### 实现骨架（`diffsinger-hutao/melody_extract.py`）

```python
def extract_melody(vocals_path, lyrics, bpm=None, out=None):
    """vocals.wav + 已知歌词 → melody v2 JSON（供 sing_engine 直接消费）"""
    y, sr = sf.read(vocals_path, dtype="float32")

    # 1) 节拍网格：优先用原曲混音测，退化时用 vocals
    grid = beat_grid(y, sr) if bpm is None else grid_from_bpm(bpm, len(y) / sr)
    #    beat_this → (bpm, beats[], downbeats[])，并做半/倍频仲裁

    # 2) 逐帧 F0（GPU）
    f0, conf = crepe_f0(y, sr, hop_ms=10, model="full")   # torchcrepe.predict
    f0 = fix_octave_jumps(f0, conf)                        # ±12 半音中值校正

    # 3) 音符切分：能量 onset + F0 稳定段 + 最短音长
    notes = segment_notes(f0, conf, sr, min_dur=0.08, hop_ms=10)

    # 4) 吸附到节拍网格（容忍 ±1/4 拍，避免把人声自由速度硬掰直）
    notes = snap_to_grid(notes, grid, tol=0.25)

    # 5) 字 → 音符：先按乐句边界分段，段内按「字时长加权」比例分配
    char_times = align_lyrics(vocals_path, lyrics)          # ctc-forced-aligner
    notes = assign_syllables(notes, char_times, lyrics)

    return {
        "name": Path(vocals_path).stem, "version": 2,
        "bpm": grid.bpm, "offset_sec": grid.offset, "beats_per_bar": grid.meter,
        "notes": [{"midi": n.midi, "start_beat": n.sb, "dur_beat": n.db,
                   "syllable": n.syl, "slur": n.slur} for n in notes],
        "source": {"engine": "crepe+beat_this", "built_at": now_iso()},
    }
```

#### 现实预期（必须提前对齐）

自动扒谱能做到「**听得出来是这首歌，音准节奏大致对**」，做不到「和原唱一模一样」。原因不是算法不行，而是：

- 人声有大量非离散音高（滑音、气声、说唱式快速换字），强行量化必然丢信息；
- 换气、句尾拖腔的时值选择没有唯一正确答案；
- 一字多音（拖腔）cut 成几个音，取决于主观判断。

**所以自动扒谱的定位应该是「80 分自动化 + 人工一键微调」**，而不是「全自动 100 分」。建议配一个 `melodies/<歌名>.json` 的可视化编辑器（哪怕只是个简陋的钢琴卷帘网页），让管理员改 3–5 个音就能救回来。

### 2.3 方案 B：在线 MIDI 库 / LLM 生成旋律

**在线 MIDI 库：现阶段不建议作为主路径。**

- 没有稳定、合法、免 key 的中文流行歌 MIDI API。BitMidi / MuseScore 抓取质量参差，版权风险明确。
- 唯一靠谱的形态是**「用户上传 MIDI」入口**：`POST /api/melodies` 接收 `.mid`，用 `mido`/`pretty_midi` 解析 → 直接转 melody v2。这个成本极低（半天），价值高，**建议做**。

**LLM 生成旋律：不做「唱原曲」，但能救「瞎编调」。**

现在的 `melody_engine.build_melody()` 是「音阶级数随机游走 + 固定节奏模板」，听起来就是「机器在念谱」。换成 LLM 生成会明显更像歌：

```
Prompt: 为下面 16 字歌词写一段旋律，要求：
  - 调式：C 大调，音域 C4–A4（女声舒适区）
  - BPM 92，4/4，共 2 乐句，第 2 句是第 1 句的模进
  - 每字 1–2 个音，句尾长音，避免连续 3 个同音
  - 输出 ABC 记谱法
```

再用 `music21` 解析 ABC → 校验音域 → 落到 melody v2。成本约 1 次 LLM 调用（<2s），比现在的算法旋律好听一个档次。

> 但要说清楚：**这依然是「现编的调」，不是原曲。** 机器人必须如实说明。假装在唱原曲是最伤信任的行为。

### 2.4 方案 C：抛弃 DiffSinger，上 Zero-shot SVS

逐个点评（2026-10 现状），这里容易踩营销话术的坑：

| 模型 | 它是 SVS 还是 TTS/SVC | 能不能替代 DiffSinger |
|---|---|---|
| **GPT-SoVITS v4** | TTS（强情感、零样本音色） | ❌ **不能**。没有显式 F0/时值控制，唱长句必跑调。它的强项是「说话像人」 |
| **Fish Speech / CosyVoice** | TTS | ❌ 同上 |
| **Seed-VC** | **SVC**（需要参考人声） | ❌ 它不是「文本→歌声」，它和 RVC 是同类，属于 S1 路线 |
| **Suno / 商用音乐 API** | 端到端歌曲生成 | ❌ 音色不可控、成本按首计、合规风险，且无法「用胡桃的声音」 |
| **DiffSinger** | **SVS**（音素/时值/音高全显式） | ✅ **仍是可控 SVS 的最优解** |
| so-vits-svc 4.1 | SVC（48k） | 可作为 RVC 的替代，音质上限更高，但推理更慢 |

**结论：SVS 这一层不要换。** 换掉它你会失去「改歌词、改调、改节奏」的唯一可控入口，而这是点歌机器人区别于「变声器」的核心。

真正该做的是**降低对 SVS 的依赖**（见 2.5 的路由）。如果非要在 SVS 上提升，方向是换更好的**声库**（DiffSinger 社区有大量中文声库）和更多 `acoustic_steps`，而不是换框架。

### 2.5 推荐路由（把三方案串成决策树）

```js
// src/song-router.js
async function route(req) {
  // ① 有原曲音频（用户上传 / 曲库命中）且歌词不变 → RVC，最快最准
  if (req.audioPath && !req.rewriteLyrics) {
    return { path: 'cover_rvc', eta: 45_000, quality: 'A' };
  }
  // ② 有原曲音频 + 要重唱 → 自动扒谱 → SVS
  if (req.audioPath && req.rewriteLyrics) {
    const mel = await ensureMelody(req.audioPath, req.lyrics);  // 带缓存
    return { path: 'svs', melody: mel, eta: 90_000, quality: 'B+' };
  }
  // ③ 有 MIDI / 旋律库命中 → SVS
  if (req.midiPath || melodyLib.has(req.songName)) {
    return { path: 'svs', melody: req.midiPath || melodyLib.get(req.songName), eta: 40_000 };
  }
  // ④ 什么都没有 → LLM 旋律 / 算法旋律，且必须告知
  return { path: 'svs_generated', eta: 30_000, quality: 'C',
           disclaimer: '这首没有原曲旋律，是我现编的调' };
}
```

**这条路由是整套方案里性价比最高的改动**：不加任何模型，只改「先问有没有音频」，就能把 S1 的体验从 60 分拉到 90 分。

## 3. 任务 2：异步任务队列

### 3.1 为什么不用 Celery

- **语言边界成本**：Celery 是 Python 生态，Node 侧要么走 HTTP 轮询、要么装 `celery-js`（不可靠）。你会在「两个运行时之间同步状态」上花掉比队列本身更多的时间。
- **你需要的能力它都过剩**：单机、单 GPU、单进程 bot。Celery 的 broker/result backend/worker 池/flower 监控，在这里全是负债。
- **排查成本**：出问题时你要同时看 Node 日志、Redis、Celery worker 日志、Python 音频日志。而现在只有一份 `qqagent-main.log`。

**队列的刚需只有三条：互斥、优先级、持久化。** 下面用 200 行 Node 就能全占。

### 3.2 推荐形态

**Phase 0（现在）：进程内队列 + JSONL 持久化。**

- `concurrency.gpu = 1`，`concurrency.cpu = 2`
- 任务状态 append 到 `data/jobs.jsonl`，启动时重放恢复（未完成的标记 `interrupted` 并可重试）
- Python 作为**执行器**被 spawn，通过 **stdout JSONL** 上报进度 —— 天然流式、无需额外依赖

**什么时候才需要 Redis：**

1. 要跑**多台机器**（GPU 机 + 主控机分离）；
2. 要**多进程消费**同一个队列；
3. 任务必须**跨重启强一致**（付费点歌、计费场景）。

只要还是「一台机器、一个 bot 进程」，Redis 就是净负债。真到了那一天，把 `JobQueue` 的 `push/pop/complete` 三个方法换成 BullMQ 即可 —— 所以下面的接口要按「可替换」来设计。

### 3.3 数据结构

```ts
type JobKind = 'cover' | 'sing' | 'acapella';
type JobStage =
  | 'resolve' | 'separate' | 'transcribe' | 'melody'
  | 'synth' | 'convert' | 'mix' | 'master' | 'deliver';
type JobStatus = 'queued' | 'running' | 'succeeded' | 'failed' | 'canceled';

interface SongJob {
  id: string;                 // job_20261019_183012_ab12cd
  chatKey: string;            // 'group:123456789'
  requesterId: string;        // QQ 号
  kind: JobKind;

  input: {
    query?: string;           // 「反方向的钟」
    audioPath?: string;       // 已落盘的原曲
    lyrics?: string;
    melody?: string;          // 旋律库 key 或 json 路径
    voice: string;            // hutao | nahida
    keyShift?: number;
    bpm?: number;
    params?: Record<string, number>;   // indexRate / protect / enhance ...
  };

  // 内容寻址：同一份输入 + 同一模型版本 = 同一份产物
  cacheKey: string;           // sha1(audioSha1 | voice | modelVer | params)
  songHash?: string;

  status: JobStatus;
  stage: JobStage | null;
  progress: number;           // 0..100
  etaMs: number;              // 剩余预估
  attempts: number;
  maxAttempts: number;        // 默认 2
  priority: number;           // 点歌 10 / 闲聊 5 / 预生成 1

  // 阶段产物（可复用于重试与缓存）
  artifacts: { stage: JobStage; path: string; bytes: number; sec: number }[];
  timings: Partial<Record<JobStage, number>>;    // 各阶段耗时 ms
  error?: { code: string; message: string; stage: JobStage; retryable: boolean };

  // 交付
  notify: { ackSentAt?: number; milestones: JobStage[]; deliveredAt?: number };

  createdAt: number;
  startedAt?: number;
  finishedAt?: number;
  heartbeatAt?: number;       // 僵尸检测：> 90s 无更新且 running → 判死
}
```

**状态机**

```
queued ──claim──► running ──ok──► succeeded ──deliver──► (删除 30min 后)
                    │  ▲
              fail  │  │ retry (attempts < max)
                    ▼  │
                  queued
                    └── fail 终态 ──► failed
任意态 ──cancel──► canceled
```

**Node 侧：队列 + worker + 去重 + 公平**

```js
// src/job-queue.js
import { spawn } from 'node:child_process';
import { randomUUID, createHash } from 'node:crypto';
import fs from 'node:fs';

export class JobQueue {
  constructor({ concurrency = { gpu: 1, cpu: 2 }, journal = 'data/jobs.jsonl', emit, log }) {
    this.jobs = new Map();           // id -> job
    this.pending = [];               // 按 priority desc, createdAt asc 排序
    this.running = new Map();        // id -> { child, stage }
    this.byCacheKey = new Map();     // cacheKey -> jobId（在途去重）
    this.concurrency = concurrency;
    this.emit = emit; this.log = log;
    this.journal = journal;
    this.#recover();
  }

  // ── 对外：入队 ───────────────────────────────────────────
  async add({ chatKey, requesterId, kind, input, audioSha1, modelVer, priority = 10 }) {
    const cacheKey = createHash('sha1')
      .update([audioSha1 || input.query || '', input.voice, modelVer,
               JSON.stringify(input.params || {}), input.lyrics || '', input.melody || ''].join('|'))
      .digest('hex').slice(0, 16);

    // ① 正在跑同一首 → 合并请求者，不重复烧 GPU
    const inflight = this.byCacheKey.get(cacheKey);
    if (inflight && this.jobs.has(inflight)) {
      const j = this.jobs.get(inflight);
      j.recipients.push({ chatKey, requesterId });      // 成品 fan-out 给所有人
      this.log(`[queue] 合并到在途任务 ${inflight}`);
      return { jobId: inflight, deduped: true, position: 0, etaMs: j.etaMs };
    }

    // ② 已有成品缓存 → 直接投递，秒回
    const hit = this.#cacheLookup(cacheKey);
    if (hit) {
      queueMicrotask(() => this.#deliverCached(hit, { chatKey, requesterId }));
      return { jobId: 'cache_' + cacheKey, deduped: true, cached: true, position: 0, etaMs: 800 };
    }

    const job = {
      id: `job_${ts()}_${randomUUID().slice(0, 6)}`,
      chatKey, requesterId, kind, input,
      cacheKey, status: 'queued', stage: null,
      progress: 0, etaMs: estimateEta(kind, input), attempts: 0, maxAttempts: 2,
      priority, artifacts: [], timings: {}, recipients: [{ chatKey, requesterId }],
      notify: { milestones: [] }, createdAt: Date.now(),
    };
    this.jobs.set(job.id, job);
    this.byCacheKey.set(cacheKey, job.id);
    this.pending.push(job);
    this.#sort();
    this.#append({ type: 'queued', job });
    this.emit('job.queued', { jobId: job.id, position: this.#position(job), etaMs: job.etaMs });
    this.#pump();
    return { jobId: job.id, deduped: false, position: this.#position(job), etaMs: job.etaMs };
  }

  // ── 调度：按群轮转，防止一个群刷屏饿死别人 ────────────────
  #pump() {
    while (this.running.size < this.concurrency.gpu && this.pending.length) {
      const job = this.#pickFair();
      this.#run(job);              // GPU 阶段是串行的，所以只用一个池
    }
  }

  #pickFair() {
    // 以 chatKey 分组做 round-robin：每组内按 priority/createdAt
    const groups = new Map();
    for (const j of this.pending) {
      if (!groups.has(j.chatKey)) groups.set(j.chatKey, []);
      groups.get(j.chatKey).push(j);
    }
    const keys = [...groups.keys()].sort();
    const k = keys[this.rrCursor % keys.length] || keys[0];
    this.rrCursor = (this.rrCursor || 0) + 1;
    const group = groups.get(k).sort((a, b) => b.priority - a.priority || a.createdAt - b.createdAt);
    const job = group[0];
    this.pending = this.pending.filter((x) => x.id !== job.id);
    return job;
  }

  // ── 执行：spawn 一个 Python 执行器，逐行读进度 ─────────────
  #run(job) {
    job.status = 'running';
    job.startedAt = Date.now();
    job.heartbeatAt = Date.now();

    const child = spawn(PY, [RUNNER, '--job', JSON.stringify(job)], {
      cwd: DS_DIR,
      env: { ...process.env, PYTHONUNBUFFERED: '1', OMP_NUM_THREADS: '1' },
      windowsHide: true,          // ★ 不要 detached（Windows 下管道会收不到输出）
    });
    this.running.set(job.id, { child, stage: null });

    child.stdin.end();
    lineReader(child.stdout, (line) => this.#onEvent(job, line));
    let errBuf = '';
    child.stderr.on('data', (d) => { errBuf = (errBuf + d).slice(-4000); });

    child.on('exit', (code) => {
      this.running.delete(job.id);
      if (job.status === 'succeeded' || job.status === 'canceled') return;
      // 进程死了但没收到 done/error → 判失败（不要让它永远卡在 running）
      this.#fail(job, 'WORKER_EXIT', `执行器退出 code=${code}\n${errBuf}`, true);
    });
  }

  #onEvent(job, line) {
    let ev; try { ev = JSON.parse(line); } catch { return; }
    job.heartbeatAt = Date.now();

    if (ev.ev === 'progress') {
      job.stage = ev.stage; job.progress = ev.pct ?? job.progress;
      if (ev.etaMs != null) job.etaMs = ev.etaMs;
      this.emit('job.progress', { jobId: job.id, stage: ev.stage,
                                  progress: job.progress, etaMs: job.etaMs, msg: ev.msg });
      this.#maybeMilestone(job, ev);          // 「分离完成」「开始唱了」
    } else if (ev.ev === 'artifact') {
      job.artifacts.push({ stage: ev.stage, path: ev.path, bytes: ev.bytes });
    } else if (ev.ev === 'done') {
      job.status = 'succeeded'; job.progress = 100; job.finishedAt = Date.now();
      job.timings = ev.result.timings || {};
      this.byCacheKey.delete(job.cacheKey);
      this.#append({ type: 'done', job, result: ev.result });
      this.#fanout(job, ev.result);           // 推给所有合并进来的请求者
    } else if (ev.ev === 'error') {
      this.#fail(job, ev.code, ev.message, ev.retryable);
    }
  }

  #fail(job, code, message, retryable) {
    job.error = { code, message: String(message).slice(0, 500),
                  stage: job.stage, retryable: !!retryable };
    this.byCacheKey.delete(job.cacheKey);
    if (retryable && job.attempts < job.maxAttempts - 1) {
      job.attempts++; job.status = 'queued'; job.stage = null; job.progress = 0;
      this.pending.push(job); this.#sort(); this.#append({ type: 'retry', job });
      this.log(`[queue] ${job.id} 第 ${job.attempts} 次重试（${code}）`);
      this.#pump();
      return;
    }
    job.status = 'failed'; job.finishedAt = Date.now();
    this.#append({ type: 'failed', job });
    this.emit('job.failed', { jobId: job.id, stage: job.stage, message: job.error.message,
                              retryable: job.error.retryable });
  }
}
```

### 3.6 体验设计（比技术更重要）

技术只解决「不阻塞」，体验解决「不烦人」。

| 时点 | 动作 | 文案示例 |
|---|---|---|
| T+0s | 立即回执 | 「收到，《反方向的钟》已排队（前面 1 首），大概 2 分钟，好了我直接发群里」 |
| T+3s | 若队列为空 | 「开始了，先分离伴奏」 |
| T+45s | 里程碑（最多 2 条） | 「伴奏切好了，开始用胡桃的声音唱」 |
| **T+90s** | **Hook 试听（杀手锏）** | 先发副歌 15 秒语音条：「先听一耳朵，全曲马上好」 |
| T+180s | 成品 | 发文件 + 一句吐槽 |
| 失败 | 明确可行动 | 「这首的旋律没扒准，我换个调再试一次？回复『重试』」 |

**Hook 试听** 是这套方案里体验收益最高的一招：把「等 3 分钟」变成「45 秒就听到声音」，主观等待感下降一个数量级。实现上成本很低 —— `synth` 阶段先把前 15–20 秒的 `.ds`（截一个完整乐句）单独渲染一版发出去，剩下的继续跑。

**其他必须有的护栏**

- **每群每日配额**（默认 20 首）：防刷屏、防单人烧卡。
- **同群去重**：60 秒内同一个人点同一首歌 → 直接回「刚点过了，马上到」。
- **深夜限速**：00:00–08:00 concurrency 降到 1，且不回执里程碑，避免吵人。
- **文件体积**：QQ 群文件上限约 100MB，3 分钟 44.1k 立体声 wav ≈ 32MB，安全；但**语音条有 60 秒限制**，超过必须转文件发送（已有逻辑，需确认阈值）。

## 4. 任务 3：BPM 与节奏严格对齐

### 4.1 复现「95.7 对不齐」的根因

现有 `songs/melodies/*.json` 里存的是 `[midi, dur_sec]` —— **绝对秒**。

渲染时 DiffSinger 按这些秒数逐个排音符。如果旋律提取时 BPM 被判成 95.7，而伴奏实际是 96.0，那么每拍误差 `0.6/96² ≈ 0.065ms`，看着很小，但**累积**：

```
30 秒（48 拍）后累计偏移 ≈ 48 × 0.065ms × 96 ≈ 300ms ≈ 半拍
```

更糟的是：如果旋律来自「第 65 秒开始的 30 秒片段」，然后循环铺满整首，每一轮的误差还会叠加。**这就是为什么短片段听着还行、整首越唱越飘。**

**修复方向不是「把 BPM 调准一点」，而是换成不依赖绝对时间的表示。**

### 4.2 melody schema v2（向后兼容）

```jsonc
{
  "name": "反方向的钟",
  "version": 2,
  "bpm": 95.7,
  "offset_sec": 0.412,        // 第一拍相对音频起点的偏移
  "beats_per_bar": 4,
  "key_root": 57,             // A3，可选
  "notes": [
    { "midi": 57, "start_beat": 0.0,  "dur_beat": 0.5,  "syllable": "反" },
    { "midi": 58, "start_beat": 0.5,  "dur_beat": 1.0,  "syllable": "方" },
    { "midi": 55, "start_beat": 1.5,  "dur_beat": 0.75, "syllable": "向", "slur": true }
  ],
  "source": { "engine": "crepe+beat_this", "built_at": "2026-10-19T18:30:00+08:00" }
}
```

渲染时：`dur_sec = dur_beat × 60 / bpm`。

**收益**：

1. 改 BPM（用户说「唱慢一点」）只需换 `bpm`，音符一个不动；
2. 移调只改 `midi`，时值完全不变（现在移调是安全的，但 BPM 不是）；
3. 可以精确表达「切分音」「附点」「三连音」，而不是一串奇怪的秒数；
4. 与伴奏的对齐关系变成「第几拍」，可以直接用 beat grid 校验。

**兼容**：`sing_engine.load_melody()` 里判断 `version`，v1 走现在的路径（把 `dur_sec` 累加成时间轴），v2 走 beat 换算。改动约 30 行，两首老歌不用重扒。

### 4.3 节拍检测选型

| 工具 | 评价 |
|---|---|
| **beat_this**（推荐） | 2025 ISMIR，`pip install beat-this`，对流行乐的 downbeat 明显更准；输出 BPM + beats + downbeats |
| madmom | 精度接近，但依赖 Cython 扩展，Python 3.10+ 上编译经常失败，**不推荐新项目用** |
| librosa.beat | 零依赖，BPM 半/倍频错误率高。**只做 fallback** |

**关键坑：必须用「原始混音」测 BPM，不要用分离后的伴奏。**

Demucs 分离会削弱 kick 的瞬态和 60–100Hz 的低频（这正是节拍的主要线索），在分离后的伴奏上跑 beat tracking，BPM 错误率会翻倍 —— 而且往往是**半速/倍速**错（95.7 vs 191.4），这种错误最隐蔽：听起来「好像对」，但两小节后就错位。

**BPM 半/倍频仲裁**（必做）：

```python
def arbitrate_bpm(cands, downbeats, vocal_onsets):
    """在 {b, 2b, b/2} 里选一个：downbeat 间隔更接近 4 拍、且与换气/乐句边界吻合的胜出"""
    score = {}
    for b in cands:
        # ① downbeat 间隔应 ≈ 4 拍
        bar_err = abs(np.median(np.diff(downbeats)) - 4 * 60 / b)
        # ② 人声乐句起点应落在强拍附近（换气点通常在小节线后）
        align = sum(min(abs(t - db) for db in downbeats) < 0.15 for t in vocal_onsets) / len(vocal_onsets)
        score[b] = -bar_err / 0.05 + align * 2
    return max(score, key=score.get)
```

### 4.4 强制对齐（MFA）值不值得接

**结论：值，但它的作用不是「对齐节奏」，而是「字↔音频」。**

MFA（Montreal Forced Aligner）解决的是「**已知文本**在音频里的音素级起止时间」。它能给你：

- 每个字的精确起点（用于把歌词音节映射到旋律音符）；
- 每个音素的时长（用于 DiffSinger 的时长建模微调）。

它**不能**给你：旋律本身、BPM、以及「这个字应该唱哪个音」。

**选型建议**：

| 需求 | 用什么 | 理由 |
|---|---|---|
| 字级时间戳（给 SVS 分配音符） | **ctc-forced-aligner**（首选）/ MFA 3.x | pip 直装、纯 torch、有中文模型；MFA 精度略高但模型 1GB+ |
| 逐字卡拉OK字幕 | MFA（音素级） | 只有这个场景需要音素级 |
| 说话场景的转写 | WhisperX / Paraformer | 注意：**唱段不适用** |
| 节奏对齐 | **不需要 MFA** | 节奏靠 beat grid，不靠对齐器 |

**注意**：MFA 的声学模型是在**朗读语料**上训的。唱歌的长音、颤音、拖腔会让它把字边界切在奇怪的地方。缓解手段：

- 只对齐到**音节**而不是音素（粒度粗，鲁棒）；
- 用 `--beam 100 --retry_beam 400` 放宽搜索；
- 对失败的句子降级为「按字数比例均分」（有 beat grid 兜底，效果可接受）。

### 4.5 字 ↔ 音符对齐（真正的难点）

给定：音符序列 `N`（含 `start_beat` / `dur_beat`）和字序列 `C`（含 `t0` / `t1`）。需要单调映射，且允许：

- **一字多音**（拖腔）：`1 字 → k 音符`，后续音符标 `slur: true`
- **多字一音**（说唱）：`k 字 → 1 音符`，音符按字数均分

**实用做法（O(n)，够用）**：

```python
def assign_syllables(notes, char_times, chars):
    out = []
    j = 0
    for i, n in enumerate(notes):
        n_start, n_end = beat2sec(n.start_beat), beat2sec(n.start_beat + n.dur_beat)
        # 落在本音符区间内的字起音
        inside = [c for c in chars[j:] if n_start - 0.05 <= char_times[c].t0 < n_end]
        if not inside:
            # 没有字 → 是上一个字的拖腔
            out.append({**n, "syllable": out[-1]["syllable"] if out else "", "slur": True})
            continue
        if len(inside) == 1:
            out.append({**n, "syllable": inside[0]})
            j += 1
        else:
            # 多字一音：按字数均分时值
            step = n.dur_beat / len(inside)
            for k, c in enumerate(inside):
                out.append({**n, "syllable": c, "start_beat": n.start_beat + k * step, "dur_beat": step})
            j += len(inside)
    return out
```

**DP 什么时候才需要**：当对齐器给出的 `t0` 明显不可信（置信度低、跳过若干字）时。此时用 DP 求全局最优（`cost = |note_start - char_start| + λ·音高跳变 + μ·字数惩罚`），允许 `1:N` 与 `N:1`。但**不要默认上 DP** —— 在 beat grid 已经正确的前提下，顺序分配 95% 的情况都对，DP 只会引入难以调试的边界行为。

### 4.6 渲染后的长度校验（最后一道保险）

无论前面多准，渲染出来的时长必须和伴奏对得上。加一道硬校验：

```python
def fit_to_inst(render_wav, inst_sec, bpm, tolerance_beats=1.0):
    render_sec = probe_dur(render_wav)
    drift_beats = abs(render_sec - inst_sec) / (60 / bpm)

    if drift_beats <= tolerance_beats:
        return render_wav                       # 合格
    if drift_beats / (inst_sec / (60 / bpm)) < 0.03:
        # 差 < 3%：整体时间拉伸，保音高（WSOLA）
        return time_stretch(render_wav, inst_sec / render_sec)
    # 差 > 3%：旋律提取错了，别硬救
    raise StageError("TEMPO_DRIFT", f"偏差 {drift_beats:.1f} 拍，旋律不可用",
                     stage="melody", retryable=True)
```

**两条铁律**：

1. **绝不改伴奏速度去适配人声。** 伴奏一变速，原曲的律动、瞬态、混响尾巴全毁，而且用户一听就知道「这歌怪怪的」。错的永远是人声。
2. **拉伸用 WSOLA / phase vocoder，不要用重采样。** `librosa.effects.time_stretch` 是 phase vocoder（够用）；要求更高用 `pyrubberband`（Rubber Band，WSOLA 系，瞬态更自然）。重采样会同时改变音高 —— 一首歌整体升半个调是最刺耳的失败。

## 5. 音质专项（痛点 3：「窄且暗」）

先拆根因，否则容易乱试：

| 根因 | 占比 | 验证方法 |
|---|---|---|
| RVC 模型本身是 40k 训练，8k 以上基本无内容 | **~50%** | 看 `metrics.py` 的 `hf8` 指标 / 频谱图 10k 以上是否一片黑 |
| 重采样链路过长（44.1 → 40 → 44.1 → 48） | ~25% | 数一下链路里 resample 次数 |
| mel 重建损失（RVC 的 vocoder 上限） | ~15% | 对比 RVC 输入/输出的高频相关性 |
| 混音把人声压暗（EQ/压缩过度） | ~10% | 单独听 `vocal_rvc.wav` vs 成品 |

**对策（按投入产出排序）**

1. **换 48k RVC 模型**（收益最大）。现有模型如果只有 40k，高频天花板就在 16kHz，怎么 EQ 都补不回来。社区有大量 48k v2 模型。
2. **全链路只重采样一次**。统一到 48k 工作，Demucs 输出 44.1 → 一次性 soxr 到 48（`soxr_hq`），之后所有阶段都在 48k 跑，最后输出才决定落 48 还是 44.1。**不要每个阶段各 resample 一次** —— 每次都是一次低通 + 相位损伤。
3. **原唱高频嫁接**（对「暗」最直接）：
   ```python
   # 把原唱 6k+ 的空气感，按包络匹配后叠到 RVC 人声上（15–25% 比例）
   hi_src = bandpass(orig_vocal, 6000, 16000)
   hi_dst = bandpass(rvc_vocal, 6000, 16000)
   hi_src = hi_src * (rms(hi_dst) / (rms(hi_src) + 1e-9))   # 包络匹配
   out = rvc_vocal + 0.2 * hi_src
   ```
   风险：齿音/咬字细节会带上原唱的特征（本质是「借」）。控制比例 ≤25%，并在 `qc.py` 里加一项「与原唱高频相关性」防串味。
4. **动态 EQ 而不是静态提升**：300Hz 附近 -1.5dB（去浑浊）、3kHz +1dB（存在感）、10kHz 用动态 shelf（只在有能量时抬，避免嘶声）。
5. **人声/伴奏的侧链避让已有（`_sentence_duck`），别再加**。过度避让会让伴奏「抽气」，反而显得人声干。

## 6. 坑清单（按踩中概率排序）

| # | 坑 | 现象 | 规避 |
|---|---|---|---|
| 1 | **BPM 半/倍频错** | 前两小节对，之后整体错位 | 用原曲混音测 BPM + downbeat 仲裁（§4.3） |
| 2 | **用分离后的伴奏测节拍** | BPM 偏差 3–5%，且不稳定 | 永远用原始混音做 beat tracking |
| 3 | **唱段用 ASR 打时间戳** | 漏字、串词、长音处时间戳飞掉 | 已知歌词 + forced alignment（§4.4） |
| 4 | **绝对秒累积误差** | 短片段正常，整首越唱越飘 | melody v2 用 beat 坐标（§4.2） |
| 5 | **多次重采样** | 越处理越闷，高频一层层掉 | 统一 48k 内部工作，最后只 resample 一次 |
| 6 | **4GB 显存 OOM** | Demucs + ONNX + RVC 同时驻留直接崩 | GPU 队列串行 + 显存看门狗 + 失败回退 CPU |
| 7 | **僵尸任务** | 任务永远卡在 running，队列堵死 | heartbeat + 子进程 `exit` 即判失败（§3.5） |
| 8 | **重复点歌烧 GPU** | 5 个人同时点同一首，跑 5 遍 | cacheKey 在途去重 + fan-out（§3.3） |
| 9 | **QQ 语音条 60s 限制** | 超过时长的歌发送失败 | >60s 一律转文件；<60s 才走语音条 |
| 10 | **文件上传频率限制** | 短时间多条被风控 | 发送队列已有（`sender.js`），加 2s 间隔 |
| 11 | **中文多音字 / 中英混唱** | 「行了」唱成 hang le，英文单词被拆成拼音 | g2p 前做一遍人工词典覆盖；英文词单独标 `en` 音素 |
| 12 | **旋律循环接缝** | 每轮循环处有明显「断气」或音高跳 | 循环点选在乐句边界，接缝处插 80–150ms 换气 |
| 13 | **冷启动吃满显存** | 第一个任务 90s，后面 30s | 模型常驻 + 空闲 10 分钟后再卸载（LRU） |
| 14 | **缓存不失效** | 换了 RVC 模型，仍返回旧成品 | cacheKey 里带 `modelVer`（模型文件 mtime + size 的 hash） |
| 15 | **版权** | 自动下载原曲的合规风险 | 不做自动全网下载；只接受用户上传 / 管理员导入，并在协议里说明 |

### 9.3 顺手挖出来的 4 个真 bug

1. **`spawnSync` 冻结事件循环**（最严重）。渲染期间 Node 完全停摆：收不到 QQ 消息、发不出进度、心跳可能被判超时。异步队列如果没有这一项，等于白做。

3. **24bit 当成 16bit 算时长**。`mix_master` 输出 PCM_24，旧代码 `buffer.length/44100/2/2` 把 15 秒算成 **22.5 秒**（文件名、语音条/文件判断全受影响）。与之前「16k 当成 44.1k」是同一类错误，这次统一改成读 RIFF 头。
4. **失败只报「退出码 1」**。`cover-song.js` 把 stderr 吞了，群里只能看到无信息量的失败提示。现在会带最后 4000 字符里的关键行。

### 9.4 与原方案的偏差（需要你知道）

**没有实现 `job_runner.py`。** 原方案设想让 Python 当编排器、Node 只负责投递，但实际代码里 `route_a.py` 已经是一条完整流水线、Node 侧也已经有 `singLyrics`/`coverSong` 两个编排函数。再套一层 Python 编排器等于把调用逻辑写两遍，收益（统一的 JSONL 协议）可以用更便宜的方式拿到 —— 现在由 Node 把 Python 的日志行映射成进度，协议层省掉，风险最小。

`job_runner.py` 真正有价值的时机是 **P2 引入「扒谱 + 合成」多阶段流水线**时：那时需要一个进程内常驻模型、复用中间产物。届时再做。

### 10.3 三个和原方案不一样的结论

**① 「48k 单次重采样」这个目标本身要修正。** 实测糊桃 RVC 模型是 **48k** 原生率（不是方案里假设的 40k），所以链路上唯一一次转换是 48→44.1。但更重要的是：**这次转换不是「窄且暗」的原因**。对 RVC 输出做能量统计，16k 以上只有 **-77dB**、20k 以上 **-80dB** —— 模型根本没产出那部分频段。也就是说即使把整条母带链改成 48k，也捞不回任何东西。

所以 P1 里真正有效的动作是 **把中间产物从 16bit 升到 24bit**（量化噪声会在 EQ/压缩后放大），以及**把散落的 3 处 `if sr != SR` 收敛成一处并记账**（可测量、可回归）。高频问题是模型带宽问题，必须靠 P3 的「高频嫁接」解决 —— 把原唱人声 8–16k 的谱包络搬过来，而不是靠换采样率。

**② 缓存必须在 Python 侧做，而不是 Node 侧。** Node 侧算 cacheKey 只能缓存「整首成品」，粒度太粗：换个混音参数就全废。放到 `route_a.py` 里按阶段切，才能做到「只改 EQ 时只重跑母带」（实测 204s → 12.2s）。键用**文件内容哈希**而不是路径，同一首歌改名/移动目录也不影响命中。

**③ 「只给歌名」必须能直接点歌，否则路由等于没做。** 原来的 `sing_lyrics` 要求 `lyrics` 必填，模型遇到「唱个反方向的钟」只能把歌名塞进 lyrics，然后去唱「反方向的钟」五个字。现在 `lyrics` 非必填 + `title` 分离，并且加了兜底：短文本 + 高置信度命中曲库时自动改判成歌名。

### 10.4 待办（P2/P3 衔接）

- **全曲分离 + 窗口切片**：现在 stems 缓存键含 `start/dur`，同一首歌点不同段落仍要重新分离。正确做法是整首分离一次、按窗口切片（265 秒的歌 GPU 约 13 分钟，所以只在「同一首被点第二次」时触发全量分离最划算）。
- **HTTP `/api/jobs/:id`**：队列已支持查询/取消，只是没挂到控制台。
- **HF 嫁接**（P3）：按 §10.3 ① 的测量，这是解决「窄且暗」的唯一有效路径。

### 10.5 端到端验证时又挖出两个真 bug（比缓存更值钱）

**① m4a / aac 源直接翻唱必死。** 群友从 QQ 发来的音频很多是 m4a，`demucs` 内部的 sphn 解码器读不了，报
`LoadAudioError: no channel`；退到 ffmpeg 时又发现系统没装 ffmpeg。也就是说「发个音频来翻唱」这条路
**从来没通过**，只是之前没人试过 m4a。

修法（`audio_io.normalize_input`）：
- 能 `soundfile` 读的（wav/flac/mp3/ogg）→ 直接读 + `soxr_vhq` 转 44.1k；
- 读不了的（m4a/aac/ape）→ 找 ffmpeg 解码。ffmpeg 取 **项目自带**的
  `gpt-sovits-app/GPT-SoVITS-v2pro-20250604/runtime/ffmpeg.exe`，也可用 `FFMPEG_BIN` 覆盖；
- 解码结果按内容哈希缓存，同一首歌第二次翻唱不再解码；
- 找不到 ffmpeg 时给明确报错（指出格式、路径、怎么配），不再静默失败。

顺带的好处：输入统一成 44.1k wav 之后，Demucs 内部不再自己重采样，入口这一次转换是可控的。

**② 只翻 60 秒却把整首跑一遍。** `separate()` 的 `start/fit_sec` 是在 Demucs **之后**才裁的，
所以 258 秒的歌点 10 秒片段，Demucs 照样处理 258 秒。

修法（`route_a.py` 的 `precut`）：先把 `[start, start+dur]` 直切成 wav 再交给 Demucs。
实测 10 秒片段分离 **40.1s**（不预切估算约 1000s，因为 Demucs 约 4× 实时）。`--no-precut` 可关。

> 注意缓存键必须继续用**原始** `start/dur`，不能用预切后的 0 —— 否则所有窗口算出同一个键，
> 会把 A 段的伴奏发给点 B 段的人。

### 10.6 端到端结果（真实走完「只报歌名 → 投递」）

`node test-song-flow.mjs fxd 10`：路由判定 `fxd → cover`，回执 **0.01s**，队列内 **94s** 出成品
（解码 m4a + 预切 10s + 分离 40s + F0 6.7s + RVC 22.3s + 母带 2.2s），投递 `fxd-10s.wav` 2.5MB，
质检 7/9 项通过；同参数第二次点击 **cached=true，秒回**。

重采样记账：`count=1`，唯一一次是 `48000→44100 (fxd_rvc.wav)`。

### 10.7 P3 高频嫁接落地（`hf_splice.py`）

#### ① 先把前提推翻：糊桃模型不缺高频

§10.3 说「RVC 16k 以上只有 -77dB，所以要嫁接」——后来发现这个判断**只在 17k 以上成立**，
而且同窗口对比之后结论完全反过来：

| 频段（30–42s 同窗口，各自归一化到 0dB RMS） | RVC 人声 | 原唱人声（Demucs） |
|---|---|---|
| 3–5k | -18.2 | -31.0 |
| 5–8k | -17.7 | -33.5 |
| 8–11k | -22.2 | -40.1 |
| 11–14k | -33.0 | -46.5 |
| 14–16.5k | -43.8 | -55.5 |

RVC 的 8k 以上比原唱**亮 10–12dB**（声码器自带高频噪声底），真正「断崖」只有 17k 以上。
而原版母带 17k 以上只剩 **-81dB** —— 那里的能量是 Demucs 的分离残留，不是人声。
所以嫁接上限压到 **16.5k**，且必须做成「数据说该补才补」，否则会往成品里搬噪声。

#### ② 算法：按帧补到「目标相对电平」

不是 `out = dst + 0.2 * src_hf`（0.2 幅度在不相关叠加下只抬 0.17dB，等于没做，还会在安静处翻出镲片残留）。
做法是：

1. 把原唱电平对齐到 RVC（后者做过 -16dB 响度归一化，不对齐没法比）；
2. 取原唱该频段的**相对电平** `L = 10log10(频带功率/全带功率)` 作为目标（`--hf-air` 可再往上抬）；
3. 逐帧（10ms）用 RVC 自己的全带功率推算该帧「该有多少高频」，差值就是本次要补的功率：
   `s(t) = sqrt((P_target − P_dst) / P_src)`，40ms 平滑后插值到采样点。

三个自然结果：局部已经够亮（齿音/气声）的帧差值为负 → 不动，不会二次加倍；气口/静音帧目标随全带功率归零 → 不翻底噪；
每一帧加进去的功率恰好等于目标增量。

四道闸：目标默认「严格对齐原唱」、每帧源增益上限 8×、结果不许高于全带 -20dB、报告里给高频包络相关度。

#### ③ 实测

| 场景 | 结果 |
|---|---|
| 合成「暗模型」（把 RVC 10k 以上砍掉） | 14–16.5k **+34dB**，与原 RVC 高频包络相关 0.82 |
| 真实素材 ×2（hutao 模型） | 两组都判定「原唱不高于 RVC」→ **零改动**（`applied=0`，maxΔ=0.0000） |
| 强制 `--hf-air` 为正 | 源比目标暗时仍不补（目标还没超过 RVC 现有水平），符合预期 |
| 自测 | `test_hf_splice.py` **13/13** 通过（补偿、旁路、长度、峰值、对齐） |

链路新增阶段 `hf`（键 = RVC 输出哈希 + 原唱人声哈希 + air），命中时只花 **0.12s**；
只改混音参数时 `stems/f0/rvc/hf` 四级全中，总耗时 **11.8s**。

#### ④ 顺手修掉的真 bug：Windows 上缓存目录 rename 偶发拒绝访问

`os.replace(tmp_dir, dst_dir)` 有约 1/10 概率报 `WinError 5`（杀软/索引服务短暂持有句柄）。
改成重试 5 次 + 退化为「直接往目标目录拷」。这个坑对 `stems/rvc/final` 一样存在，只是以前没撞上。

#### ⑤ 「暗」的真因不是缺高频，是整体倾斜

同窗口把成品和原版母带比（各自归一化）：

| 频段 | 150–400 | 400–1k | 1–3k | 3–5k | 5–8k | 8–11k | 11–14k | 14–16.5k |
|---|---|---|---|---|---|---|---|---|
| 成品 − 原曲 | +2.2 | +1.7 | -2.3 | -2.1 | -1.7 | -1.1 | -1.8 | -3.0 |

**低频多 2dB、3k 以上一律少 1–3dB** —— 这是一条 2dB 的整体倾斜，不是「缺一层空气」。
同时分离出来的伴奏与原始混音在 1–16.5k 几乎完全一致（±0.2dB），说明锅不在 Demucs，
而在人声链的低中频补偿（355Hz +7dB / 420Hz body / 707Hz +4dB）把整体往「暖」的方向拽。

所以 P3 剩下的动作应该是**总线倾斜校正**（拿 `ref_audio` 做参考，限幅 ±3dB 的 shelf），
而不是继续在人声上堆高频。`--hf-air` 在这里也救不了：源本来就比 RVC 暗，抬目标也只是把暗源放大。

|---|---|
| `diffsinger-hutao/melody_v2.py` | melody v2 数据结构：拍坐标、v1 自动升级、整小节循环、变速换算 |
| `diffsinger-hutao/melody_extract.py` | 自动扒谱：节拍网格 + crepe F0 + 音符切分 + 吸附 + 字音分配 + 质量评估 |
| `diffsinger-hutao/test_melody_v2.py` | 19 项逻辑断言（v1 兼容 / 变速 / 整小节循环 / rest 不占字） |
| `diffsinger-hutao/test_melody_extract.py` | 合成信号回归（16 音旋律 / 切分三连音 / 跨八度大跳） |
| `diffsinger-hutao/sing_engine.py` | 载入 v1/v2、循环闭合、`--melody-bpm`、`--strict-timing` |
| `src/sing-song.js` | 有旋律时不再强塞 `--bpm 92` |

### 11.2 melody v2 到底解决了什么

§4.2 说的是「绝对秒会累积误差」。真做下来，v2 的价值比原方案描述的多两点：

**① 循环接缝。** v1 的循环单位是「第 N 个音符」，一个乐句如果不是整小节，
每循环一圈就错开一点。v2 把段落**补齐到小节整数倍**（不足的部分补 `rest`，
而不是拉长最后一个音——拉长会让那个字被拖着唱，听感像抢拍）。

**② 换气口是一等公民。** 扒谱出来的人声里本来就有换气，v1 没地方放。
v2 允许 `{"rest": true}` 条目，且**不消耗歌词字**。连带的修正是：当旋律自带 rest 时，
`build_ds` 不再额外插乐句气口——否则唱的版本比谱面长，循环时逐圈错开。

**③ 变速只改一个数。** 实测 v1「反方向的钟」9.93s 的谱，`--melody-bpm 88`
后变成 10.38s（比例正好 92/88），音符一个没动。

### 11.3 扒谱：4 个必须记住的坑

**① 中文流行歌的主歌扒不准，而且这是原理性的。**
实测某段音高稳定在 **57.7**（距 A3 与 A#3 各 30 音分）——说话式唱法，
「最近的半音」本身就模棱两可。量化后每 100ms 在 A3/A#3 之间抖。
处理办法是 `de_flap`（吞掉 A-B-A 的小二度抖动）+ 「音高解释率」指标，
而不是硬调参数。

**② 八度纠错不能按窗口取中值。**
旧写法（3 秒窗口中值 + ±12 校正）会把真实的跨八度大跳拉平：
合成测试里 `C3→C5→C3` 被压成连绵的 C3，音高命中 **0/8**。
改成两级——帧级只修「恰好偏 ±12 且邻居彼此一致」的毛刺，
音符级只修「孤立、短（<320ms）、两侧同音」的八度误判——之后 **8/8**。

**③ torchcrepe 的 batch_size 会改变结果（本机 4GB 上）。**
`batch_size=512` 时 523Hz 会被读成 131Hz 且置信度 0；`128` 时正常返回 523Hz/0.96。
同一段音频、同一个模型，只有批大小不同。**固定 128**，并在注释里写明原因。
顺带把 F0 段从 29s 降到 9.7s（12s 音频）。

**④ BPM 必须用原始混音测。** 分离伴奏上测 tempo 会错半速/倍速，
而且这种错误「听起来好像对」，两小节后才错位（§4.3 已写，实测确认）。

### 11.4 实测

**合成信号回归**（`test_melody_extract.py`，已知谱面 → 合成类人声 → 扒回来）：

| 用例 | 音高命中 | 起音中位偏差 | 音符数 |
|---|---|---|---|
| 级进+跳进+长短音（16 音） | **16/16 (100%)** | 0.008 拍 | 16/16 |
| 附点/切分/三连音（12 音） | **12/12 (100%)** | 0.007 拍 | 12/12 |
| 跨八度大跳（8 音） | **8/8 (100%)** | 0.003 拍 | 8/8 |

**真实素材**（反方向的钟，24 音/12s 窗口）：

| 窗口 | 音高解释率 | 结论 |
|---|---|---|
| 主歌 30–42s | 71% | 告警「说话式唱法，扒谱不可靠」 |
| 副歌 100–112s | **88%** | 通过（音域 55–69，明显更旋律化） |
| 整段 18–60s | 75% | 告警 |

「音高解释率」= 每一帧 F0 与所在音符 midi 相差 < 0.5 半音的帧占比。
这是判断「这段能不能用」的唯一硬指标，也是验收标准「可用率 ≥ 70%」的测量方式。

**耗时**：12s 音频端到端 12.4s（节拍 3.7s + F0 9.4s 含首次 CUDA 初始化 15s 摊销；
热态 F0 约 0.28× 实时）。3 分钟整曲预估 60–70s。

### 11.5 顺手修掉的真问题：渲染比谱面长 4%

`sing_engine.build_ds` 只给 `note_dur`，让时长模型自己决定音素时长。
实测 12.69s 的谱渲染成 **13.19s（+4%）**，逐句累积 → 后半段拖拍。

修法：`--strict-timing`（有旋律时默认开）直接写 `ph_dur`：声母压到 40ms，
其余全给韵母。实测同一段谱：

| 模式 | 渲染长度 | 谱面长度 | 偏差 | 单偏移下的音高命中 |
|---|---|---|---|---|
| 交给时长模型 | 13.19s | 12.69s | +3.9% | 57% |
| 钉死时值 | 11.94s | 11.91s | **+0.25%** | **74%** |

这就是 §4「BPM 严格对齐」真正落地的地方——不是把 BPM 调准，而是**不让模型改时值**。

### 11.6 用法

```bash

  --src songs/raw/反方向的钟.wav --separate \

# 按新速度唱（只改 bpm，音符不动）

```

机器人下次请求就能匹配到（模型工具枚举是启动时固化的，不重启也能靠「报歌名」自动匹配）。

## 12. P2.5 落地：点歌时「现场扒旋律」+ 作业可观测（2026-10-19）

§11 的扒谱是个**离线脚本**：要人先跑一遍、把谱子放进旋律库，点歌才用得上。
旋律库因此永远只有两首。这一节把它接进点歌流程：**只给歌词 + 歌名，系统自己扒**。

### 12.1 链路

```
群友「唱：我对着天空许下心愿」+「反方向的钟」
  → submitSing 判断：没旋律、歌名能匹配到 songs/raw/ 里的原曲
  → 入队回执（21ms），预估时长里已含扒谱
  → 作业阶段 0：melody-auto.js
       melody_extract.py --src 原曲 --separate --auto-window --title 歌名
       （Demucs 分离 → CREPE F0 → 音符切分 → melody v2）
  → 作业阶段 1：sing_engine.py --melody <cache/melody/xxx.json>
  → 投递语音条 + 「旋律是刚按原曲扒的，音高贴合 86%」
```

### 12.2 两个必须加的参数

**`--auto-window`（自动选段）**：群友不会报第几秒开始。从 0 秒扒到的是前奏，
只有几个音，铺到整段歌词上就变成另一首歌。实现：300–3400Hz 带通 → 50ms 帧能量
→ 1s 平滑 → 按窗口长度滑窗求和取最大，起点至少 8s、结尾留 0.5s。
实测《反方向的钟》（265s）自动选中 **224.1–244.1s**，正是最后一遍副歌。

**`--title`（显示名）**：分离目录用 `mel-<hash>` 避免互相覆盖，
但谱面里的 `name` 要给人看。没有这个参数，日志和群消息里会写成
`《mel-9a103dd116874ab1》唱好了`。

### 12.3 质量门槛：宁可用算法旋律，也不用跑调的谱

`melody-auto.js` 读 `pitch_fit`（帧 F0 与所属音符相差 <0.5 半音的比例）：

| pitch_fit | 行为 |
|---|---|
| ≥ 0.62 | 用这份谱 |
| < 0.62 | **不用**，回退算法旋律，并在群里如实说「原曲那段扒得不准」 |

缓存也认这个门槛：上次低于 0.62 的窗口不会拿来复用，会重新挑一段。
`inflight` 表防止同一段被并发扒两遍（两个群同时点同一首歌）。

### 12.4 实测

| 项 | 结果 |
|---|---|
| 首次扒谱（20s 窗口） | **66.6s**（分离 48 + F0 14.7 + 后处理 3.9） |
| 二次点歌 | **1ms**（内容寻址缓存） |
| 谱面质量 | 42 音、解释率 **85%**、BPM 95.7、3 个换气 rest |
| 端到端（歌词+歌名 → 语音条） | 入队 **21ms**，作业 **80.6s**，`test-song-auto.mjs` **9/9** |
| 群消息 | 「《反方向的钟》唱好了，4 秒（旋律是刚按原曲扒的，音高贴合 86%）」 |

### 12.5 作业可观测：`/api/jobs` + SSE

队列在进程内，但「在后台跑」如果没有观测接口，就等于「看不见」。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/jobs?group=&limit=` | 列表（可按会话过滤），按创建时间倒序 |
| GET | `/api/jobs/:id` | 单个作业：status/stage/progress/etaMs/error |

同时队列事件（`job.queued/stage/done/failed/canceled`）会转发到已有的
`/api/events` SSE 流，控制台或外部面板订阅一次即可，不用轮询。
已验证：不存在 id 返回 404 `{"ok":false,"error":"job_not_found"}`，
取消不存在返回 409。

### 12.6 防刷屏

`MAX_ACTIVE_PER_CHAT = 2`：同一会话同时最多两个作业（排队 + 运行），
超了直接回「这个会话已经排了 2 首，等一首唱完再点」。
按会话而不是按 QQ 号，是因为当前 `ctx` 只带 `chatKey`；要按人限流需要

## 13. P4：人声音色校正（总线 shelf 的正确形态）2026-10-19

### 13.1 先证伪：总线 shelf 修不平

按「低频 -2dB@150、高频 +1.5dB@3000」实测，1/6oct 从 11.2 只降到 **10.9**；
网格搜索（low 150–450 / high 2k–4k，步长 1dB）最好的两段组合也只到 **7.0**，
而且需要 `+6@450 / +7@3000` —— 这已经不是「微调倾斜」，是把伴奏整体变亮。

原因：RVC 干声的偏差不是一条斜线，是**三段塌陷 + 一段鼓包**：

```
频段    250  354  445  500  707   1k  1122   2k  2520  2828   4k  5.6k   8k
偏差    -7  -13  -16  -12   -6    0    +7    +5    +6    -6   -9   -16   -12
```

350–700Hz（胸腔/厚度）塌 12–16dB，4–8k（空气）塌 10–16dB，1–2.5k 反而凸 5–7dB。
任何单调的 shelf 都只能「一边抬一边压」，把凸的地方抬得更凸。

### 13.2 做法：拿原唱干声当目标，只改人声

`diffsinger-hutao/vocal_tone.py`（新增）：

1. 两条干声各做 1/6oct LTAS，1kHz 归一到同一条基线；
2. 10 个候选滤波器（2 shelf + 8 bell）做**有界最小二乘**（`lsq_linear`，±8dB），
   再按「贡献 <0.8dB 丢掉」「只留 5 段」「±1.5dB 坐标细化」收尾；
3. 范围锁 250–8k（100Hz 以下不是 RVC 的锅，10k 以上归高频嫁接）。

为什么不用最小相位 FIR 一步贴合：31 段逐点拟合会把换气/齿音的瞬时谱也当目标，
实测 sibilance 变尖；而且参数不可读、出问题没法逐段回退。

`route_a.py` 新增阶段 **3c**（在 3b 高频嫁接之后、母带之前），带自己的缓存
`tone-v1`（键 = 干声文件 + 原唱干声 + max_db），失败自动降级为「不校正」。

### 13.3 两个必须同时改的参数（否则白干）

| 参数 | 旧 | 新 | 为什么 |
|---|---|---|---|
| `vocal_eq_scale` | 1.0（写死） | **0.35** | 母带里 `+7@355 / +4@707 / +3@2830 / +4shelf@2200 / +3@5k` 是照**旧 RVC 缺中低频**手工补的。人声已经校正过再补就是二次叠加 —— 实测 1–4k 占比 6.7%→2.0%，1/6oct 反而从 4.5 涨到 5.2 |
| `inst_low_db` | 18dB@65Hz | **8dB** | 这个 +18 是「人声抬、伴奏压之后 40–80 会掉」的补偿，但它把总能量全推到低频：1–4k 占比被压到 **2.0%**（原曲 5.5%）。改 8 后占比 6.4%、40–80 收到 -4.7dB（原曲 -4.8），一举两得 |

`vocal_eq_scale` 只在「音色校正真的跑了」时才传 0.35；`--no-tone` 时仍是 1.0，
老行为不变（缓存键 `final-v3` 已把这两个参数算进去）。

### 13.4 顺手修掉的三个质检 bug

1. **参考段取错**：预切后 `start` 被重置成 0，但质检传的是 `ref_start=start`，
   于是永远拿原曲 **0–30s** 当参考。`1/6oct` 实测 4.4dB 被算成 **19.0dB**，
   恒挂。改用 `orig_start`（若参考就是预切后的文件则用 0）。
2. **密度/动态用了绝对阈值**：`4.12±1 个/秒`、`>8dB` 只对某几首现代混音成立。
   《反方向的钟》原曲自身密度 **6.43**、DR **4.3** —— 参考自己都过不了。
   有 `ref_audio` 时改成「对着原曲同段判」（密度差 ≤0.8 个/秒；DR 不低于原曲 1dB），
   绝对阈值降级为兜底。
3. **RVC 音高项逐帧不可比**：参考 F0 来自 Demucs 干声（有伴奏串音），女声模型又容易被
   判成二次谐波 —— 同一段音频逐帧中位差 1900 音分，但 chroma 相似度 0.87。
   改成 **chroma 调性一致**（≥0.75 通过）：对八度和时间偏移都不敏感，对真移调敏感
   （人为 ±5 半音会从 0.87 掉到 0.34–0.47）。

### 13.5 实测（《反方向的钟》100–130s，30s）

| 指标 | 改前 | 改后 |
|---|---|---|
| 干声 max\|dev\|（1/6oct，对原唱干声） | 15.9dB | **6.0–6.5dB** |
| 干声 RMS 偏差 | 8.99dB | **2.8–3.1dB** |
| 成品 1/6oct（250–8k，对原曲同段） | 11.2dB ❌ | **4.1–4.4dB** ✅ |
| 1–4k 能量占比 | 2.0%（压过头）/ 6.1%（旧人声） | **6.0–6.4%**（原曲 5.5） |
| 40–80Hz | -1.9dB（比原曲肥 3dB） | **-4.9dB**（原曲 -4.8） |
| DR | 7.6–8.1（靠低频灌出来的） | **5.3**（原曲 4.3，更贴） |
| QC | 5/9 | **9/9** |

全链路（含 Demucs + RVC + 嫁接 + 校正 + 母带 + 质检）148.6s，其中校正 **6s**、母带 3.4s。
`test_vocal_tone.py` 11/11（合成信号，不需要 GPU）。

### 13.6 用法

```bash
# 默认就开（拿原唱干声做目标）
python route_a.py --src 原曲.wav --name 成品 --start 100 --dur 30 --ref-audio 原曲.wav

python route_a.py ... --no-tone            # 关掉校正
python route_a.py ... --tone-max-db 6      # 收紧单段上限（更保守）
python route_a.py ... --tone-eq-scale 0    # 母带人声固定 EQ 全关（校正很准时可试）
python route_a.py ... --inst-low 12        # 想要更肥的低频（会让 1–4k 占比变低）
```

### 13.7 还留着的坑

- 1/6oct 的残差是**谐波梳状**（1122 +5.3 / 1414 -3.7 / 2000 +5.0 / 2520 +6.5），
  来自「换了一个人唱」的谐波幅度差异，EQ 修不掉也不该修。
- 只对同一首歌有效：目标来自原唱干声，**跨歌不通用**（所以不能做成固定的几条曲线）。
- 说唱/快歌的干声串音更重，LTAS 目标会更脏；目前没有「可信度」门槛，
  后续可以用「原唱干声的 voiced 比例」做闸门。

## 14. P5：唱歌默认干声（可在设置里切回带伴奏）2026-10-19

### 14.1 需求

「以后唱歌默认干声，可以在程序里选默认干声还是带旋律（带伴奏）唱」。

两条唱歌链路的「干声」是两件不同的事，必须分开处理：

| 链路 | 干声做法 | 带伴奏做法 |
|---|---|---|
| **唱歌词**（sing_engine.py / DiffSinger） | `--no-acc`：跳过 `auto_accompaniment`，只输出人声（仍做 polish + 峰值 0.9） | 按 key/bpm 生成和弦伴奏后混音 |
| **翻唱原曲**（route_a.py / RVC） | 新增 `--dry`：跳过混音母带与成品质检，直接输出「高频嫁接 + 音色校正后」的人声，只做淡入淡出 + 峰值归到 -1dBFS | 混原曲伴奏 + 母带 + 9 项质检 |

两条都默认干声。翻唱的干声分支是本次新写的（原来只能出混音成品）。

### 14.2 配置项（config.json）

```jsonc
"audio": {
  "svc": {
    "singDry": true,     // 「唱：歌词」默认干声；false = 带自动伴奏
    "coverDry": true     // 按原曲翻唱默认干声；false = 混音成品
  }
}
```

UI：设置 → 语音 → 唱歌，两个开关（保存后下一次点歌生效）。

工具层可以临时覆盖，不传就按设置默认：

- `sing_lyrics`：`noAcc`（true=干声 / false=带伴奏）；点歌走翻唱路由时透传 `dry`
- `sing_cover`：新增 `dry`

群友在群里说「清唱 / 不要伴奏 / 只听人声」→ 干声；说「带伴奏 / 要原曲那种」→ 带伴奏。

### 14.3 两个必须一起做的改动（否则出 bug）

1. **成品缓存键要加 dry 维度**：`final-v3` → `final-v4`，把 `bool(dry)` 算进键。
   否则点了干声之后点带伴奏的，会命中上一次的干声成品（反之亦然）。
2. **输出文件名要分开**：翻唱干声写成 `<歌名>_路线A_30s_干声.wav`，
   混音仍是 `<歌名>_路线A_30s.wav`。缓存键虽然区分了，但 `out/` 是给人直接听的，
   同名会让后跑的覆盖先跑的。

### 14.4 干声不做的两件事（有意为之）

- **不做母带**：那套 EQ/压缩/响度是针对「人声 + 伴奏」调的，套在纯人声上会变形
  （比如 `inst_low +8dB@65Hz` 是补伴奏低频的，人声不需要）。
- **不做成品质检**：1/6oct 偏差、声场 Side−Mid、40–80Hz 这些的参照物是「原曲混音」，
  对一条纯人声没有参照意义，做了只会给出误导性的红字。
  干声只查一项：**和原唱干声的 chroma 调性一致度**（≥0.75 通过）——
  这是唯一能证明「没唱跑调」的硬指标，且对八度误判、时间偏移都不敏感。

`qc.py` 里把这段抽成了公共函数 `chroma_key_sim(a, b, sr)`，run_qc 内部的判定维持不动。

### 14.5 实测（《反方向的钟》100–130s，30s）

| 项 | 结果 |
|---|---|
| 干声翻唱全程（各阶段缓存命中） | **4.3s** |
| 峰值 | -1.0 dBFS（单声道 30.00s） |
| 与伴奏的相关性 | **0.001**（确认没混进伴奏） |
| 与「音色校正后」人声的相关性 | **0.999**（确认就是那条人声） |
| 调性一致度（vs 原唱干声） | **0.892**（≥0.75 通过） |
| 干声唱歌词（8 字） | 53s（渲染本身，跟带不带伴奏无关） |

### 14.6 附：翻唱时的旋律到底是怎么处理的（调研结论）

**翻唱不扒谱、不量化、不改音准，旋律 = 原唱旋律原样照抄。**

```
原曲 → Demucs 分离 → 原唱干声 ─┬─→ RVC：用自己的 f0 方法（rmvpe）从这条干声提音高
                              │        → 按模型重建，只换音色（+ f0up 整体移调）
                              └─→ pitch_track 提 F0：只写报告/供质检，**不参与合成**
```

- RVC 是「音色迁移」：音高曲线直接来自原唱干声。原唱的滑音、颤音、
  甚至跑调都原样保留 —— 好处是像原曲，代价是**修不了音准**。
- 想整体移调只有一个旋钮：`--f0up`（半音整数，默认 0）。
- `pitch_track` 那一路 F0 的用途只有三个：报告里的音域/voiced 比例、
  质检的音高项、以及干声模式的调性一致度。它不喂给 RVC。
- 女声模型 + 分离干声串音会让逐帧 F0 判定不可靠（实测同一段音频逐帧中位差
  1900 音分，但 chroma 相似度 0.892），所以音准一律用 chroma 判定，不用逐帧 F0。

对照「唱歌词」链路，旋律有三个来源（优先级从高到低）：

1. **旋律库** `songs/melodies/*.json`（手工/历史扒的）
2. **现场扒谱** `melody_extract.py`：CREPE F0 → 音符切分 → 量化到半音 → melody v2 谱面，
   `pitch_fit < 0.62` 就弃用、回退算法旋律
3. **算法生成**：sing_engine 按 key/scale/bpm 现编

一句话区分：**翻唱 = 音色迁移（音高照抄原唱）；唱歌词 = 按谱合成（音高来自谱面）。**
这也是为什么「翻唱」必须要有原曲文件，而「唱歌词」只要歌词就能唱。

## 15. P6：曲库里没有的歌怎么唱（群友发音频 / 哼一段）2026-10-19

### 15.1 先厘清一个误解：「歌不需要训练」

被问到「翻唱一首没训练过的歌（如《让一颗心免于哀伤》），不乱唱，能直接做到吗」时，
前提里有个常见误解 —— **RVC 训练的是「胡桃的音色」，不是某一首歌**。
换歌不需要重新训练，模型一直在那儿。

真正的瓶颈是：**翻唱是音色迁移，音高曲线直接照抄原唱干声，所以必须有原曲音频**。
没有音频 = AI 没听过这首歌 = 不知道旋律长什么样 = 只能算法现编 = 听众耳里的「乱唱」。

于是「不乱唱」只有三条路，本次把后两条都打通了：

| 路 | 需要什么 | 唱出来是什么 | 改前 | 改后 |
|---|---|---|---|---|
| 翻唱（RVC） | 原曲音频 | 原唱的旋律 + 胡桃音色 | 只吃本地曲库文件 | **群友发音频/直链也能**（`sing_cover.messageId` / `.url`） |
| 按谱唱（DiffSinger） | 一段能听出调的音频 | 扒出来的旋律 + 胡桃音色 | 只在曲库有原曲时现场扒 | **群友哼一段也能**（`sing_lyrics.messageId`） |
| 算法现编 | 只要歌词 | 现编的旋律 + 胡桃音色 | 兜底 | 仍是兜底，且必须如实说「调是我编的」 |

### 15.2 群友发音频 → 正式入库 → 翻唱（`sing_cover`）

新增参数 `messageId`（群友发的语音/文件）和 `url`（直链）。流程：

```
取音频（get_record / 本地文件 / 直链） → 嗅探真实格式 → 落盘 songs/raw/<歌名>.<ext>
  → 刷新曲库缓存 → 走完整翻唱链路（Demucs→F0→RVC→嫁接→音色校正→母带/干声）
```

关键设计：**落进正式曲库而不是临时目录**。这次翻唱完，这首歌就永久在 `songs/raw` 里，
以后群友再报这个歌名，`findLocalSong` 直接命中，**不用再发第二次音频**。
（`sing_lyrics` 的现场扒谱也因此自动受益。）

三个细节：

- **格式嗅探**：QQ 语音可能是 silk，URL 后缀也不可信。按文件头判
  （RIFF/fLaC/OggS/ID3/ftyp），认不出再用 ffmpeg 转 wav 后入库。
- **绝不覆盖**：同名且字节数一致 → 复用；同名不同内容 → 加 `-2` 序号。
- **参考音频不进曲库**：只给歌词时那段音频只是「旋律参考」，存 `cache/incoming/`；
  不给歌词（=当一首歌点播）才存 `songs/raw/`。

### 15.3 群友哼一段 → 扒谱 → 按谱唱（`sing_lyrics`）

发整首歌门槛太高，哼一句就够。同样加 `messageId` / `url`，落盘后交给
`melody-auto.js` 现场扒谱，**并且跳过分离**：

- `melody_extract.py` 不传 `--separate` 时会把输入直接当人声 —— 哼唱正好是纯人声，
  省掉 Demucs 那 40~60 秒，也避免分离把哼唱削坏；
- 缓存键加了 `separate` 维度（`sep` / `raw`），否则哼唱会命中原曲分离版的老谱；
- 超时从 `180s + win*2.5s` 降到 `60s + win*2.5s`；
- 扒谱失败（`pitch_fit < 0.62`）照旧回退算法旋律，并如实告知。

另补一个分支：**只报歌名、没歌词、但发了音频** → 直接按翻唱排队，不再反问「要唱哪段词」。

### 15.4 实测

| 项 | 结果 |
|---|---|
| 入库自测 `test-incoming-song.mjs` | **15/15** |
| 端到端（新歌入库 → 完整翻唱，20s 干声） | **128.7s**（分离 42.9 + F0 14.7 + RVC 38.4 + 干声输出 0.1） |
| 干声峰值 | -1.0 dBFS |
| 调性一致度 | **0.889**（≥0.75 通过） |
| 音色校正 | 生效（bell@450 +8 / @1200 −7.5 / @2500 −8 / shelf@3200 …） |

### 15.5 用法

群友：*「唱个让一颗心免于哀伤」*
→ 机器人：库里没有 → 「把歌发过来（或哼一段），我就能按原曲唱」
→ 群友发音频 → 机器人调 `sing_cover { messageId: <那条消息>, name: "让一颗心免于哀伤" }`
→ 入库 + 翻唱，**以后再报歌名直接命中**。

群友只哼了一段 → `sing_lyrics { lyrics: "…", messageId: <那条语音>, title: "歌名" }`
→ 从哼唱里扒谱 → 按真旋律唱。

### 15.6 没做的

- 不会自动联网搜歌下载（版权 + 之前实测网络时常不可达）；
- 参考音频没有时长/质量门槛，群友发一段 3 秒噪音也会照扒，然后被 `pitch_fit` 拦下回退；
- 入库的歌不会自动写进旋律库（`songs/melodies/`），所以「按谱唱」那侧下次仍要重扒
  （有 `cache/melody/` 内容寻址缓存，二次是 1ms，影响很小）。

### 16.3 顺手补的强心针：点歌台缓存也是曲库

修到一半发现一个更划算的事实：**B站缓存歌单里躺着 23 首原曲**（包含群里点名的
《使一颗心免于哀伤》），而唱歌链路的曲库只有 `songs/raw` 里那一两首。

于是把点歌台接进曲库（`song-router.js`）：

- `findSongInPlaylist(title)`（异步）：`resolvePlayQuery` 命中（只要 `exact/bvid/index`）→ `ensureMp3` 按需转码 → 返回 mp3 路径；
- `findCachedPlaylistAudio(title)`（同步，队列里用）：只认已转好码的文件，不触发转码 ——
  否则会出现「工具说按原曲唱、队列里其实在现编」的前后不一致；
- `sing_lyrics` 点歌模式 / 有歌词时的旋律来源判断 / `sing_cover` 的按名找曲，三处都接上。

实测：`使一颗心免于哀伤 → data/playlist/audio/bili-1537675442.mp3`，
`青花瓷`、`反方向的钟` 同样命中；《雨爱》没有（所以仍要要素材，行为正确）。
