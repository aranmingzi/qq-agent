> 2026-10-29 · 对标 AstrBot 4.29.3 / LangBot 4.11.2 / MaiBot 1.3.18
> 一句话：**模型拼错一个下划线，整轮就白跑了。** 这一轮让它知道该改成什么。

## §1 原来错在哪

### 1.1 拼错一个字符 = 整轮报废

实测 `data/sessions/` 1000 份会话里出现过这条原文：

```
错误：未知工具 get_ message_images
```

注意名字里那个**空格**。模型的意图完全正确 —— 它就是要取那条消息里的图，参数也对 ——
但拿回一句"未知工具"就放弃了那一轮。用户看到的是**"它没理我"**。

这类失败和"能力不足"完全不同：能力是够的，只是**名字没对上**。
而错误文案里没有给出任何可执行的下一步，模型只能重试或放弃。

`watch_video` 是同一个形状的另一种表现。实测 3 次全是：

```
错误：这个视频看不了：yt-dlp：视频信息解析失败：
ERROR: [generic] '2137847126' is not a valid URL
```

`2137847126` / `53431312` / `#1510279327` —— 模型把**消息 id** 当成了视频链接。
`findVideoUrl()` 找不到链接，代码就 `hit?.url || rawUrl` 把原样字符串丢给 yt-dlp，
拿回一句对模型毫无信息量的英文报错。

### 1.2 `load_tools` 装回工具后顺序不稳

`src/orchestrator.js` 的 `enablePack()` 里，排序基准用的是 `this.toolDefs`：

```js
const order = new Map((this.toolDefs || []).map((d, i) => [d.name, i]));
```

`this.toolDefs` 是**未经功能开关过滤**的全集；而第一次 `selectToolDefs` 用的基准是
`allAllowed`（**过滤后**的全集）。被开关关掉的工具（视频关了、搜索关了、
非主人会话的 `masterOnly`）在 `allAllowed` 里根本没有，却仍占着 `this.toolDefs` 的位次。

结果：装回来的工具会排到不可预期的位置。**这不会报错**，只会让前缀缓存的稳定前缀
每次略微不同 —— 最难查的那一类问题（全局缓存命中率 78.3%，掉一点就是真金白银）。

## §2 借鉴了什么

| 来源 | 借鉴点 | 我怎么改的 |
|---|---|---|
| AstrBot 4.29.3 `astrbot/core/pipeline/` | 工具调用失败时把**可执行的下一步**写进返回值，而不是只报错 | 提示文案点名正确工具 + "改用它重试" |
| LangBot 4.11.2 `src/langbot/pkg/provider/` | 工具名与 schema 的**归一化匹配**（大小写/分隔符无关） | `normalizeToolName()`：去空白、转小写、分隔符统一后删除 |
| MaiBot 1.3.18 `src/chat/tools/` | 工具名相近时**不猜**，宁可让模型重试 | 首 token 硬闸 + 0.82 门槛，猜不出就照旧"未知工具" |

**没有照抄的部分**：AstrBot 那套是把工具名注册进一个别名表，需要维护；
我这边是**纯函数按需计算**，不引入任何持久状态 —— 更符合本项目的依赖约束。

### 2.1 为什么不复用 `song-router.js` 的 `nameScore`

第一版图省事用了现成的 `nameScore`（中文歌名的 CJK 二元组 + Dice），结果：

```
nameScore('send_stickr', 'send_sticker') = 0.674
nameScore('web_serch',   'web_search')   = 0.640
nameScore('get_message_img','get_message_images') = 0.727
```

因为它对非精确匹配**乘了 0.8 的折扣**（`return dice >= 0.45 ? dice * 0.8 : 0;`），
**上限就是 0.8**。而我把门槛设在 0.82 —— 于是模糊路径**永远不可能命中**，
整条通道是死代码，测试却是绿的（因为归一化路径还在工作，看起来"能用"）。

改用字符级编辑距离后：

```
editSimilarity('send_stickr','send_sticker')     = 0.917
editSimilarity('web_serch','web_search')         = 0.900
editSimilarity('get_message_img','get_message_images') = 0.833
editSimilarity('send_stickr','send_message')     = 0.417   ← 不会误判
```

工具名是纯 ASCII 的 snake_case，编辑距离比 CJK 二元组可靠得多。
**教训：复用之前先量一下被复用函数的取值范围，别假设它和你的量纲一致。**

## §3 改了什么

### 3.1 新模块 `src/tool-name-hint.js`（142 行，纯函数）

| 导出 | 作用 |
|---|---|
| `normalizeToolName(name)` | 去空白 → 小写 → 分隔符统一为 `_` → 删掉所有 `_` |
| `editSimilarity(a, b)` | `1 - 编辑距离 / 较长者长度`；空串互比返回 0（不是 1） |
| `suggestToolName(name, available, opts)` | 两级匹配，返回 `{name, score, via}` 或 `null` |
| `describeToolSuggestion(name, suggestion)` | 面向模型的中文提示文案；无候选返回 `''` |

**两级匹配的顺序是有意的**：

1. **归一化相等** —— 无条件命中，`score: 1`。这一类（多空格、少下划线、大小写）
   最常见也最可靠，不该被任何门槛挡住。
2. **编辑距离** —— 必须同时满足 `>= minScore (0.82)` **且首 token 相同**。

首 token 硬闸是为了防这一类错误：

```
suggestToolName('web_xxx', TOOLS, { score: () => 0.99 })
  → 只能返回 web_ 族，绝不会猜 send_message
```

猜错动作族的代价比不猜大得多 —— 模型会真的去发一条消息。

### 3.2 `src/tools.js` 接入

`executeTool()` 查表失败时：

```js
const guess = suggestToolName(name, defs.map((d) => d.name));
const hint = describeToolSuggestion(name, guess);
return { content: hint ? `错误：${hint}` : `错误：未知工具 ${name}`, isError: true };
```

同时**删掉了** `nameScore` 的导入 —— 它在这个文件里只有这一处用途，
留着会诱导后来者再踩一次 §2.1 的坑。

### 3.3 `watch_video` 认出裸消息 id

```js
const bareId = /^#?\d{4,20}$/.test(rawUrl);
if (bareId && !hit) {
  return err(`「${rawUrl}」看起来是消息 id，不是视频链接。`
    + '要拿那条消息里的视频，用 get_message_images（图片/视频都走它）；'
    + '真正要看视频内容，就给我 B站视频链接或 BV 号。');
}
```

**顺序很关键**：先 `findVideoUrl()`，只有在**没找到链接**且**看起来像 id** 时才拦。
这样 `BV1xx411c7mD` 和 `https://b23.tv/abc` 仍然正常解析（已验证）。

### 3.4 `enablePack` 排序基准

```js
const order = new Map(allAllowed.map((d, i) => [d.name, i]));
```

## §4 踩到的坑

1. **`nameScore` 上限 0.8** —— 见 §2.1。整条模糊通道是死代码，而测试是绿的。
   原因：归一化路径独立工作，18 项里只有 1 项覆盖模糊路径，而那 1 项又写错了
   （见第 2 条）。
2. **测试用例本身测错了东西** —— 原本写 `suggestToolName('x', TOOLS, { score: () => 0.95 })`
   想测"过门槛就给结果"，但 `'x'` 的首 token 对不上任何工具，被硬闸先筛掉了。
   这个用例测的是**闸门**，不是**门槛**。改成 `'send_xxx'` 才测对，
   并补了一条专门测闸门的用例。
3. **Python 字符串替换把语法改坏了** —— 连续两次 `.replace()` 把模板字符串的插值
   删成了 `{  }` / `{ , minScore: 0.82 }`。
   教训：脚本化改代码后**立刻** `node --check`，别等跑测试才发现。
4. **`xargs` 被安全网拦下** ——
   `Error: BLOCKED by CC Safety Net / Reason: xargs dynamic input can supply arbitrary executable command source`。
   改用 `_tmp_*.mjs` 脚本文件再 `node` 跑。

## §6 残留问题

1. **只覆盖"名字拼错"，不覆盖"参数结构错"**。模型把 `messages` 写成字符串而不是数组
   这类问题仍然只有原始报错。下一轮可以考虑做参数 schema 的就近修正。
2. **首 token 硬闸会漏掉跨族重构**。比如模型想调 `get_message_images` 却写了
   `message_images`（首 token 变成 `message`），会被闸掉。这是**故意**的取舍：
   宁可漏提示也不误导。
3. **0.82 门槛是拍的**，没有用真实错名样本调过 —— 生产里只出现过 1 个错名样本
   （`get_ message_images`），样本量不足以调参。
4. **`watch_video` 的正则 `/^#?\d{4,20}$/` 可能误伤**。如果某个视频平台的链接
   恰好是纯数字（理论上存在，比如某些短链），会被当成消息 id 拦下。
   目前 `findVideoUrl()` 先跑，能识别出来的都不会误伤，但覆盖不全。
5. **`load_tools` 排序修复没有专门的测试**。`test/test-enable-pack-binding.mjs`
   只测了 `this` 绑定（4 项），没测排序稳定性 —— 因为它只在
   "装回工具后"才体现，需要构造多轮前缀对比才能测。
