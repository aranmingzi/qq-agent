# 阶段 1：IndexTTS-2.5 在 4GB 显卡上的可行性实测

日期：2026-10-30
涉及：`_indextts/`（隔离实验目录，未接入 `src/`）

## 一句话结论

**技术上跑通了，但速度不合格——判定 No-Go，不接进 QQagent。**

四项验收过三项：显存够（3.28GB / 4GB）、音色几乎无损（余弦 0.998）、情绪真能拉开
（F0 极差 122.9Hz）。唯一卡住的是 **RTF 5.56**——她说完一句话，你得等五倍于它的时间。

| 验收项 | 实测 | 门槛 | 结果 |
| --- | --- | --- | --- |
| 峰值显存 | 3.284 GB | < 3.6 GB | ✓ |
| 平均 RTF | **5.56** | < 1.0 | ✗ |
| 音色余弦 | 0.998 | ≥ 0.98 | ✓ |
| F0 极差 | 122.9 Hz | ≥ 100 | ✓ |

对比现在线上的 GPT-SoVITS：RTF 1.61~2.86（见 `docs/语音语气-2026-10-29.md`）。
**IndexTTS 比它慢一倍以上**，而这个"慢"是 3050 的算力问题，不是配置问题。

## 为什么值得记下来

阶段 1 的价值不在"装上了没有"，而在**四个具体数字**。它们回答了三个以后绕不开的问题：

1. **4GB 到底能不能装下这套 4GB 大小的模型？** 能，但必须半精度 + 把 w2v-bert 挪到 CPU。
2. **音色/情绪解耦是不是真的？** 是。同一段参考音频，8 维情绪向量能把 F0 从 280Hz
   拉到 403Hz，同时音色余弦稳在 0.997~0.999。
3. **值不值得为它换掉现在的引擎？** 不值得。多花一倍的等待时间，换一个"更会演情绪"，
   在 QQ 群聊这个场景里是亏的——群友等不了 20 秒。

## 怎么跑通的（4GB 的三个关键约束）

官方代码默认假设"整条管线一个精度"，直接跑必失败。为了在 4GB 上活下来，
在 `_indextts/lowmem_patch.py` 里做了三件事，每件都有实测依据：

### ① GPT 必须"上卡即半精度"

官方顺序是 `.to(device)` 再 `.bfloat16()`——先按 fp32 占满 3.04GB，再转半精度，
峰值已经吃掉。实测第一次就是死在这：`CUDA out of memory. Tried to allocate 256MiB.`
（`probe_run2.log`）。后面还有一次更难看：GPT 装进去之后加载 w2v-bert 直接
**原生崩溃 0xC0000005**，连 Python 异常都没有（`loadtest3.log`）。

解法是 hook `torch.nn.Module.to()`：搬去 cuda 的那一刻就地转半精度。GPT 从 3.04GB
降到 1.52GB。

### ② w2v-bert 必须留在 CPU

各组件半精度占用：GPT 1.52 / **w2v-bert 1.08** / codec 0.09 / s2mel 0.19 /
bigvgan 0.21 / campplus 0.03 ≈ 3.12GB。4GB 卡扣掉驱动只剩约 3.4GB，推理还要几百 MB
激活值——实测 3.44GB 就 OOM。

w2v-bert 一个人占 1.08GB，而 `get_emb()` **只在参考音频上跑一次**（`infer_v2_5.py:620`
有 `cache_spk_cond` 缓存），不是每句都跑。挪到 CPU 的代价只是"第一句多等 1~2 秒"，
换来 1GB 常驻显存。挪完加载峰值从 3.35GB 降到 **2.27GB**。

### ③ 除 GPT 外一律保持 fp32

这是踩了四次坑才认的账。本以为"全都半精度更省"，结果：

| 报错 | 位置 | 原因 |
| --- | --- | --- |
| `mat1 and mat2 must have the same dtype, got Float and Half` | `get_emb` | w2v 半精度，输入 fp32 |
| `expected scalar type Float but found Half` | 同上 | 反过来 |
| `Input type cuda.FloatTensor and weight cuda.HalfTensor` | campplus conv | DTDNN 用了 autocast 白名单外的算子 |
| `Expected weight to have type Float but got Half` | campplus | 再反过来 |
| `GET was unable to find an engine to execute this computation` | bigvgan | fp16 权重 + fp32 输入的 conv 无匹配引擎 |

根因是 `flow_matching.solve_euler` 里手工 `torch.randn()` / `torch.linspace()` 造
**fp32** 张量，autocast 管不到它们。把 s2mel / codec / bigvgan / campplus 全部留 fp32 后，
问题一次性消失——它们加起来才 1.03GB，不值得为省这 0.5GB 去趟 dtype 的雷区。

最终配置与显存：

```
GPT      bf16   cuda   1.52 GB
w2v-bert fp32   cpu    (0)
codec    fp32   cuda   0.19 GB
s2mel    fp32   cuda   0.39 GB
bigvgan  fp32   cuda   0.42 GB
campplus fp32   cuda   0.03 GB
                       ─────────
加载峰值   2.781 GB
推理峰值   3.284 GB   ← 就是这一下贴近了 4GB
```

## 实测明细

冷启动 65s（加载 + 首次编译）。三句话（发音色余弦都按同一段真人参考音频算）：

| 句子 | 音频时长 | 合成耗时 | RTF | 音色余弦 |
| --- | --- | --- | --- | --- |
| 短句 | 2.43s | 16.51s | 6.80 | 0.997 |
| 中句 | 4.14s | 20.98s | 5.06 | 0.997 |
| 长句 | 9.89s | 47.70s | 4.82 | 0.999 |

情绪向量（同一句话，只换 8 维向量）：

| 情绪 | 音频时长 | 合成耗时 | F0 中位 |
| --- | --- | --- | --- |
| 平静 | 3.27s | 17.83s | 280.1 Hz |
| 开心 | 3.67s | 19.70s | 395.9 Hz |
| 生气 | 3.70s | 20.55s | 403.0 Hz |
| 难过 | 4.19s | 21.00s | 389.5 Hz |

**F0 极差 122.9Hz**：情绪向量是真的在工作，不是摆设。而 0.997~0.999 的余弦说明
音色没有被情绪带跑——这正是 GPT-SoVITS 做不到的（它必须为每种情绪单独准备一段
"该角色用那种情绪说的话"，胡桃那 6 条就是这么造出来的）。

对比如下（GPT-SoVITS 胡桃，`bench_gsv.mjs` 同批句子）：

| | GPT-SoVITS（16 步） | GPT-SoVITS（32 步） | IndexTTS-2.5 |
| --- | --- | --- | --- |
| 平均 RTF | 1.61 | 2.86 | **5.56** |
| 峰值显存 | ~3.4 GB | ~3.4 GB | 3.28 GB |
| 情绪机制 | 换参考音频（需预造） | 同左 | 8 维向量（真解耦） |
| 冷启动 | ~30s | ~30s | 65s |

## 为什么慢（以及能不能救）

慢在 GPT 自回归解码：815M 参数、24 层，逐 token 生成语义码。3050 是 4GB 笔记本卡，
算力约 60 TFLOPS(fp16) 但显存带宽只有 192GB/s——自回归生成是**带宽受限**的，
这才是 RTF 5.5 的主因，不是"没优化好"。

能想到的路，都划不来：

- **降精度**：已经 bf16 了，再降是 fp8，3050 不支持。
- **减小分段**：`low_vram` 已经自动在 40 字处切分，不影响总时间。
- **换小模型**：IndexTTS-1.5 是 3.36GB 且 apache-2.0，但它是**老一代**，
  没有情绪/音色解耦——那还不如继续用现在的 GPT-SoVITS。
- **上 vLLM**：官方有 vLLM recipe，但那是给 A100/4090 的，4GB 卡上 vLLM 起不来。
- **加显存**：换卡就超出"在这台机器上跑"的前提了。

## 对后续的结论

**阶段 2（接入为可选引擎）不做了。** 一个 RTF 5.56 的引擎接进 QQ，
群友发一句"在吗"，要等 20 秒才听到回复——这比"语气不够丰富"严重得多。

真正值得做的，是把 IndexTTS 验证出来的**方法论**搬回现有链路：

1. **情绪/音色解耦的价值被证实了**。现在 GPT-SoVITS 的痛点是"每种情绪都要造一段
   参考音频"，纳西妲/芙宁娜/神里绫华至今各只有 1 条。既然造音频这条路已验证可行
   （胡桃 6 条，余弦 0.993~0.998），就继续用 `gen_emotions.mjs` 补齐 —— 这是当前
   唯一"零等待成本"的路。
2. **如果将来换机器**（显存 ≥ 12GB），IndexTTS-2.5 是明确优于 GPT-SoVITS 的选择：
   音色/情绪解耦、`emo_alpha` 可调强度、`duration_factor` 控时长。到那时
   `lowmem_patch.py` 里那三个约束可以只留"GPT 半精度"一条，其余都能放开。

## 隔离目录说明

`_indextts/` 是一份**完全隔离**的实验环境，没有接入 `src/`，没有改任何 QQagent 配置。
删除它就能回到原状：

```bash
rm -rf C:/QQagent/_indextts    # 释放 15.8 GB
```

保留下来的原因：里面有三个以后还会用到的东西。

| 路径 | 是什么 |
| --- | --- |
| `lowmem_patch.py` | 4GB 运行的三个约束（GPT 半精度 / w2v 挪 CPU / 其余 fp32），带完整踩坑注释 |
| `stage1_probe.py` | 四项验收探针，换机器后可以直接重跑做对比 |
| `src/checkpoints/` | 模型权重 5.2GB，重下要 20 分钟（modelscope + BigVGAN 走 hf-mirror） |
| `out/*.wav` | 7 条实测音频，可以直接听 RTF 5.56 到底是什么体感 |

## 复现命令

```bash
cd C:/QQagent/_indextts
# 环境已在 src/.venv（python 3.11 + torch 2.8.0+cu128）
USE_MODELSCOPE=true \
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True,max_split_size_mb:64 \
  ./src/.venv/Scripts/python.exe -u stage1_probe.py
```

依赖安装的两个坑（都已绕过，记下来免得重踩）：

- `uv sync` 会从 PyPI 装 `torch==2.8.0+cpu`（230MB），把 cu128 版覆盖掉。
  正确做法是单独指定 wheel URL 装 torch，其余依赖用 `--index-url 阿里云` 装。
- BigVGAN 在 modelscope 上不存在（404），必须走 `hf-mirror.com` 手动下。
  代码里 `need_proxy()` 的自动切换对 `nvidia/bigvgan_*` 无效，因为那个 repo
  压根没进 modelscope。
