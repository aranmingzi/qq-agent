## 三、最关键的三个改动（上线前必须知道）

### 3.1 每一条出站消息发送前都要过一次许可复核

```js
// orchestrator.gateBeforeSend(chatKey) —— 每次发送前重判**现值**
if (this.paused)          → 否决（kind: paused）
if (this.overBudget())    → 否决（kind: budget）
if (!allowed(kind,id,getConfig())) → 否决（kind: whitelist）
```

- 接线在 `app.js` 的 `SendQueue` 构造处，用**延迟引用**（`sendGateRef`）递进去 ——
  sender 必须先于 orchestrator 构造，两边因此不必互相 import。
- 六条出口全部覆盖：文字批次 / 文件 / 图片 / 表情 / 语音 / 拍一拍。
- 排在 `#checkRate` **之前**：被拦下的消息不占限额（否则被拦几次就哑了）。
- 复核自己抛错 → **放行**（兜底的 bug 不该让机器人变哑）。
- 总闸：**`config.send.recheckBeforeSend`**（默认 `true`，关掉 = 回到老行为）。

⚠️ 行为变化：以前**只入站判白名单**，所以主动发言/定时汇报/唱歌交付这些
"入站之后发起"的路径从不复核。现在它们也会被拦。若某个会话被移出白名单，
正在进行的那一轮会**发到一半停下**（已发出的不追回，未发的记 skip 并报错）。

### 3.2 OneBot 回包：传输成功与业务成功是两个字段

以前是 `if (body.status !== 'ok' && body.retcode !== 0)` ——
AND 连的是两个"失败"条件，于是 **`retcode=0 + status=failed` 会被判成成功**，
表现为"以为发出去了其实没有"。现在改成 AND 连两个"成功"条件的否定：

```js
let businessOk = true;
if (sawStatus && status !== 'ok' && status !== 'success') businessOk = false;
if (sawRetcode && retcode !== 0) businessOk = false;
```

判定产出 `kind` 三态，直接决定"能不能重发"：

| kind | 含义 | `classifySendFailure` | 处理 |
|---|---|---|---|
| `transport` | HTTP 不通 / 接口不存在 | `failed` | 可重试 |
| `business` | 请求被处理但没做成（含 retcode=0+status=failed） | `failed` | 看 retcode 再决定 |
| `no-body` | 传输通但响应体读不出 | `unknown` | **落台账、不重发** |

`kind` 直接进 `error.result`，`send-ledger.js` 据此判定，**不再靠正则猜文案**。

### 3.3 跳过记录：90% 的时间在"决定不说话"，现在全都留痕

`src/skip-log.js` 的 17 个 stage 枚举**全部有接线**（有测试钉着，加空转枚举会红）。
新增的几条：

- `send-gate` 被发送前复核拦下（3.1）
- `send-fail` 确定失败（3.2 的 `failed` 那两档；`unknown` 走台账不混进来）
- `identity` 身份切换流程直接处理，未进模型
- `directive` 点歌台指令由代码直接处理，未进模型
- `budget-retry` 输出被思考占满（与 `model-silent` **必须分开**：一个能靠调大 `maxOutputTokens` 修好，一个不能）

新 API：`GET /api/skips?limit=50&since=<毫秒>`，返回 `{ items, stats }`。

## 四、未读消费模型（P1-4）

`drainUnread(chatKey)` 语义不变，实现改成**先取快照、再按 id 消费**：

```js
noteUnread(chatKey)              // 只读，不消费（判定可反复看同一批）
consume(chatKey, ids)            // 单点消费，返回实际消费条数
drainUnread(chatKey)             // = noteUnread + consume
```

- 结构上**不提供** `markAllRead` / `clearUnread`（有测试钉着：写了会红）。
  理由：那种 API 一旦存在，早晚会有人在"顺手清理一下"的地方调它，
  而它的失败方式是**静默的** —— 消息没了，没人知道它们从没被看过。
- 直接收益：快照与消费之间新到的消息**必然留下**，
  修掉"它明明在线却没回我那句"这类最难复现的丢消息。

## 五、P2-8 为什么没做（不是忘了）

程序/数据分离 + 连续启动失败自动回滚，需要先把 `C:\QQagent` 的目录布局推翻重来
（`versions/<ver>` + `current.json` 指针 + `runtime/node.previous`）。它是**结构性搬迁**，
判据（`FAILURE_THRESHOLD=2`、30s 内死算失败、一次健康启动清零）好抄，
但布局改动会牵动 Electron 打包、便携包、控制台路径解析三处，
不适合和本批行为改动一起上线。**建议单独排期，先做 `runtime-state` 那半个（只加失败计数）。**

## 八、留下的话

这套源码最值钱的不是某个功能，是三条纪律，落地时一条条照着做了：

1. **判据住零依赖叶子，接线只有一处** —— 本批 6 个新文件 5 个是叶子，
   白名单抽出 `whitelist.js` 就是因为"入站能判、出站判不了"。
2. **失败方向按职责声明，别抄一句"失败一律放行"** ——
   出口闸门 fail-closed、发送前复核出错 fail-open、回包无响应体单列 `no-body`。
3. **静默必须留痕** —— 每一次"没说话""没发出""被拦下"都有一条可查的记录，
   且**分开记**：`model-silent` 与 `budget-retry`、`send-fail` 与台账，混成一类就查不动。
