## 2. 借鉴来源

- **`chauko0423/ohwhale-deploy`**（MIT，实测在 QQ 9.9.35 上跑通）—— 整个思路的来源。
  它是 WASAPI 环回 + VB-Cable + pywinauto 的 Python 实现，本仓库换成
  Electron loopback + 纯 PowerShell UIA，去掉 Python 依赖。
  - 抄了它的参数：静音 900ms（注释原话「0.55 太急，一句话中间换气就被截断」）、
    预录 450ms、打断倍率 3.0（「2.0 时环境噪音就误触发」）。
  - 抄了它的两个教训：① 只在标题含「通话」的窗口里找按钮（全树扫一轮 >20 秒会错过来电）；
    ② 接听正则 `接听|接受|接起`，挂断正则 `挂断|拒绝|关闭`（后者**永远不能**被当成接听）。
  - **没抄**它的视频方案：`docs/07_发布状态.md` 自己写了视频不通过 ——
    CameraEmulator DLL 单独跑能读 150 帧，QQ 里还是显示物理摄像头。
- **Pipecat 的 frame-processor 分层** —— 手/耳朵/嘴各是一个可替换环节，不是一个巨型函数。
- **PowerShell 调用纪律**来自本仓库 `src/napcat-process.js:206`：
  以 stdout 能否解析成 JSON 为准，不拿 exit code 当判据（PowerShell 的 exit code 语义很松，
  非终止错误和中文编码问题都会让它非 0）；`$matched = @()` 用普通数组，
  因为 PowerShell 5.1 解析不了"元素是 object 的泛型 List"，一写就整段 exit 1 且没有任何 stderr。

## 4. 残留问题

1. ~~**本机没装虚拟声卡**~~ → **已解决（2026-10-29 晚）**：VB-Cable 装好并验过签名驱动包，
   `src/audio-devices.js` 已认出播放端「扬声器 (VB-Audio Virtual Cable)」和录音端
   「CABLE Output (VB-Audio Virtual Cable)」。用 1 kHz 正弦波注入验证环回：
   注入幅度 12000，从 CABLE Output 录回来的峰值 12001 —— 链路是真的通的，不是"枚举到了"。
   **仍未验证的是"对方真的听到"**：那需要一通真实 QQ 来电，本机没有第二台设备打进来。
2. **没在真实来电上验证过接听**。探测时机器上没有通话窗口，
   所以「接听」按钮的真实无障碍名称是从 ohwhale 的正则推出来的，不是本机实测的。
   面板上的「干跑一次扫描」就是为这个准备的 —— 有来电时先看一眼。
   这也是为什么默认 `enabled: false`。
3. **本机 QQ 是 9.9.33.52230**，ohwhale 实测的是 9.9.35.52892。版本差异可能影响元素树结构。
4. **视频没做**，理由见上（原作者自己也没通过）。
5. **loopback 采集只支持 Windows**，且必须在 Electron 里 —— 纯浏览器打开控制台拿不到系统声音。
6. **单通话、无并发保护**：同时来两通电话时只会接一通，另一通不管。
7. **打断阈值没在本机调过**：3.0 倍是照搬 ohwhale 的 WASAPI 链路的经验值，
   本机用 Electron loopback 后噪声底可能不同，`config.call.bargeInRatio` 要按实际情况再调。

## 5. 踩过的坑

- **`finally { process.exit(0) }` 会吞掉断言异常**。`test-call-smoke.mjs` 第一版就是：
  `app.start({ port })` 忽略了参数（start 不接受参数，端口来自配置），
  fetch 全打到默认 3210，断言全抛，但 `finally` 的 `exit(0)` 让脚本"通过"。
  改成 `catch` 里 `exit(1)`、正常路径末尾 `exit(0)` 之后才真正开始跑。
- **`app.start()` 不接参数**，端口必须写进临时 `config.json` 的 `server.port` 再导入 app。
- **`/api/voice/status` 里少声明一个 `ccfg`** → `ReferenceError` → 裸 500，日志里什么都没有，
  只有测试报「期望 200 实际 500」。加变量时要在用到它的那个分支里声明。
- **`edit` 工具偶尔吃掉换行**，把两行拼成一行（`const result = listAudioDevices();        return json(...)`）。
  语法合法但可读性毁了，且 `tsc`/`node --check` 都不报。每次 edit 后读回来确认。
- **固定长度的源码窗口会让正确的改动变红**：`test/test-restart.mjs` 用 `slice(i, i + 900)` 找
  `closeAllConnections`，给 `stop()` 加两行注释就把它挤出窗口。改成按函数边界切。

## 6. 后续补丁：误点防护（同日晚，实测发现）

装好 VB-Cable 之后跑全套测试，`test/test-call-status.mjs` 里一条断言变红：

```
✗ probe 能指定 windowPattern（QQ 改版时不用改配置先试）
    QQ 主窗口里没有接听按钮：期望 "none"，实际 "answer"
```

追下去是**真的会误点**，不是测试写错了。`windowPattern: 'QQ'` 扫到的窗口列表里包含
DSH 自己的窗口「QQagent — DeepSeek Harness」，而那个窗口里有个按钮叫：

> 打开计划：QQ 通话三步落地计划（自动接听 → 环回耳朵 → 虚拟声卡嘴）

按钮名里含「接听」两个字，旧逻辑只看 `answerPattern` 是否命中，于是判成"来电，接语音"，
准备去 `Invoke` 它 —— 点下去会打开一个计划面板，而真正的来电还在响。

修法是给"像不像接听动作"加三道闸（`src/qq-call-answer.js` 的 `looksLikeCallButton`）：

| 闸 | 规则 | 拦的是哪种误判 |
|---|---|---|
| 长度 | `> CALL_BUTTON_MAX_CHARS`（16） | 带说明文字的长标题按钮 |
| 冒号 | 含 `：` 或 `:` | 「打开计划：…」「说明：…」这类标题式按钮 |
| 黑名单 | 含 `设置/自动/开关/说明/计划/教程/帮助` | 「自动接听」「设置接听」这类开关项 |

真按钮都很短：`接听`(2) / `接受`(2) / `接起`(2) / `视频接听`(4)。

被拦下的按钮不静默丢弃，而是进 `skipped` 数组，一路带到
`/api/call/status` 的 `watcher.lastSkipped` 和面板上的一行橙色提示。
理由是：只报"没有来电"的话，用户会以为扫描坏了，永远不知道其实扫到了东西。

**测试写法的教训**：三条闸对长标题按钮是**冗余**的（它同时超长、带冒号、命中黑名单），
所以只测它的话，删掉任意单条闸门测试仍然是绿的 —— 那是假通过。
补了一组"只踩一条闸"的隔离用例（`接听电话并把这个通话转给另一个人处理` 只超长、
`接听：语音` 只带冒号、`自动接听` 只命中黑名单），三条闸各自变异后都能变红。

顺带修的两处：

- `pickOutputDevice` 里 16 通道变体（`CABLE In 16 Ch`）现在排在普通端点后面 ——
  两个都是虚拟声卡，但 16 通道那条会给 TTS 上混，而且用户按名字分不清。
  另外 Chromium 在 Windows 上给的 label 是**端点友好名**「扬声器 (VB-Audio Virtual Cable)」，
  里面根本没有 "CABLE Input" 字样，所以 hint 命不中是常态，
  原来那句"没找到名字含 X 的设备"会让人以为坏了，改成"按内置规则认出来的"。
- 面板上加了一行「最近一次判断」，直接显示 `watcher.lastReason`。
