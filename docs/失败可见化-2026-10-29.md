## 1. 原来错在哪

`src/orchestrator.js` 的 `wake()` 里，`#runAgent` 抛异常后只做三件事：

```js
} catch (error) {
  session.error = String(error?.message ?? error);
  this.sessions.finish(session.id, 'error');
  console.error(`[orchestrator] 运行 ${session.id} 出错:`, error);
}
```

于是**同一个现象有两种完全不同的成因，用户端看起来一模一样**：

| 真实原因 | 用户看到 | 面板看到 |
|---|---|---|
| 她判断这条不值得接（`model-silent`） | 没说话 | 有一条 skip 记录 |
| 模型端点挂了 / 欠费 / 超时 | **没说话** | **什么都没有** |

第二种情况下：
- 用户不知道是"她不想理我"还是"系统坏了"，只能反复 @ 她；
- 主人（部署者）只能靠翻 `console.error` 的滚动日志，而 Electron 打包后那行输出根本不在眼前；
- 最糟的是欠费：她会**永久**沉默，没有任何提示指向"该充值了"。

这不是文案问题，是**可观测性缺口**。AstrBot 用 `persona_error_reply` 补的正是这一块，
MaiBot 那侧则更狠 —— 它对"运营类失败"和"用户侧失败"用了两套完全不同的出口。

## 2. 现在的行为

### 2.1 分类（`classifyLlmError`）

判据顺序即优先级，注释写在 `src/error-reply.js:67-78`：

| kind | 触发 | 归属 | 可重试 |
|---|---|---|---|
| `context` | 上下文超长（与 `orchestrator.js:2795 isContextOverflowError` **同序同判据**） | operator | 否 |
| `quota` | 402 / 余额不足 / insufficient_quota | operator | 否 |
| `auth` | 401 / 403 / 密钥 / 令牌 | operator | 否 |
| `rate-limit` | 429 / too many requests / 限流 | transient | 是 |
| `timeout` | 超时 / timed out | transient | 是 |
| `network` | ECONNREFUSED / fetch failed / DNS | transient | 是 |
| `server` | 5xx / 无法解析的 JSON / 缺少 choices | transient | 是 |
| `bad-request` | 400 / 422 / 404（且不是 context） | operator | 否 |
| `unknown` | 认不出来 | operator（**保守**） | 是 |

`unknown` 刻意归 operator：认不出来的时候宁可少说，也不要对着群友编一个"网抽风了"。

### 2.2 决策（`decideErrorReply`）

按顺序短路，每条拒绝理由都会写进 skip-log 的 `reason`：

1. `enabled === false` → 全闭嘴（回退开关）
2. `sentAny`（这一轮已经发过话）→ 不说。已经回了就别补道歉，那会让前面那句显得可疑
3. `proactive`（主动机会失败）→ 不说。没人问，不自曝
4. `!direct`（不是在叫它）→ 不说
5. **冷却期内** → 不说（`cooldownMs`，默认 10 分钟，**按会话**计）
6. 运营类（quota/auth/bad-request/context）→ 只有 `isMaster && 私聊 && operatorNotice` 才发，scope = `operator`
7. 瞬时类 → scope = `user`；群里要求 `inGroup !== false`

冷却按**会话**而不是全局：一个群挂在一个坏端点上，不该让另一个群也跟着闭嘴。
冷却戳只在**内存**里：重启后多提示一次无害，落盘要多一个文件、多一种损坏可能。

### 2.3 文案

**用户端**（`DEFAULT_USER_LINES`）—— 短、不解释、不给技术词：

```
timeout    : 刚卡了一下，你再说一遍？ / 等我一下，刚才慢了半拍
network    : 刚断了一下，我回来了 / 网抽风了，你说到哪儿了
rate-limit : 我这边被限速了，缓一下 / 消息太密，我慢半拍
server     : 刚才那边抖了一下，再试一次？ / 我这边出了点岔子，你刚说什么
unknown    : 刚才没接住，你再说一遍？
```

每类**至少两句**随机取 —— 连着两次一模一样，比沉默更像机器人。
`config.errorReply.lines` 可以覆盖任意一类；覆盖成 `[]` 表示**这一类闭嘴**（区分"没配"和"配成空"）。

**运营端** —— 带 `【模型失败】` 前缀，一眼能认出不是她说的：

```
【模型失败】小鲸鱼这一轮没有回复：账户欠费或余额不足。原始错误：模型 API HTTP 402：…（截 200 字）
```

不加 `【】` 的话这句会混进聊天流，被当成她真的回了话。

### 2.4 落账

新增 `SKIP_STAGES.RUN_ERROR = 'run-error'`，每轮失败都记一条（**包括因为冷却没发的那次**）：

```json
{"stage":"run-error","reason":"服务端出错；未提示：提示冷却中（还剩 599s，避免一个坏端点刷屏）",
 "detail":{"kind":"server","owner":"transient","retryable":true,"sent":0,"error":"模型 API HTTP 500：…"}}
```

`notified` 字段只在真发了的时候出现（`user` / `operator`），没发的原因在 `reason` 里。

## 3. 三个踩过的坑

### 3.1 重复写历史

第一版在 `#notifyRunError` 里自己调了 `store.appendSelf`，**但 `sender.sendTextBatch`
内部已经写了**（`src/sender.js:471`）。结果是同一句话在历史里出现两条，
下一轮提示词里她看到自己重复说了两遍。现在只发不写，落库交给 sender。

### 3.2 上下文判据两处不一致

`orchestrator.js:2798` 能认出 `Input length must be less than 8192`，
而 `error-reply.js` 只写了 `input is too long`。同一句报错，上面判"可裁剪重试"、
下面判"参数错误"——自相矛盾。**修法不是"两边各补一遍"，而是把正则收敛到一处**：`CONTEXT_RE` 只定义在
`src/error-reply.js:73` 并由 `orchestrator.js` import 复用，物理上不可能再漂。
`test/test-error-reply.mjs` 里加了一条双向护栏（5 个"该认出来"+2 个"不该误判"），
并且**故意注入错误验证过它真的会红**（EXIT=1）—— 这条很关键，见 §3.4。

### 3.3 用"连不上"造错测不出东西

E2E 里第一版把 `baseUrl` 指向 `127.0.0.1:1`，以为会 `ECONNREFUSED`。
实际上 undici 把 1/7/9 列为 **unsafe port**，先抛 `bad port`，于是分类落到 `unknown`。
现在改成起一个真 HTTP server，用状态码精确控制（500 / 402 / 200）。

### 3.4 async 用例在同步 helper 里会静默假通过

新加的那条护栏是 `async`（要 `await import` orchestrator），但测试文件的
`ok(name, fn)` 当时是同步的：`fn()` 返回的 Promise 被直接丢掉，里面 assert 失败
只会变成 unhandled rejection —— 屏幕上照样打 `✓`，护栏等于没有。

改成 `async function ok(name, fn) { await fn(); … }`，并把 26 处调用都 `await`。
然后**故意把断言改成错的值跑一遍**，确认 EXIT=1 才算数：
一个从没红过的测试，和一个不存在的测试没有区别。

## 5. 残留问题

1. **没有面板入口**。`/api/skips` 接口早就有，但 console 前端还没做 skip 列表页，
   所以 `run-error` 记录目前只能用接口或日志看。这是下一个该补的洞。
2. **冷却不跨重启**。重启后 10 分钟内可能再提示一次。可接受，但如果是"端点长期坏 + 频繁重启"
   会显得絮叨。
3. **`retryable` 目前只写进 detail，没有被消费**。设计意图是给"自动重试一次"用，
   但重试策略还没做 —— 现在失败就是失败，不会自己再试。
4. **没做"降级到 fallback 模型后再失败"的区分**。`model-fallback.js` 换过模型仍然失败时，
   现在的文案不会告诉主人"已经试过备用模型了"。
