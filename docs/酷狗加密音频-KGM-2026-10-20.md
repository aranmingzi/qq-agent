# 群友发的是酷狗加密的歌（KGM），唱不了 —— 已自动解密

> **2026-10-21 更新**：本文写的「只能解前 64 MiB / 前 3 分钟」已经过时。
> 新版改用 table1/table2 位移递推算 mask（不再依赖 4 MiB 的 `kgm.mask` 表），
> **整首歌都能解开**，实测 81 MB / 3:37 的 96 kHz flac 全曲零错误。
> 细节见 `docs/音频格式兼容-2026-10-21.md`，代码见 `src/kgm.js`。
> 下面关于密文结构、魔数判断、怎么救历史文件的部分仍然有效。

2026-10-20。现场：私聊发了一首 `侧脸.kgm.flac`（81 MB），点歌直接失败。

## 症状长什么样

`data/jobs.jsonl` 里是这样一条：

```
"key": "cover|81206770_...|0|60|侧脸|dry"
"status": "failed", "progress": 5,
"error": "路线 A 失败（退出码 1）：RuntimeError: ffmpeg 解码失败（侧脸.flac）：
          Output file #0 does not contain any stream"
```

两个容易误判的点：

1. **不是下载失败**。作业键里的 `81206770` 就是文件字节数，和本地
   `songs/raw/侧脸.flac` 一模一样 —— 文件是完整的，只是内容不是音频。
2. **不是 ffmpeg 装错了**。`Output file #0 does not contain any stream` 的意思是
   「这个输入里一帧音频都没有」，因为它是密文。

判断方法（一行）：

```
od -An -tx1 -N 16 "songs/raw/xxx.flac"
```

- 正常 flac：`66 4c 61 43`（`fLaC`）
- **KGM**：`7c d5 32 eb 86 02 7f 4b a8 af a6 8e 0f ff 99 14`
- VPR：`05 28 bc 96 e9 e4 5a 43 91 aa bd d0 7a f5 36 31`

扩展名完全不可信 —— 酷狗下载下来是 `侧脸.kgm.flac`，群友转发时只保留了最后的 `.flac`。

## 怎么修的

新增 `src/kgm.js`（算法来自 unlock-music，MIT）：

| 函数 | 作用 |
|---|---|
| `isKgm(buf)` / `isKgmFile(file)` | 只认 16 字节魔数；文件版只读前 16 字节，不把 80 MB 密文吞进内存 |
| `decryptKgmSync(buf, mask)` | 逐字节解密，得到明文 flac |
| `decryptKgmToAudio(buf, {stem, dir})` | 解密 + 转码成 44.1k 立体声 wav，返回时长/是否被截断 |

解密算法（每个字节）：

```
med8 = key[i % 17] ^ raw[i]
med8 ^= (med8 & 0xf) << 4
msk8 = predef[i % 272] ^ mask[i >> 4]
msk8 ^= (msk8 & 0xf) << 4
out[i] = med8 ^ msk8
```

- `key`：从文件 `0x1c` 起取 16 字节，第 17 字节恒为 0
- `headerLen`：`readUInt32LE(0x10)`（这首是 `0x400`），音频数据从该偏移开始
- `mask`：一张 4 MiB 的静态表，首次使用自动下到 `data/kgm.mask`

接入点两处：

- `tools.js::saveIncomingSong` —— 群友发来 → 入库前解密，落 `${歌名}.wav`
- `cover-song.js::coverSong` —— 曲库里已经躺着密文时兜底，解密后把 wav 路径交给 `route_a.py`

## 必须知道的硬边界

mask 表只有 4 MiB，索引是 `i >> 4`，**只覆盖前 64 MiB 密文**。

- 81 MB / 217.85 秒的歌，只能解出**前 177.7 秒**（丢最后 40 秒）。
- 翻唱默认 60 秒、语音交付最长 165 秒，所以实际使用**不受影响**。

解完之后为什么一定要过一遍 ffmpeg 而不是直接存 flac？
因为 STREAMINFO 里写着 217 秒，实际数据只有 178 秒，直接落盘会让 Demucs/RVC
解到一半炸掉。用 `-err_detect ignore_err` 容错解码，它会一路解到干净边界为止，
输出一个时长正确的 wav。**不加这个开关的话，ffmpeg 在第一个坏帧就中断，只能拿到碎片。**

试过、但**都不对**的超界处理（别再试了）：

- mask 索引取模续上 → `invalid subframe padding`
- 超界部分不加 mask → `invalid rice order`
- 每 64 MiB 重置 key 相位 → `invalid coding type`
- 按 0x4000 块重置 → 同上

超界那部分是酷狗另一种封装（头部 `0x14=3` 的 v5 风格），要真正解开得逆向客户端取 AES key，
不值得。要完整歌就让群友发未加密的 flac/mp3。

## 自检与验证

- `node test/test-kgm.mjs` —— 8 项（魔数识别、普通音频不误判、`isKgmFile` 读盘、
  加密→解密往返、异常 headerLen 给可读报错），已挂进 `npm test`
- 真实样本：`侧脸.kgm.flac` 解密 3.6 秒 → 177.7 秒 wav，`ffmpeg -f null -` 解码零报错
- 整链路：`coverSong({src:'songs/raw/侧脸.wav', dur:10, dry:true})` 98.4 秒出成品

## 历史文件怎么救

曲库里已经存在的密文不用删，两种都行：

1. 直接点这首歌 —— `coverSong` 会就地解密（每次重新解一次，比较慢）
2. 手动换掉（推荐）：

```bash
node -e "
import('./src/kgm.js').then(async (m) => {
  const fs = require('fs');
  const buf = fs.readFileSync('songs/raw/<歌名>.flac');
  await m.decryptKgmToAudio(buf, { stem: '<歌名>', dir: 'songs/raw', log: console.log });
  fs.renameSync('songs/raw/<歌名>.flac', 'songs/raw/<歌名>.kgm.bak');
})"
```

`.bak` 不在 `SONG_EXTS` 里，不会参与曲库匹配。
