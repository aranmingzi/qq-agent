# 点歌台：B站缓存 → 结构化歌单 → QQ 群点播

> 实现文件：`src/bilibili-cache.js`、`src/playlist.js`、`src/playback.js`、`src/playlist-commands.js`、`src/media-tools.js`
> 自检：`node test/test-playlist.mjs`　重建：`node tools/build-playlist.mjs`
> 控制台接口：`GET /api/playlist`、`POST /api/playlist/rebuild`

## 0. 一句话

把 `Videos\bilibili` 下的缓存（含带私有头的 `.m4s`）扫成一份 `library.json`，群友发 `#点歌 青花瓷`
（或 `#点歌 15`、`#随机`）时，机器人把对应音频转成带封面的 mp3 直接发进群。

**它和「唱歌」是两条完全独立的链路：**

| | 点歌台（本文） | 唱歌链路（旧） |
|---|---|---|
| 做什么 | 播放缓存里的**原曲** | 用胡桃/纳西妲音色**翻唱** |
| 触发 | `#点歌 歌名`、`#随机`（确定性指令） | `唱XX`、`sing_lyrics` 工具 |
| 音源 | B站缓存原音频 | `songs/raw` + RVC / DiffSinger |
| 耗时 | 命中缓存 <1s，首次转码 3~6s | 30 秒~3 分钟（GPU 队列） |
| 输出 | 带封面的 mp3 文件 | 语音条 / wav 成品 |

两条链路互不影响：点歌台不会碰 `songs/`，唱歌也不会读 `data/playlist/`。

---

## 1. 目录与产物

```
data/playlist/
  library.json     扫描生成的歌单（唯一真实来源，可随时重建，不要手改）
  overrides.json   人工修正：标题/歌手/别名/标签/隐藏（重建后依然生效，可选创建）
  stats.json       点播次数、最近点播（与 library 分开存，重建不丢）
  audio/           交付用 mp3（<trackId>.mp3 + 同名 .json 缓存签名）
  voice/           语音条试听片段（<trackId>.<秒>s.wav）
  tmp/             去私有头后的干净副本（按 路径+大小+mtime+偏移 做键）
```

`library.json` 可以删：下一次 `#点歌` 或 `POST /api/playlist/rebuild` 会重新生成。
`stats.json` 建议保留。

## 2. 歌单格式（library.json）

```jsonc
{
  "version": 1,
  "name": "点歌台",
  "generatedAt": "2026-10-19T10:41:11.082Z",
  "buildMs": 154,
  "roots": ["C:\\Users\\<用户名>\\Videos\\bilibili"],
  "errors": [],
  "stats": { "total": 25, "playable": 23, "collections": 2, "artists": 7, "durationSec": 4281 },
  "playlists": [
    { "id": "all", "name": "全部歌曲", "trackIds": ["bili-1197237911", "..."] },
    { "id": "artist:纳西妲", "name": "纳西妲", "trackIds": ["...", "..."] }
  ],
  "tracks": [
    {
      "id": "bili-1360626540",          // 稳定 ID：bili-<缓存目录名>
      "no": 15,                          // 序号（#点歌 15 用；重建后会重排）
      "title": "轻涟",                   // 清洗后的歌名
      "artist": "纳西妲",                // 歌手（尽量从标题/系列名推断）
      "album": "AI纳西妲",               // 系列/企划
      "rawTitle": "【AI纳西妲】《轻涟》", // B站原始标题，检索也参与打分
      "aliases": ["AI纳西妲轻涟", "纳西妲轻涟"],
      "tags": ["AI翻唱", "AI纳西妲"],
      "kind": "song",                    // song | clip | collection
      "duration": 144,                   // 秒（来自 .videoInfo，缺失时 ffprobe 补）
      "source": {
        "platform": "bilibili",
        "bvid": "BV1rQ4y137Tt", "cid": "1360626540", "aid": 707015506, "page": 12,
        "url": "https://www.bilibili.com/video/BV1rQ4y137Tt"
      },
      "audio": {
        "path": "C:\\Users\\<用户名>\\Videos\\bilibili\\1360626540\\1360626540-1-30280.m4s",
        "name": "1360626540-1-30280.m4s",
        "size": 1918741, "ext": ".m4s", "qn": 30280, "muxed": false
      },
      "cover": "C:\\...\\image.jpg",
      "cacheDir": "C:\\...\\1360626540",
      "format": "pc",                    // pc | android | plain
      "status": "ok",                    // ok | incomplete | no-audio
      "addedAt": "2026-10-19T10:16:08.689Z",
      "updatedAt": "2026-10-19T10:41:11.070Z",
      "plays": 0,
      "lastPlayedAt": ""
    }
  ]
}
```

设计要点：

- **`tracks` 是扁平列表**，序号/分页/检索都在这一层完成；`playlists` 只是按歌手聚合的视图（≥2 首才建组），方便以后做「按歌手选歌」。
- **`kind` 决定能不能默认点播**：`collection`（合集、语音包、干声、>15 分钟）不进默认列表，只能用序号点播；`clip` 是片段（74s 这类），照常可点。
- **`id` 稳定**，所以 `stats.json`、`overrides.json`、转码缓存都以它为键；缓存目录被 B站重下也不会丢统计。

### 人工修正（overrides.json）

`library.json` 是生成物，任何手改都会在下次重建时丢失。要改就写 `data/playlist/overrides.json`：

```json
{
  "bili-1360626540": {
    "title": "轻涟（纳西妲版）",
    "artist": "纳西妲",
    "aliases": ["轻链", "qinglian"],
    "tags": ["原神"],
    "hidden": false
  }
}
```

`hidden: true` 会让它从歌单和检索里消失（缓存目录仍保留）。

## 3. 标题清洗与分类规则

B站标题不是元数据，是一句宣传语。`parseTitle()` 按信息量取：

1. 「」里的中文 → 歌名（`《崩坏：星穹铁道》EP：「使一颗心免于哀伤」` → `使一颗心免于哀伤`）
2. 否则取《》里的内容（`【AI纳西妲】《青花瓷》纳西妲一直在等你！` → `青花瓷`）
3. 都没有则去掉【】、按 `|`/`｜` 切段，再按 ` - ` 拆「歌名 - 歌手」；`知更鸟-在银河中孤独摇摆` 这种无空格连字符也能拆
4. 统一清掉：`完整版 / 片段 / 高音质 / 无损 / Hi-Res / 动态歌词 / 官方MV / 4K / B站最强AI调音 / 百万级录音棚试听`

歌手优先级：书名号前的署名（`胡桃《…》`）→ 书名号后 ≤4 字的署名（`《妈妈的话》纳西妲`）→ 【】里的系列名（去掉 `AI` 前缀）→ UP主。
`Hi-Res无损`、`⭐轮播合集`、`《崩坏：星穹铁道》音乐` 这类栏目/企划名会被过滤掉，不会变成歌手。

分类（`kind`）：

| 判定 | kind | 默认进歌单 |
|---|---|---|
| 标题含 合集/大全/串烧/语音包/干声/纯人声，或时长 ≥ 900s | `collection` | ❌（序号可点） |
| 标题含「片段」，或时长 < 70s | `clip` | ✅（列表标「片段」） |
| 其它 | `song` | ✅ |

## 4. 点播触发方式

### 4.1 确定性指令（不进模型）

在 `app.js` 的 `ingestMessage()` 里，消息入库后立刻交给 `handlePlaylistCommand()`；
命中就自己发消息并 `return`，**不触发 LLM**。点播要的是「立刻、稳定、可预期」，不能靠模型猜意图。

| 指令 | 作用 |
|---|---|
| `#点歌 青花瓷` / `点歌 青花瓷` / `点歌青花瓷` | 检索并播放（`#`/`!`/`！` 前缀可选） |
| `#点歌 15` | 按序号播放 |
| `#点歌 BV1cX4y1Y7BF` | 按 BV 号播放（也认整条 B站链接，大小写随意） |
| `#点歌` | 显示第 1 页歌单 + 用法（不触发冷却） |
| `#歌单` / `#歌单 2` / `#歌单 纳西妲` | 分页 / 按关键词筛选 |
| `#搜歌 关键词` | 只列候选，不播放 |
| `#随机` / `#随机点歌` | 随机一首 |
| `#重扫歌单` | 重新扫描缓存（仅主人 `persona.masterQQ`） |
| `#点歌帮助` | 用法说明 |

**前缀规则**：带 `#`/`!`/`！` 一定认；裸词只放行 `点歌 / 点播` 且后面必须带内容，
`#放歌`、`#来一首` 也必须带前缀 —— 这样「放歌了」「来一首？」不会被误判成指令。

**刻意不拦截**：`点歌`（单独两个字）、`歌单`、`随机`、`点歌姬好可爱`、`放首歌听听` —— 继续交给模型闲聊。

**防刷屏**：同一人同会话 `cooldownSec`（默认 5s）冷却；同会话音频串行发送，等待超过 3 首拒绝。

### 4.2 自然语言（工具）

模型工具 `play_song(keyword, random?, asVoice?)` 与指令共用同一套检索/交付。
群友说「放首青花瓷听听」「随便来一首」时由模型调用；匹配不唯一时工具返回候选，
模型只负责把序号念给群友，不替人做选择。

**粘链接怎么办**：群友常直接甩一条 B站链接过来。`resolvePlayQuery` 会先用 `extractBvid()`
把 `BV[0-9A-Za-z]{10}` 抠出来（整条 URL、带 `?p=1`、大小写混写都认），按 `source.bvid`
精确匹配 —— 命中就播原曲，不参与模糊打分，避免「链接近似度」把别的歌播出来。
没缓存则返回 `reason: 'notCached'`，工具会明确告诉模型「这首还没缓存，别假装在准备」，
系统提示也写死了这条，防止它空口答应「去调音」然后没有下文。
注意：只有**明确说要翻唱**才走 `sing_lyrics` / `sing_cover`（唱歌链路本身不支持 B站链接）。

## 5. 检索算法

`resolvePlayQuery()` 的判定顺序：

1. **序号**：纯数字 → `no` 精确命中。
2. **随机**：`随机/随便` → 在可播放曲目里均匀抽一首。
3. **打分**：对每首歌取以下字段的最大值
   - `title` ×1.0、`aliases` ×0.95、`rawTitle` ×0.9、`artist` ×0.86、`album` ×0.72、`tags` ×0.66
   - 相似度用 `song-router.js` 的 `nameScore()`：归一化后「完全相等 → 包含 → bigram Dice」
   - 归一化后互相包含 → 至少 0.93（中文短查询「青花瓷」不至于被别的歌压过）
   - `collection` ×0.7（避免「点歌 胡桃」把 30 分钟语音包排前面）、`clip` ×0.98
   - 点播热度最多 +0.04
4. **判定**：`top ≥ 0.97` 或 `top ≥ 0.88 且领先第二名 ≥ 0.07` → 直接播；
   否则返回前 5 个候选，提示 `#点歌 序号`。
5. **合集保护**：只有「用户确实在说这个合集」（标题完全相等，或 ≥4 字且覆盖标题 40% 以上）才提示
   「这是合集，用 #点歌 <序号> 确认」，绝不自动发半小时音频。

例：`青花瓷`→精确命中；`纳西妲`→多候选（16 首）；`胡桃翻唱大合集`→合集提示；`胡桃`→候选歌曲。

## 6. 播放流程（点播一次发生了什么）

```
#点歌 青花瓷
  ├─ 解析指令 → 需要歌单？ensureLibrary()（缺失/过期 30min 才重扫，否则直接读缓存）
  ├─ resolvePlayQuery → track
  ├─ 命中缓存？isAudioCached(track)  ── 否 → 回一句「首次点播要转码，约几秒」
  ├─ ensureMp3(track)
  │    ├─ cleanedSource()：检测 ftyp 偏移，跳过 9 字节私有头（副本落在 tmp/）
  │    ├─ ffmpeg：-vn -map 0:a:0 -c:a libmp3lame -b:a 192k -ar 44100 -ac 2
  │    │           + ID3(title/artist/album/comment=BV号)
  │    ├─ attachCover()：jpg → attached_pic 写进 ID3（失败不影响音频）
  │    └─ 写 <id>.mp3 + 签名 json（源路径/大小/mtime/码率，源变了自动失效）
  ├─ sender.sendTextBatch(信息卡)   「🎵 小明 点播：《青花瓷》/ 4:00 · 纳西妲」
  ├─ sender.sendFile(mp3, "青花瓷 - 纳西妲.mp3")
  └─ recordPlay()（stats.json，1.5s 合并写盘）
```

发送模式（`playlist.sendMode`）：

- `file`（默认）：整首发 mp3 文件，QQ 里可在线播放/保存。
- `auto`：时长 ≤55s 的歌发语音条，其余发文件。
- `voice`：总是发语音条；超过 55s 时自动截 `snippetSec`（默认 45s）的片段，从 32% 处开始（多数歌那里是副歌）。

失败处理：转码失败 → 群里明确回「《X》没发出去：原因」，不会静默；
单曲失败不影响该会话后续点播（发送链条兜底）。

> QQ 语音条上限 60s，所以「整首歌」只能以文件形式发；想要「点开就听」的语音条，
> 用 `#点歌 X` 后让 `sendMode=auto`，或工具参数 `asVoice: true` 发 45s 试听。

## 7. 缓存文件的本地读取与兼容

### 7.1 支持的缓存形态

| 形态 | 识别特征 | 元数据来源 |
|---|---|---|
| PC 客户端 | `<root>/<id>/` 下有 `.videoInfo` + `<id>-<p>-<qn>.m4s` | `.videoInfo`（JSON：标题/UP主/时长/BV号/封面路径/完成状态） |
| 安卓客户端 | `<aid>/<cid>/` 下有 `entry.json` + `audio.m4s`/`video.m4s` | `entry.json`（`total_time_milli` 是毫秒） |
| 散装音频 | 目录里直接放 mp3/m4a/flac/wav/ogg | 文件名当标题，时长用 ffprobe 补 |
| 音视频合流 | 只有一个 mp4/m4s/flv | 记为 `muxed`，转码时只取音轨 |

音轨识别：文件名末尾清晰度码在 `30216/30232/30250/30280/30300…` → 纯音频；
`audio.m4s` → 纯音频；`video.m4s` → 视频；名字认不出时才用 `ffprobe`（最多探 4 个）。

### 7.2 必须处理的坑

1. **9 字节私有头**：PC 缓存的 `.m4s` 前 9 字节是 ASCII `000000000`，之后才是 `ftyp`。
   ffmpeg 直接读报 `Invalid data found when processing input`，`-skip_initial_bytes 9` 也无效。
   处理：`detectMp4Offset()` 在前 8KB 里找合法的 `ftyp` 盒子，`cleanedSource()` 从该偏移复制一份到 `tmp/`。
   **原缓存永远只读**，B站客户端还要用它。
2. **时长单位不统一**：`.videoInfo.duration` 是秒，`entry.json.total_time_milli` 是毫秒 →
   `normalizeDuration()` 统一成秒（>10000 视为毫秒）。
3. **未下完的缓存**：`vi.status !== 'completed'` 或 `loadedSize < totalSize*98%` → `status: incomplete`，
   点播时直接提示「缓存不完整」，不会发出半首歌。
4. **中间产物混入**：`-vocal/-inst/-seg/_fixed/instrumental/伴奏/干声` 等文件名被过滤；
   缓存根目录下的散文件（历史实验产物）也不会把整个根目录当成一首歌。
5. **中文/空格路径**：全程用绝对路径传给 ffmpeg 和 NapCat（不做 URL/CQ 转义）；
   上传文件名会清洗 `\ / : * ? " < > |` 并截断 70 字。
6. **封面**：优先 `.videoInfo.coverPath`，其次 `image.jpg / cover.jpg / group.jpg`；
   合流 mp3 写 ID3 封面失败只记日志，不影响音频。
7. **缓存被替换**：转码缓存签名含 `源路径 + 大小 + mtime + 码率`，B站重下后自动重转，不会播旧版本。
8. **多根目录/重复**：同一份音频被多个根覆盖时按音频路径去重；同一目录多 P 只取一个（父目录无媒体才下钻）。

## 8. 配置（`data/config.json` → `playlist`）

```json
{
  "playlist": {
    "enabled": true,
    "roots": [],
    "autoRebuildMinutes": 30,
    "pageSize": 10,
    "cooldownSec": 5,
    "maxFileMb": 120,
    "transcodeBitrate": "192k",
    "snippetSec": 45,
    "sendMode": "file"
  }
}
```

- `roots` 留空 = 自动探测 `%USERPROFILE%\Videos\bilibili`（也认 `BILIBILI_CACHE_DIR` 环境变量）。
  换盘/改路径时填绝对路径数组，例如 `["D:\\BilibiliCache"]`。
- `autoRebuildMinutes`：歌单缓存有效期。缓存目录里新增/删除歌曲后，最多 30 分钟自动生效；
  想立刻生效就发 `#重扫歌单` 或调 `POST /api/playlist/rebuild`。
- 码率/大小上限按群文件体验调：192k 约 1.4MB/分钟，120MB 上限足够 80 分钟。

## 9. 运维与排障

```bash
node tools/build-playlist.mjs            # 手动重建并打印歌单
node tools/build-playlist.mjs --json     # 输出完整 JSON（排查解析问题）
node tools/build-playlist.mjs --root "D:\BilibiliCache"
node test/test-playlist.mjs              # 解析/检索/转码自检（不依赖 QQ）
```

| 现象 | 排查 |
|---|---|
| 提示「没有找到 B站缓存目录」 | 确认路径存在；写 `playlist.roots` 或 `BILIBILI_CACHE_DIR` |
| 某首歌没进歌单 | `--json` 看是否有该 track；`status` 是否 `incomplete`；标题是否被中间产物正则过滤 |
| 提示「缓存不完整」 | B站客户端里重新下载完成；`#重扫歌单` |
| 转码失败 | 看日志最后几行 ffmpeg stderr；确认 `runtime/ffmpeg.exe` 存在（`FFMPEG_PATH` 可覆盖） |
| 发出去没声音/打不开 | 源缓存可能只有视频轨（`muxed` 且无音轨）；换别的清晰度重新缓存 |
| 点歌没反应 | 看是否是裸词被放行给模型（`点歌` 单独两字）；用 `#点歌 歌名` |
| 冷却挡了测试 | 调 `playlist.cooldownSec = 0` |

控制台接口：

- `GET /api/playlist?q=青花瓷&page=1&pageSize=50` → 元信息 + 曲目
- `POST /api/playlist/rebuild` → 返回 `stats / buildMs / roots / errors`

## 10. 已知限制

- QQ 没有「点播队列/播放器」：所谓播放就是**投递音频文件或语音条**，不能真的替群友播放。
- 语音条上限 60s，整首歌只能发文件；试听片段固定从 32% 处截（没有做副歌检测）。
- 序号 `no` 在重建后会重排（按歌手 + 歌名排序）；用歌名点播不受影响。
- 合集/语音包不分轨：`胡桃翻唱大合集` 只能整段发，要分轨得先自己切。
