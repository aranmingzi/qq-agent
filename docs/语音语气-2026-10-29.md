# 语音语气：让她在不同语境里换一种念法

日期：2026-10-29
涉及：`src/voice-delivery.js`（新）、`src/prosody.js`、`src/gpt-sovits.js`、`src/vibe.js`、
`src/orchestrator.js`、`src/tools.js`、`src/prompt.js`、`src/config.js`、`src/app.js`、`console/`

## 一句话

以前"发语音用什么语气"完全靠模型自己写一句 `style` 自由文本，结果是同一个音色
在开心、难过、生气时念出来一模一样。现在情绪是一等公民：**情绪标签 → 参考音频 +
语速偏置 + 韵律参数 + 写法提示**，模型只需要填一个 `emotion`。

## 为什么不是"再写一句更长的提示词"

调研了几家开源 TTS 的做法，通行结论一致：**情绪由结构化的东西承载，不由一句自由描述承载。**

| 项目 | 情绪怎么进去 | 出处 |
| --- | --- | --- |
| GPT-SoVITS | 换参考音频。官方原话是"由参考音频的情感、音色、语速控制合成音频的情感、音色、语速" | [kekewolf/GPT-SoVITS](https://github.com/kekewolf/GPT-SoVITS/) |
| vits-simple-api | 给 GPT-SoVITS 配"参考音频预设"，调用时按 preset 名切换 | [zwssunny/vits-simple-api](https://github.com/zwssunny/vits-simple-api) |
| ChatTTS | 细粒度韵律控制：笑声、停顿、插入语，面向对话场景 | [CyberWon/ChatTTS-API](https://github.com/CyberWon/ChatTTS-API/) |
| EmotiVoice | 输入是 `<speaker_id>\|<emotion_prompt>\|<phoneme>\|<text>`，情绪提示与文本**分离** | [mirrors/EmotiVoice](https://gitee.com/mirrors/EmotiVoice) |
| CosyVoice | `inference_instruct2` 指令式控制 + fine_grained_control | 官方 README |

我们这边原本的 `style` 参数是"一句话自由文本"，正好踩在所有人都避开的那条路上。
更糟的是线上配置用的是 `cosyvoice-v3-flash`，它的 `instruction` 只认
「你说话的情感是X。」这一种句式，自由描述会被 `normalizeCosyvoiceInstruction`
归一化掉 —— 用户写的那句很讲究的语气描述，实际只发出了「你说话的情感是happy。」。

## 落地的四层

### 1. 情绪表（`src/voice-delivery.js`）

16 个键：vibe 的 14 种情绪（开心/兴奋/得意/好奇/害羞/别扭/委屈/失落/没劲/嫌弃/
假生气/心疼/累/平静）+ 吃惊 + 恐惧。每项：

```js
'心疼': {
  gsv: '难过',          // 用哪条参考音频（GSV_TAGS 之一）
  cosyvoice: 'sad',     // 千问兜底时用哪个合法情感值
  speedBias: 0.92,      // 语速偏置（× prosody 算出来的倍数）
  params: { temperature: 0.94, topK: 13, topP: 1, fragmentInterval: 0.35, repetitionPenalty: 1.36 },
  line: '软下来，慢慢说，像在旁边',   // 给 instruction 的一句话
  textHint: '句子短，别讲道理'        // 给模型的写法提示
}
```

`resolveTone()` 是唯一的入口，输入 `{emotion, vibeEmotion, voice, availableRefs,
moodScore, strength, enabled}`，输出完整计划。几条纪律写在代码里、也钉在测试里：

- **强度 0 = 老行为**。`strength: 0` 时连参考音频都不换（`mode: 'param'`、
  `enabled: false`、参数全等于 `NEUTRAL_PARAMS`）—— "关掉开关就回原样"必须是真话。
- **没有参考音频就诚实降级**。`mode: 'ref'` 只在 `availableRefs` 真的包含
  `entry.gsv` 时出现；否则 `'param'`，只调参数，不假装换了音色。
- **不认识的情绪不许瞎演**。模型填了表外的词（"非常暴躁"），先 `guessTone` 猜一次，
  还猜不出就落「平静」且 `enabled: false`。
- **心情底色只动 20%**。`moodLean(moodScore)` 给出 ±1，再乘 0.2 作用在偏置上：
  低落时兴奋会收敛成"没那么跳"，但不会反过来变慢。
- **参数夹在 `PARAM_BOUNDS` 里**，`topK` 取整，任何脏输入都不出 NaN。

### 2. 语速（`src/prosody.js`）

`resolveSpeed(text, baseSpeed, opts)` 多了 `opts.emotionBias`：

```js
mult  = clamp(auto.mult * bias, 0.88, 1.26)   // 仍然是乘数，不是替换
speed = clamp(base * mult, 0.5, 2.0)
```

标点算出来的语速和情绪偏置**叠乘**，两条线互补：一句话可以是"情绪很兴奋但文本有省略号"，
结果比纯标点快、比纯情绪慢。

### 3. 韵律参数（`src/gpt-sovits.js`）

本地 `api_v2.py` 的 `TTS_Request` 一直支持 `temperature / top_k / top_p /
fragment_interval / repetition_penalty`，此前一个都没用。现在按 `plan.params` 下发，
且**只发和默认值不同的项**（默认值由服务端自己带，多发等于多一层维护面）。
关掉：`audio.toneParams = false`。

### 4. 提示词（`src/prompt.js`）

`voiceToolsSection()` 从"写短、说人话"扩成"写短、说人话、**语气跟着语境走**"：

- 列出 16 个可用值；
- `auto` 的语义 = 用此刻心情（接上 `vibe.js` 算出来的 `vibeEmotion`）；
- 给对照例子：安慰人用「心疼」不是「平静」，被怼回嘴用「假生气」不是「生气」；
- 连续几条语音别用同一个情绪，但也别为了变而变；
- `style` 退回它该有的位置：只在情绪表达不出来时补一句。

编排层另外注入一段 `【此刻的语气】`（`formatToneHint()`），内容形如：

```
【此刻的语气】心疼——软下来，慢慢说，像在旁边。发语音时把 emotion 填成「心疼」，文本句子短，别讲道理。
```

## 数据流

```
用户消息
  → vibe.js 算出 blend / topEmotion           ← 快变量（此刻心情）
  → mood.js 算出 score                        ← 慢变量（底色）
  → orchestrator 拼 vibeText + toneText
      ├─ buildUserBundle 注入【此刻的心情】【此刻的语气】
      └─ 工具 ctx 带上 { moodScore, vibeEmotion }   ← 顺带修了 ctx.moodScore 恒 50 的老 bug
  → 模型调 send_voice({ text, emotion })
  → tools.js 用**实际** voiceKey 现算 resolveTone
      （gsvAllowModelPick 打开时模型可能换音色，能换哪条参考音频要现算）
  → gsvSpeak(text, { plan })   ①本音：按 plan.gsv 选参考音频 + 下发音律参数
      └失败→ synthesizeSpeech({ instruction })  ②兜底：CosyVoice 直接给合法情感句式
```

## 配置项（`config.audio`）

| 键 | 默认 | 作用 | 关掉会怎样 |
| --- | --- | --- | --- |
| `toneAuto` | `true` | 按语境换语气 | 回到"模型自己写一句 style"的老样子 |
| `toneStrength` | `1` | 情绪强度 0–1.5 | 0 = 完全按老样子，1.5 = 演得夸张些 |
| `toneParams` | `true` | 下发韵律参数 | 只剩语速调节（出爆音/咬字发飘时关它） |
| `prosodyAuto` | `true` | 按标点微调语速 | 每个音色一个固定语速 |
| `gsvSampleSteps` | `32` | CFM 扩散步数（8–64） | 32 是官方默认；调低更快更糙，**只对 v4 音色生效** |
| `gsvSeed` | `-1` | 随机种子 | `-1` = 每次随机；固定值 = 同句同结果 |

## 接口

- `GET /api/gsv/tone-plan?voice=liuying&emotion=心疼&moodScore=30` — 纯计算，不合成。
  返回 `{plan, hint, describe, coverage}`，控制台和排查都靠它。
- `POST /api/gsv/preview` 支持 body `{voice, text, emotion, style}`，响应头多
  `x-gsv-emotion` / `x-gsv-mode` / `x-gsv-speed`。
- `GET /api/gsv/voices` 多返回 `toneAuto / toneStrength / toneParams / coverage`，
  `coverage[].refEmotions` 是"真能换参考音频"的情绪，`paramOnly` 是"只能调参数"的。

## 控制台

设置 → 语音音色 → **语气与情绪**：自动换语气开关、韵律参数开关、情绪强度、
试听情绪下拉（自动 / 16 种）、以及"这个音色能真的换几种语气"的覆盖度说明。

   | 小鱼（昔涟） | 4 | 部分回落 | — | — |

   或在 `src/gpt-sovits.js` 的 `emotions` 表里登记已有文件。

   ⚠️ **花火那 4 条官方音频一直躺在 `emotions/` 目录里，但代码从没登记过** ——
   等于白存（语气系统看不到，永远走参数模式）。这类"文件在、表里没有"的问题
   只靠肉眼翻目录查不出来，`listGsvVoices()` 的 `emotions` 字段才是真相。

   **除流萤、花火的官方原声外，其余都是本机造的**。链路是
   `千问 TTS 按情绪句式合成 → RVC(<音色>.pth) 换音色 → rvc/train/enhance.py 压掉
   声码器编造的高频 → 重采样到 48kHz`，成品在 `rvc/train/emo/<音色>_*_final.wav`。
   质量控制三步：ASR 回读确认字没糊（编辑距离算 WER，按句长分档）、F0 中位数确认
   情绪真的拉开了、与真人默认那条的 MFCC 余弦相似度确认还是同一个人。

   ⚠️ **角色差异不能拿一套直觉去套**：
   - **纳西妲**生气时不是往上拔，而是压低了再发力（angry 的 F0 中位 248Hz 是那批里
     **最低**的，p10 只有 104Hz）。这是角色特征，不是录坏了。
   - **神里绫华**平时声线端庄，惊恐时反差最大（434Hz）。听着不违和，属角色特性。
   - **花火**的 angry/calm 两条 F0 中位几乎一样（276.7 vs 277.2），但动态范围差很多
     （angry p10~p90 = 100~547Hz，calm 75~392Hz）—— 生气是"起伏大"，不是"音更高"。
     别只看中位数就以为两条录重了，先比 p10/p90 或 md5。
   - 判断标准永远是 `check_emotions.mjs` 的三项指标，不是直觉。

   ⚠️ **芙宁娜的 RVC 模型对省略号特别敏感**：原句「别过来……这里不对劲，我们快走。」
   会被念成「别动，你别动…」甚至「妈妈在呢」，而且**每次重跑结果都不同**（模型在放飞）。
   换成无省略号的连贯句式后就稳定了。以后重做别把省略号加回去。

   ```bash
   # 换音色只要改 --only / --install（2026-10-30 修掉了三个只会做胡桃的坑：
   #   产物名写死 _hutao、convertVoice 没传 model、--only 解析后没用）
   node gen_emotions.mjs --only=nahida --install=nahida
   node rvc/train/check_emotions.mjs --dir=nahida --ref="<该角色真人默认.wav>"
   ```

   **RVC 权重来源**（`rvc/models/*.pth`）：胡桃/花火是自训或原有；
   纳西妲、芙宁娜、神里绫华、知更鸟来自 HuggingFace `mrmocciai/genshin-impact`
   （RVC v2 40k，f0=1）。同一仓库里绫华有三个版本（`ayaka-rmvpe` / `ayaka-v2` /
   `ayaka_400`），选了 `-rmvpe` 与芙宁娜同系列，f0 提取方法一致。
   ⚠️ 该仓库的 `.pth` 和 `.index` 是分开放的（`model/weights/` 与 `model/<名字>/`），
   两个都要下，只下 `.pth` 能用但音质差一档。

   ⚠️ 合成时 instruction 必须用 CosyVoice 的合法句式 `你说话的情感是xxx。`，
   否则 `normalizeCosyvoiceInstruction` 会按关键词猜，猜不中就兜底成 happy。
   ⚠️ `--dir=` 不能省：不筛音色的话，胡桃和纳西妲的成品会混在一张表里，
   余弦值会显示得莫名其妙地低（拿别人的音色当基线）。
2. **`aux_ref_audio_paths` 没接**：api_v2 支持多参考音频融合，但**对 v4 音色是无效的**——
   它不是"暂时没做"，是做了也没用。融合逻辑在 `GPT_SoVITS/module/models.py` 的 `decode()`
   （`if type(refer) == list: ... torch.stack(ges, 0).mean(0)`），而 v4/v3 在
   `TTS_infer_pack/TTS.py` 里一进来就把 `use_vocoder` 置 True，改走
   `using_vocoder_synthesis` / `using_vocoder_synthesis_batched_infer`，
   两者都只取 `prompt_cache["refer_spec"][0]` 单条。所以只有 v2ProPlus（流萤、花火）能吃融合。
   胡桃/纳西妲/芙宁娜/神里绫华传了是白传 —— 别再为这个开开关了。
3. **`streaming_mode` 也没接**，两个原因：v4 传 `2`/`3` 会直接
   `raise RuntimeError("SoVits V3/4模型不支持流式推理模式")`，只有 `1` 安全；
   而 `1` 等价于"整段合成完再分块返回"，可 `toQqVoice()` 必须拿到完整 buffer 才能
   ffmpeg 转 16k 单声道发语音条 —— **首字延迟对语音条没有意义**，这个优化留到
   将来做"控制台边合成边播"时再单独设计。
4. **`sample_steps` 只对 v4 生效**：它走的是 `TTS.py` 里 vocoder 分支才传下去的
   `n_timesteps`（`module/models.py` 的 `d = 1 / n_timesteps`）。流萤、花火是 v2ProPlus，
   走另一条解码路径，**这个值对它们完全没作用**。切到那两个音色时觉得"调了没反应"
   是这个原因，不是配置没生效。`gsvSpeak` 的返回值里有 `sampleSteps`，
   没下发就是 `undefined`，一眼能看出来。
5. **兜底链仍然降级**：角色本音服务没起来时走千问，CosyVoice 只有 7 个情感值，
   16 种情绪会被压成 7 个（映射表里写好了，不靠关键词猜）。

## 合成参数调优（阶段 0）

### 接了什么
`api_v2.py` 的 `TTS_Request` 里有两个参数客户端一直没发过，现在接上了：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `sample_steps` | `32` | CFM 扩散步数，越低合成越快、音质越糙 |
| `seed` | `-1` | `-1` = 服务端每次随机；固定值 = 同句同结果 |

默认值一个都没改，所以**不碰它们就等于改造前的行为**。下发逻辑集中在
`src/gpt-sovits.js` 的 `buildTtsQuery()` —— 一个不读盘、不发请求、不写日志的纯函数，
`test/test-gsv-query.mjs` 直接对它断言（21 组，含"默认配置发出的 8 个键必须和改造前完全一致"
这条回归基线）。

三条纪律：

- **等于默认值就不发**。`gsvSampleSteps: 32` / `gsvSeed: -1` 都不会出现在 query 里，
  少一层维护面，也让"没配"和"配成默认"行为一致。
- **脏输入当作没配**。`null` / `''` / `NaN` / `'abc'` 一律不下发。这里踩过一个坑：
  裸 `Number(null)` 是 `0`、`Number('')` 也是 `0`，会把"没配"读成"配了 0"再夹成下限 8，
  用户什么都没改音质却莫名变差 —— 所以用 `readNum()` 只认数字和非空数字字符串。
- **越界夹取**。`sample_steps` 夹到 `[8, 64]`：低于 8 音质塌得厉害，高于 64 只是白等。
  夹取后如果正好等于 32，同样不下发。

### 怎么定步数（别凭感觉）
```bash
node rvc/train/bench_gsv.mjs --voice=hutao --steps=16,24,32 --runs=1
node rvc/train/bench_gsv.mjs --voice=nahida --steps=8,16,32 --runs=2 --json
```

脚本走的就是 `gsvSpeak` 那条线上路径（只把步数换成这一档），自动拉起服务并**先跑一条预热**
（第一句要付加载权重/编译 kernel 的成本，实测是后一句的 2~3 倍 —— 不预热的话
"--steps 里写在第一个"的档位会被冤枉成最慢），三句话（短/中/长）× 每档 N 次，
输出 **平均合成耗时 / 音频时长 / RTF / 音色余弦 / 峰值**，以及相对 32 步快了百分之几。
试听文件落在 `data/voice/_bench/`。

### 实测数据（RTX 3050 4GB Laptop，胡桃，每档 1 次，3 句平均）

| 步数 | 平均合成 | RTF | 音色余弦 | 相对 32 步 | 峰值 |
| --- | --- | --- | --- | --- | --- |
| 16 | 7.41s | 1.61 | 1.000 | **快 41%** | 0.876 |
| 24 | 9.79s | 2.31 | 0.999 | 快 22% | 0.840 |
| 32 | 12.50s | 2.86 | 1.000 | 基准 | 0.824 |

两条结论：

1. **步数确实是线性的速度杠杆**（16→24→32 大致 7.4/9.8/12.5 秒）。但即使 16 步，
   RTF 仍然 >1 —— 这块 4GB 卡上"说得比她放得快"做不到，短句尤其明显
   （1.9s 音频要 6.2s，启动开销占比大）。
2. **MFCC 余弦挡不住这件事，别被 1.000 骗了**：三档实测都贴近 1.000。它只能拦
   "明显坏了"（串音色、糊字），分不出"好听的那点细微差别"。要判断 16 步到底能不能用，
   **只能听** `data/voice/_bench/` 里的文件。这也是为什么默认值仍然保持 32、这次没改。

怎么读：

- **RTF < 1** 才是"合成比播放快"，发语音不卡；> 1 就是她说完还得再等。
- **音色余弦**（MFCC-20 对同句 32 步那条）`≥0.98` 基本听不出换档，`<0.95` 已经能听出差别。
  但见上面的实测：这个数在 16~32 步之间几乎没有区分度，它只是兜底红线，不是音质结论。
- 表只能告诉你**差多少**，差在哪得耳朵判断 —— 定值前把相邻两档真听一遍。

`bench_gsv.mjs` 只对 v4 音色开放：拿 v2ProPlus 跑，各档耗时会是平的，脚本会直接提示并退出。

### 明确没做的（附理由，免得重复踩）
- `aux_ref_audio_paths`（多参考音频融合）—— v4 走 vocoder 分支只读 `refer_spec[0]`，无效。
- `streaming_mode` —— v4 传 2/3 直接报错；传 1 等于整段合成完再分块，对语音条无收益。
- `parallel_infer` / `batch_size` —— 服务端默认已最优，且与上面的分支互相牵制。

理由都写进了 `buildTtsQuery()` 的注释里，就在"明确不下发的四个"那一段。
