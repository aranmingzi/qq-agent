## 1. 原来错在哪

`src/orchestrator.js:1900` 的 `#proactiveCandidates(cfg)` 只有三个判据：

```js
if (meta.unread > 0) continue;
if (Date.now() - meta.lastTs < idleMs) continue;
if (this.runningChats.has(chatKey)) continue;
```

问题在于 **`idleMs` 是一个只会越来越真的条件**：没人说话的时间只会变长。于是：

| 现象 | 实际发生的事 |
|---|---|
| 一个没人搭理的群 | 每 30~90 分钟被投一次骰子（`probability: 0.25`） |
| 每次被选中 | 跑一整轮 agent（读历史、拼提示词、调模型），真金白银 |
| 结果 | 永远是 `noreply` —— 它自己判断"没必要说话" |
| 然后 | **这件事被彻底忘掉**，下一个 tick 照旧 |

面板上还看不出异常：`noreply` 是正常终态，和"她看过但决定不接"长得一模一样。
所以症状是"主动功能开着，但从来不会主动" + "账单在涨"，而日志里全是正常记录。

> **补一句诚实的边界**：上面这段是**代码推演**，不是实测。
> 我试图从 `data/sessions/` 里统计"主动唤醒多少次、真发出话多少次"，
> 结果是 **0 次主动运行** —— 本机 `data/config.json` 的 `proactive.enabled` 至今是 `false`
> （`data/config-changes.jsonl` 里也没有任何 proactive 相关改动记录）。
> 所以"浪费"目前还只是"如果开起来就会这样"，
> 真正该被验证的是：**开起来之后**，退避有没有把无意义的唤醒压下去。

## 2. 借鉴了什么

MaiBot 的 `IdleBackoffController` 给了三条规则，全部保留：

| 规则 | MaiBot 的做法 | 这里的落地 |
|---|---|---|
| ① 只数**连续**失败 | `record_cycle_result()` 遇到非 idle 的 cycle 就清零 | `noteProactiveOutcome()` 收到非主动的 `done` 就 `reset()` |
| ② 指数退避封顶 | `min(cap, base * 2 ** (count - start))` | `waitFor()` 同式，额外加 `Math.min(30, …)` 防 `2**498 === Infinity` |
| ③ 说了话走短冷却 | 无（MaiBot 没有"开口后"的概念） | `recordSent()` 走 `cooldownMs`（默认 30 分钟） |

**没抄的部分**：MaiBot 的 `bypass_pending_count`（积压消息够多就绕过退避）。
理由是这里的主动机会本来就在 `meta.unread > 0` 时被排除掉了 —— 有未读就根本不进候选，
"积压绕过"在这个架构里没有对应物，抄过来是一段永远不生效的分支。

**加的一条**：`recordSent()` 也 `streak += 1`。
理由：主动说了话却没人接，**在"没人理我"这个维度上和没说话是同一件事**，
只是代价不同 —— 说了话该等短冷却（别再自言自语），没说话该等长退避。
两条路径都推高 streak，但走不同的等待。

## 3. 改了什么

### 3.1 `src/proactive-backoff.js`（新，纯逻辑）

```js
export class ProactiveBackoff {
  constructor({ baseMs = 10*60*1000, capMs = 6*3600*1000, startCount = 2,
                cooldownMs = 30*60*1000, now = () => Date.now(), state = null } = {})
  configure({ baseMs, capMs, startCount, cooldownMs })   // 运行期可改，面板改参数不用重启
  waitFor(streak)                                        // 纯函数：streak → 该等多久
  check(chatKey)                                         // → { skip, reason, waitMs, streak, kind }
  recordDeclined(chatKey)                                // 没开口：streak+1，等指数退避
  recordSent(chatKey)                                    // 开口了：streak+1，等短冷却
  reset(chatKey)                                         // 清零；返回"是否真的变了"避免无谓写盘
  snapshot() / toJSON()
}
export function describeWait(ms)                         // "3 分钟" / "1.5 小时"
export function getProactiveBackoff(cfg) / saveProactiveBackoff(inst) / resetProactiveBackoffForTest()
```

三个实现细节值得记下来：

1. **`cap=0` 是关掉退避的开关，不能被 `Math.max(base, cap)` 悄悄救回来。**
   最初的写法是 `this.capMs = Math.max(this.baseMs, cap)`，于是配 `capMs: 0`
   得到的是"按 base 封顶"，和"我不想收敛"完全是两件事。改成：

   ```js
   this.capMs = cap === 0 ? 0 : Math.max(this.baseMs, cap);
   ```

   这是写测试时才发现的 —— 单看代码很像"防御性写法"。

2. **`check()` 取 `Math.max(until, cooldownUntil)`。**
   先开口（设 `until=0` + `lastSentAt=now`）再连续没开口（设 `until=now+长退避`），
   如果只看 `until`，短冷却会被一个过期的长退避顶掉；反过来如果只看冷却，
   长退避又会被忽略。取最大值才是"两个约束同时成立"。

3. **`#hydrate()` 丢掉过期太久的等待。**
   `if (until > 0 && until < now - this.capMs) continue;` —— 重启后不该接着等一个
   三天前的退避，那等于这个群被永久禁言。

### 3.2 `src/config.js`

`proactive` 块新增（`deepMerge` 保证老配置文件不用迁移）：

```js
backoffEnabled: true,        // 总开关
backoffBaseMs: 600000,       // 10 分钟
backoffCapMs: 21600000,      // 6 小时
backoffStartCount: 2,        // 连续 2 次没反应才开始退避
cooldownMs: 1800000          // 开口后 30 分钟不再主动
```

### 3.3 `src/orchestrator.js`

新增三个方法：

- **`pickProactiveTarget(cfg)`** —— 从 tick 闭包里**抽出来**的选目标逻辑。
  抽出来不是为了好看，是因为原来那 6 行长在 `tick` 内部，**接线错了任何测试都发现不了**（见 §4）。
- **`filterByProactiveBackoff(cfg, candidates)`** —— 逐群 `check()`，
  被挡下的落一条 `proactive-backoff` skip 记录（不花钱的跳过也要看得见，
  否则"为什么今天一次都没主动"无从排查）。
- **`noteProactiveOutcome(chatKey, status, proactive)`** —— 记账入口，接在 `wake()` 的 `finally` 里：

  ```js
  } finally {
    this.activeRuns.delete(runKey);
    this.runningChats.delete(runKey);
    this.sender.endRun?.(runKey);
    const finalStatus = session.status
      || (session.error ? 'error' : (session.sent.length > 0 ? 'done' : 'noreply'));
    this.noteProactiveOutcome(physKey, finalStatus, proactive);
    this.emit('chat-update', runKey);
  }
  ```

  两处刻意的选择：

  - **放 `finally` 而不是 `catch` 后面**：出错也要记。否则一个每次超时的群会被无限重试，
    而那才是最贵的失败。
  - **用 `physKey` 不用 `runKey`**：主动候选来自 `store.listChats()`（物理键），
    键对不上就是"记了但没人查"。

### 3.4 `src/skip-log.js`

`SKIP_STAGES` 新增 `PROACTIVE_BACKOFF: 'proactive-backoff'`。
（已确认 `ui/`、`ui-console/`、`ui-mobile/`、`console/` 里没有 stage 的 label 映射表，所以不用改 UI。）

## 4. 踩到的坑：接线测试没测到接线

第一版接线测试 12 项全绿，但**变异测试一跑就露馅**：把 tick 里那行

```js
candidates = this.filterByProactiveBackoff(cfg, candidates);
```

改成 `candidates = candidates;`（等于完全不接线），12 项断言照样全过。

原因是那 12 项全都是**直接调 `filterByProactiveBackoff`** —— 测的是方法自己，
不是"tick 有没有调它"。同样的洞还有一处：把 `finally` 里的
`this.noteProactiveOutcome(...)` 删掉，整套 `npm test`（含 e2e）也全绿。

修法分两步：

1. 把选目标逻辑从 tick 闭包里抽成 `pickProactiveTarget(cfg)`，测试可以直接调它；
2. 单开 `test/test-proactive-outcome-e2e.mjs`，**真的跑 `wake({proactive:true})`**，
   看退避状态有没有被写对。

现在再做同样的变异，两个文件都会红（`MUT_EXIT=1`）。

**这个教训要记住**：只要被测逻辑还长在闭包里，"有测试"和"测到了"是两件事。

## 5. 验证

```

[proactive-backoff]       18 项全部通过
[proactive-backoff-wire]  14 项全部通过

```

变异测试（做完立即还原，还原后重跑绿）：

| 变异 | 结果 |
|---|---|
| `filterByProactiveBackoff` 不接线 | `test-proactive-backoff-wire` 失败 ✓ |
| `finally` 里不调 `noteProactiveOutcome` | `test-proactive-outcome-e2e` 失败 ✓ |

端到端那 6 项覆盖的是**真实调用链**：起一个本地假模型端点，
分别返回 `tool_calls(send_message)` / 空 content / HTTP 500，跑真的 `wake({proactive:true})`，
断言退避状态落成 `cooldown` / `backoff(streak=1)` / `backoff(streak=1)`。

写这个测试时又踩了一个坑：**群聊里纯文本 `content` 不算发言**。
第一版假模型返回 `content: '大家都睡了吗'`，结果这一轮是 `noreply` ——
orchestrator 对群聊不兜底（只有主人私聊才有"必回重试"），
必须返回 `tool_calls` 调 `send_message` 才算真的说了话。

## 6. 残留问题

1. **`check()` 里 `until` 过期不会自动清理内存条目** —— 条目会一直留在 `Map` 里
   （只在 `reset()` / `recordXxx()` 时更新）。会话数上千时是无害的，但快照会变长。
2. **`snapshot()` 不排序** —— 面板如果要展示"最该等的几个群"，得自己排。
3. **冷却与退避共用 `streak`** —— 开口后被冷落 3 次，退避会从第 3 次直接开始算
   （`startCount=2` 时立刻进入长退避）。这在语义上是对的，但如果用户预期
   "开口过就重新数"，会觉得跳得太快。目前靠 `reset()`（群里有人说话）来重置。
4. **没接面板** —— `proactiveBackoffSnapshot()` 已经导出，但还没有 HTTP 路由/UI 去读它。
5. **`noteProactiveOutcome` 用的是 `getConfig()` 全量重读** —— 每轮一次，开销可忽略，
   但如果将来配置读取变重，这里应该改成注入。
6. **整套逻辑在生产上还是零运行** —— `proactive.enabled` 至今 false（见 §1 末尾的说明）。
   测试证明的是"逻辑对、接线通"，**不是**"线上有效"。开起来之后要盯两件事：
   `proactive-backoff` 这个 skip 阶段出现的频率（压掉了多少空转），
   以及群里被退避的 chat 有没有在有人说话后正确 `reset`（有没有把人聊死）。
