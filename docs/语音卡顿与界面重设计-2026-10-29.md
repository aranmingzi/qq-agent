# 语音通话持续卡顿 + 两个新页面重设计（2026-10-29）

> 用户报的两件事：「QQagent 打开语音通话会出现持续卡顿」「新建的 UI 设计不合理，重新设计」。
> 这篇只记这两件，不掺别的。

---

## 一、卡顿：不是网络慢，是主线程被每秒 125 次的小活压满了

### 1.1 先算流量，别猜

`AudioWorklet` 的 render quantum 是 128 帧。采集按 16kHz 跑：

```
每帧样本数 128
每秒 postMessage 次数 = 16000 / 128 = 125
每次 postMessage 附带一次 ws.send(256 字节)
→ 每秒 125 条二进制帧 × (256 B 载荷 + 2~6 B 帧头)
→ 服务端每帧回一条 {"type":"level",...} ≈ 31 B，又是 125 条
即：每秒约 250 条 ws 消息来回，35 KB/s
```

35 KB/s 对 ws 不算大。**问题是这 250 次全压在浏览器主线程上**，每次只干 8ms 的活：

1. `voice-client.ts` 的 `emit()` 每帧 `float32ToInt16(resampleTo16k(...))` —— 每秒新建 125 个 typed array，外加一次 `ws.send` 的协议封帧。
2. 同一处分发出的 `onLevel(rms(samples))` 被页面接成 `onLevel: setLevel` —— **每秒 125 次 React setState，每次都重渲染整个 492 行的页面**，包括下面那张通话记录列表。
3. 服务端对每一条非 VAD 边界的二进制帧都回一条 `level` JSON；而客户端的 `dispatch()` 里**根本没有 `level` 分支**，这 125 条/秒解析完就扔。

第 2 条是肉眼可见卡顿的主因：不是掉帧，是浏览器一直在做一件永远做不完的重渲染。第 3 条两边都白烧。

### 1.2 改了什么

**客户端 `console/src/lib/voice-client.ts`**

- 新增 `PcmChunker`：按 100ms 攒块，攒满才发。125 帧/秒 → 10 帧/秒。
  `export const CHUNK_MS = 100;` 攒块在 `push()`，尾巴由 `flush()` 吐出。
- 新增 `flushPending()`，并且**顺序很关键**：`commit()` 和 `close()` 都必须先冲尾巴再发 `stop` / 置 `closing`。顺序反了，用户最后不满 100ms 的半句话会跟着连接一起消失 —— 表现就是「我最后一个字它没听见」。
- `onLevel` 不再直接进 React：新增纯函数
  ```ts
  export function shouldEmitLevel(lastAt: number, now: number, intervalMs: number = LEVEL_INTERVAL_MS): boolean {
    if (!Number.isFinite(lastAt) || lastAt <= 0) return true;
    return now - lastAt >= Math.max(0, intervalMs);
  }
  ```
  页面侧把它折进一次 `requestAnimationFrame`，并且**电平条不再走 React state** —— 直接 `node.style.transform = scaleX(...)`。一根 3px 的线没有资格让整页重渲染。
- 顺手修了一个真 bug：ScriptProcessor 兜底分支原本 `node.connect(ctx.destination)`，等于**把麦克风原样播出来**（啸叫；而且持续的自身声音会反复触发打断）。改成过一级 `gain=0` 的 GainNode 再接 destination —— 图保持连通，`onaudioprocess` 照常触发，但一个样本都听不见。

**服务端 `src/voice-gateway.js`**

- `export const LEVEL_PUSH_MS = 50;`（20 条/秒，眼睛分辨不出更快），每个会话一个 `lastLevelAt`。
- 光改客户端不够：老客户端或别的调用方一帧一帧推，服务端还是会狂发。所以限流放在服务端。

### 1.3 验证

| 测试 | 钉的是什么 | 结果 |
|---|---|---|
| `test/test-voice-pacing.mjs` | 攒块条数、块大小、flush 尾巴、跨采样率、电平节流 | 10 条 ✓ |
| `test/test-voice-level-throttle.mjs` | 真 server + 真 ws，20ms 一帧推 1s，数服务端回了几条 level | 3 条 ✓ |

**四个变异全部被抓到**（拆掉实现就变红，说明测试不是装饰）：

```
✓ CHUNK_MS 改回 8ms（回到每 8ms 一块）
✓ shouldEmitLevel 永远返回 true（电平不限流）
✓ flush() 直接返回 null（丢掉最后半句）
✓ 服务端限流条件删掉（回到每帧一条 level）
```

实测数据：1 秒 125 帧 → **只发出 10 块**，每块 1600 样本；服务端 20ms 一帧推 50 帧（实测 1563ms）→ **只回 25 条 level**，未限流会是 50 条。

### 1.4 一个测试自己的教训

`test-voice-level-throttle.mjs` 第一版是红的，而代码是对的：它按「循环耗时正好 1000ms」算上限（22 条），但每次 `setTimeout(20)` 都带调度开销，实测 1563ms，于是 25 条被判成失败。**上限必须按实测耗时算**，不能按假定的。改法是把循环包在 `Date.now()` 里，用 `Math.ceil(elapsedMs / LEVEL_PUSH_MS) + 2`。

## 二、重设计：两个页面都从「一堆卡片」改成「先给结论」

### 2.1 语音通话页 `console/src/features/voice/voice-call-page.tsx`

改之前的问题（492 行，三张卡上下堆）：

- 电平条每秒 125 次 setState 重渲染整页（见上）。
- 「从哪里听 / 声音送到哪 / 开始 / 说完了 / 打断 / 挂断 / 计时 / 状态 / 两条提示」全挤在一张卡里。
- 输出设备是一个**没样式的原生 `<select>`**，而页面上其他控件都是 `Button` / `Badge`。
- 通话记录在**另一张卡、屏幕外**——用户说完话，看不到回复，得往下滚。

改之后：`grid gap-5 xl:grid-cols-[minmax(0,1fr)_minmax(320px,420px)]`

- **通话台**（左）：状态点 + 状态字 + 时长、3px 电平线、按钮组、一条提示。状态色从 6 种柔和色收敛到 3 种（`idle/closed → bg-muted/40`、`listening → bg-success`、其余处理中 `bg-primary`）。
- **通话记录**（右）：`max-h-[520px] overflow-y-auto`，新消息自动滚到底。并排之后，「说完立刻看到回复」这件事不用滚动了。
- **通话设置**（跨两列）：从哪里听 + 声音送到哪。
- 原生 `<select>` 换成 Radix `Select`。**踩到一个坑**：Radix Select 对 `value=""` 会抛异常，所以加了一个哨兵值
  ```ts
  const OUTPUT_SENTINEL = '__default__';
  ```
  `value={outputId || OUTPUT_SENTINEL}`，回调里再翻译回 `''`。
- 「说明」从第八张卡变成 `<details>` —— 常读一次的东西不该占首屏。

### 2.2 QQ 通话页 `console/src/features/call/qq-call-page.tsx`

改之前的问题是**信息架构错了，不是样式丑**：

- 六张卡（三块拼图 / 手 / 耳朵 / 嘴 / 说明）里躺着九个以上的开关和状态，**没有任何一处回答「我现在到底能不能接电话」**。用户要在脑子里把三张卡上的三个 Badge 做一次与运算。
- 配置项（持久化）和「点接听」（不可回退的动作）混在同一张卡里，最高风险的动作看起来像又一个设置项。
- 「嘴」那张卡自己写着「真控件在另一个页面 `#/voice`」—— 这是信息架构放错的自我举报。

改之后，顺序变成 **结论 → 条件 → 分组**：

1. **一行结论横幅**：`会替你接电话` / `不会接电话（还差：…）`。判据只有一个：
   ```ts
   const canAnswer = Boolean(status?.enabled && status?.autoAnswer);
   ```
   耳朵或嘴缺了不影响接听，所以它们不进这个判据 —— 之前把三件事混成一个「就绪」是错的。
2. **三个条件 chip**：手 / 耳朵 / 嘴，各带图标和绿/黄点，缺哪个一眼看见。
3. **`xl:grid-cols-2` 两栏**：左「设置」（四个 ToggleRow + VAD 数值），右「扫描」（干跑、扫描结果、watcher 读数、系统端点列表收进 `<details>`、去 `#/voice` 的链接）。
4. 「说明」也收进 `<details>`。

## 三、顺手修的一处：打包断言拿按钮文案当锚点

`test/test-call-smoke.mjs` 里有一条「打包里有没有 QQ 通话页」，锚点是 `bundle.includes('干跑一次扫描')`。这次重设计把那句按钮文案改掉了，测试立刻报 **「打包里没有 QQ 通话页的内容 —— 页面会 404」**，而页面其实好好的。

一条只会在改文案时变红的断言，测的不是打包。换成结论横幅的主文案：

```js
assert(bundle.includes('会替你接电话'), '打包里没有 QQ 通话页的内容 —— 页面会 404');
```

两个分支（会 / 不会）都编译进 bundle，且只有这一页会产出它，改布局改按钮都碰不到。

## 五、残留

- **杂音/回声消除没做**：AEC 依赖浏览器，虚拟声卡回路上的回声仍然存在。这次只修了「把麦克风播出来」那个低级 bug。
- **ASR 仍是整段识别**，首字延迟 1~2s；换 `paraformer-realtime-v2` 要处理「PCM 必须以裸二进制帧发、不能包在 continue-task 里」那个静默失败陷阱。
- **卡顿只在本机用假后端量过**：真机（真 QQ 通话 + 真 DashScope）没跑，因为那需要第二台设备打进来。
- 面板上的「刷新状态」在 dev 环境（后端没起）会显示 `HTTP 500` 横幅，这是预期内的降级。
