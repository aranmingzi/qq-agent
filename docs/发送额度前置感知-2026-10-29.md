## 1. 原来错在哪

`src/sender.js` 的 `#checkRate` 是**发送时**才判限流的。而一轮对话的成本结构是：

```
入站消息 → 闸门 → 拼提示词 → 模型调用（3 万 token）→ 工具调用 send_message → 撞上限 → 报错
                              ↑ 钱在这里就花完了                              ↑ 到这里才知道
```

模型拿到「发到上限了」的错误之后，常见反应是**再跑一轮**换句话重试 —— 又是一整轮。
实测的轮次分布正好印证：p50 = 2 轮，p90 = 3 轮，最多 4 轮。

更要命的是这件事在面板上**看不见**：翻了全部 78 个轮次的会话记录，搜索
`/上限|限流|超限|频控|频率|额度/` 在 tool 消息里 **0 命中** —— 限流错误文本根本没进会话存档。
所以它是"每个月账单上多出来一块，但没人知道为什么"的那种漏洞。

## 2. 借鉴了什么

两个竞品都把限流放在**入站**：

- **AstrBot 4.29.3** `astrbot/core/pipeline/rate_limit_check/stage.py`
  `RateLimitStage` 是一个独立的 pipeline stage，排在 LLM 之前。每个会话一个
  `deque[datetime]`，`_remove_expired_timestamps` 先滑出过期记录，够了就
  `asyncio.sleep(stall_duration)` 或者 `event.stop_event()` 直接丢弃。
- **LangBot 4.11.2** `src/langbot/pkg/pipeline/ratelimit/ratelimit.py` + `algos/fixedwin.py`
  同样是 pipeline 里的一个 stage（`RequireRateLimitOccupancy`），固定窗口，
  `drop` / `wait` 两种策略。

**借的**：闸门放在花钱之前。这是核心，也是唯一真正重要的一点。

**没借的**：它们的"等待"是**阻塞**当前轮次（`asyncio.sleep`）。我们不阻塞 ——
消息保持未读、安排一次带抖动的重排，让 worker 去干别的。原因是我们的
`wake()` 是全局并发池里的一个槽位，阻塞等于占着坑位干等。

**也没借**：LangBot 那套 `SessionContainer` + LRU 驱逐（`_MAX_SESSION_CONTAINERS = 10000`、
`_MAX_EVICTION_PROBES = 64`）。那是为了扛住"十万个会话同时限流"的服务端规模，
我们是单机桌面应用，`Map` 里几个 key 就够，加那套只会让代码更难懂。

## 3. 改了什么

### 3.1 新模块 `src/send-quota.js`（130 行，纯函数）

只回答"还剩几条"，不做决定、不写文件：

- `resolveMinuteLimit(chatKey, sendCfg)` —— **全项目唯一**的每分钟上限取值规则。
  私聊可用 `maxPerMinutePrivate` 单独放宽；未配置 = 沿用 `maxPerMinute`；配 `0` = 不限。
- `quotaFrom({times, limit, windowMs, now})` → `{limit, used, remaining, resetInMs, unlimited}`。
- `assessQuota({chatKey, sendCfg, minuteTimes, hourTimes, now})` —— 综合分钟与小时两个窗口，
  返回**更紧的那个**。
- `describeQuotaWait(ms)` / `describeQuota(q)` —— 人话，进日志与提示词。

三个容易写错的地方，都在代码里留了注释：

1. **不限额度时 `remaining` 必须是 `Infinity`，不能是 `null`。** 调用方统一写
   `remaining <= 0`，而 JS 里 `null <= 0` 是 `true` —— 用 `null` 会把"不限"判成"发满了"，
   结果是**所有不限速的会话全部永久不回复**。测试里专门有一行
   `assert.ok(!(q.remaining <= 0))` 钉这个语义。
2. **时间戳要收垃圾。** 桶在内存里，一个 `NaN` 或一个未来时间戳就能让某个会话
   永久"发满了"。所以过滤条件是 `Number.isFinite(x) && x <= t && t - x < span`。
3. **两个窗口剩余相同时，取等得久的那个。** 分钟窗口 5 秒后滑出、小时窗口 55 分钟后滑出，
   报"5 秒"就会让它在 5 秒后重排、再撞一次小时上限。测试用
   `q.window === 'hour' && q.resetInMs > MINUTE_MS` 钉住。

### 3.2 `wake()` 里的闸门（`src/orchestrator.js:650`）

```js
// 必须排在 drainUnread **之前**
if (!this.checkSendQuota(physKey, { proactive, traceId })) return;
```

**位置是这一段最重要的细节。** `drainUnread` 是破坏性的（把未读标成已读并消费掉），
闸门放在它后面就等于"挡下了这一轮，顺便把消息也吃掉了"。变异测试专门验证了这一点：
把闸门挪到 `drainUnread` 之后，`test-send-quota-wire.mjs` 立刻红在
「被额度挡下的轮次绝不能消费未读」。

`checkSendQuota()` 的四个取舍（都写在 docstring 里）：

| 取舍 | 为什么 |
|---|---|
| 只挡 `remaining <= 0`，不挡"剩 1 条" | 剩 1 条完全可能把话说完整，挡掉等于把正常对话一起削了 |
| 挡下时 `scheduleWake(resetInMs + 100~1500ms 抖动)` | 消息保持未读，等窗口滑过去再处理。抖动是必要的：同群多个轮次会在同一毫秒醒来，再一起撞新窗口 |
| 主动机会直接放弃，不重排 | 主动开话题本来可有可无；额度满时还排队，会在窗口一开就挤掉别人的正常对话 |
| 整段 try/catch，出错按放行处理 | 额度模块自己坏了，绝不能变成"不回复" |

### 3.3 动作集预算接真实额度

以前 `planActions()` 只按档位给数（2~4 条），而发送侧真正允许的可能是 1 条 ——
模型照 4 条规划，第一条之后全部撞墙，然后再花一整轮补救。

现在 `planActions({... sendQuota })` 收真实剩余量：

```js
const quotaCapped = Number.isFinite(Number(sendQuota)) && Number(sendQuota) >= 0
  ? Math.max(1, Math.min(planned, Number(sendQuota)))
  : planned;
```

- **下限仍是 1**：额度为 0 的轮次在 `wake()` 里就被挡下了，走不到这里；万一中途变了，
  也让模型把最要紧的那一句说完，而不是规划 0 条后哑火。
- 分条动作的开启条件从 `base >= 3` 收紧成 `base >= 3 && bubbles >= 2` ——
  只剩 1 条额度时不该还广告"分条发"。
- 被额度压窄时加一句提示：`这一分钟只剩 N 条额度了，把话并成一条说完，别先发引子再补。`

`#sendQuotaRemaining()`（-1 = 不限或算不出来）与 `checkSendQuota()` 读的是**同一个**
`sender.quotaFor()`，两边不会漂移。

### 3.4 单一来源：`resolveMinuteLimit`

`sender.#minuteLimit()` 原来的取值逻辑（私聊 vs 群聊、`0` = 不限）被抽进 `send-quota.js`，
`sender.#checkRate`、`sender.sendTextBatch`、`sender.quotaFor`、`orchestrator.checkSendQuota`
全部走它。理由写在 `#minuteLimit` 的注释里：**同一个规则写两遍必然漂移**，
而这类漂移的症状是"配置改了但只有一半生效"，极难查（前车之鉴：降级链的 `MAX_CHAIN`
与 orchestrator 的 `slice` 上限没对齐，第 8 条端点永不尝试且零报错）。

## 4. 踩到的坑

### 4.1 第 2 轮的老坑又踩了一次：接线测试没测到接线

`test-send-quota-wire.mjs` 第一版直接调 `checkSendQuota()` 和 `sendQuotaRemaining()`。
**把 `wake()` 里那行闸门整行删掉，12 条断言照样全绿。** 这和第 2 轮
（`filterByProactiveBackoff` 那件事）是同一个错误：测了单元，没测调用点。

修法：加一条走完整 `wake()` 的用例，断言"额度满了 → `sessions` 不新增 + 未读还在"。
再加一个独立的端到端文件（`test-send-quota-e2e.mjs`），用真 HTTP 假模型钉住
**"额度满时一个请求都没发出去"**（`requests.length === 0`）。这条断言无法被"只测单元"绕过。

### 4.2 全量测试里 `selftest.mjs` 的场景 7 红了

`❌ 审计失败：Error: 等待超时：会话(刷屏测试)结束`

第一反应是"限流逻辑被我改坏了"，实际不是：场景 7 验的是**发送时**撞上限之后的行为
（错误回传模型 + 反走神护栏），而新的前置闸门在**开跑前**就把这一轮挡掉了，
于是 `waitSessionDone('刷屏测试')` 永远等不到会话 —— **两道闸门里更早的那道先响了**。

这不是回归，是新的正确行为。修法是在该场景里显式 `preflightQuota: false`（测的是后一道闸门），
测完再恢复成 `true`。注释里写清了原因，免得下次有人以为这里"绕过了一道保护"。

这件事本身是个收获：**新加一道闸门时，所有"验证闸门之后行为"的老测试都可能提前被挡住**，
报错信息（"等待超时"）完全指不到真正原因。

### 4.3 `updateConfig` 的 `undefined` 不生效

测试里想"恢复默认"写了 `updateConfig({ send: { preflightQuota: undefined } })` ——
`deepMerge` 会跳过 `undefined`，等于没写，下一个用例直接红在 `true !== false`。
改成显式写回 `true`。

### 4.4 `#sendQuotaRemaining` 是私有的，测试调不到

和第 2 轮一样，改成公开方法（`sendQuotaRemaining`）。这是个反复出现的模式：
**凡是测试需要断言的内部决策，就别用 `#`**。

### 4.5 `python3` 在 Windows 上是应用商店占位程序

做变异测试时用 `python3` 写了个替换脚本，**静默什么都不做**（exit 0、无输出），
导致"变异"没生效、测试照常全绿，差点误判成"测试抓不住这个变异"。
换成 `python` 才正常。教训：**变异测试必须先确认变异真的落盘了**
（脚本里打 `gate count: 1`，并且 `grep` 确认过），否则测的是"原代码仍然通过"。

## 6. 残留问题

1. **只预判文本桶。** 表情包走的是独立桶（`${chatKey}|sticker`），语音/图片也有各自的路径。
   表情桶默认 `maxPerMinute: 1`，撞上的概率不低，但目前不在前置闸门的视野里。
2. **小时额度用了 `hourTimes`，但发送侧真正抛错的是 `#checkRate` 里的 `maxHour`。**
   两边的窗口起点语义（滚动 vs 固定）我按滚动实现了，没有跟 `#checkRate` 逐行比对过。
   如果那边其实是固定窗口，`resetInMs` 会偏乐观。
3. **重排抖动是 0~1.5 秒固定区间**，不是按会话哈希。同一个群频繁撞额度时，
   多个轮次的醒来顺序仍然近似随机，理论上可能反复抢同一个槽。
4. **`quotaFor()` 读的是内存桶。** 重启后桶清零，所以重启那一刻的"额度已满"是不知道的
   —— 会放行一轮，然后照常撞墙。要彻底解决得把发送时间戳也落盘，成本不小，
   而重启本身是低频事件，暂时接受。
5. **面板没有展示这道闸门。** `send-quota` 已经进了 `SKIP_STAGES` 和 skip-log，
   但 `ui/`、`ui-console/`、`ui-mobile/` 里都没有 stage → 中文标签的映射表，
   所以面板上看到的是原始 stage 值。
6. **`preflightQuota` 关掉之后没有任何提示。** 如果有人为了排查问题关掉它又忘了开回来，
   就会静默退回"先花钱再发现发不出去"的老行为。
