# 复读拦截：把「说过」的判定从"想发"改成"真发出去了"

2026-10-29 · 第 12 轮 · 目标模式

---

## 0. 一眼看全

| 项 | 内容 |
|---|---|
| 缺陷 | 复读拦截在**发送前**记账，导致"发送失败的那句"也被当成"已经说过" |
| 后果 | 模型换个说法重发 → 被自己上次的失败记录挡下 → 这一轮彻底沉默，用户看到"她没理我" |
| 实测规模 | 1000 个真实会话、15 次复读拦截，其中 **5 次（33%）** 是这个成因 |
| 改动 | `plugins/复读拦截/index.js` 记账时机 before-tool → after-tool；`src/orchestrator.js` 给 after-tool 补 `session` |
| 附带修复 | `messages` 双重编码（模型把数组序列化成字符串）不再整串当一句话，否决原因不再回显 `["` |
| 测试 | 新增 `test/test-echo-guard.mjs`（10 项）、`test/test-echo-guard-e2e.mjs`（3 项） |
| 全套 | `npm test` EXIT=0，**1110** 项 ✓（原 1097，+13） |
| 残留 | 见 §6（插件状态不落盘、窗口边界、并行工具调用顺序假设） |

## 1. 原来错在哪

`plugins/复读拦截/index.js` 的 `before-tool` 钩子做两件事：**判重**和**记账**。
判重没问题，问题出在记账的**时机**——它在工具真正执行之前，就把这句话写进了
`history`（"这个群最近说过什么"）。

于是这条链路成立：

```
第 1 轮  模型：send_message("孤本啊，那票价得翻倍")
         → before-tool：不重复，记账 ✓
         → sender：撞上分钟额度 / 白名单失效 → **这条没发出去**
第 2 轮  模型（看到失败）：换个说法重发同一句（这是正确反应）
         → before-tool：history 里已经有了 → **否决**
         → 模型收到"复读拦截"，不再说话
用户看到：她明明在跟我说话，突然不吭声了
```

关键在于：**模型的重试是正确行为**，是拦截器把它的正确行为判成了错误。

### 实测证据

从 `data/sessions/*.json`（1000 个会话）里捞出全部 15 次复读拦截，逐条回溯
"这句之前有没有同一句的发送尝试"：

```
total: 15
priorFailed:    5   ← 上一句是**失败**的（quota 4 次、白名单 1 次）
priorSucceeded: 1   ← 上一句确实发出去了，拦得对
noPrior:        9   ← 本会话没发过，但 history 里有（见下）
```

那 5 次误拦的原话（`file | 被拦的句子 | 上一句的失败原因`）：

```
mvqpyykn-f6f2443f | 孤本啊，那票价得翻倍        | 不在白名单里（发送前复核）
mvs742se-c2bcadef | 谁捂耳朵了 我才没嫌吵      | 这一分钟发到上限（4 条）了
mvs93utq-47345cea | 谁才是胆小鬼了哼           | 这一分钟发到上限（4 条）了
mvs941zt-5a2f7f4c | 哼，又拿这种图来敷衍我╭(╯^╰)╮ | 这一分钟发到上限（4 条）了
mvs9zsel-9ae78722 | 全群都是我主人还行，搁这儿叠buff呢(▼皿▼#) | 这一分钟发到上限（4 条）了
```

`priorFailed` 里 4 次是分钟额度——正好是第 3 轮「发送额度前置感知」修的那一类。
两个缺陷叠在一起：额度把话吞了，复读拦截再把重试也吞了。

### 顺带发现的第二个缺陷

那 9 次 `noPrior` 里有一条否决原因是这样回显给模型的：

```
复读拦截：「["劝君更哈一口气，西出阳关无大狗", "下句就是：莫愁前路
```

模型把整轮 `messages` **序列化成了字符串**再塞进 `messages` 字段
（`messages: "[\"甲\", \"乙\"]"`）。老代码把这一整串当成一句话，
`norm()` 之后开头的 `["` 留在判重串里，回显时也带出去了。

这不只是难看：判重串变成 `["劝君更哈一口气…` 之后，
`isNearDup` 拿它跟真正的句子比，**前缀永远对不上**，等于这一条既拦不准也记不准。

## 2. 借鉴了什么

| 来源 | 许可 | 借鉴的点 | 怎么落地的 |
|---|---|---|---|
| **Estrella-Bot** | MIT | 插件钩子用"否决 + 原因回灌"让模型自己改口 | 沿用（本插件本来就是从这里移植的），本轮不动否决语义 |
| **AstrBot 4.29.3** | AGPL-3.0 | `after-tool` 钩子能拿到完整上下文（含会话），据此决定"这次算不算数" | 给 `after-tool` 补 `session` 字段，插件用"成功/失败"决定是否记账 |
| **LangBot 4.11.2** | Apache-2.0 | 消息文本归一化（多层 JSON 编码要摊平） | `textsOf()` 递归解一层 `[` / `"` 包裹 |

**没有照抄的部分**：AstrBot 的 `after-tool` 直接改工具返回值（`event.set_result(...)`），
QQ Agent 的钩子总线是**只读观察**（`src/hook-bus.js` 里 `emit` 只收 `{vetoed}`）。
强行改返回值会绕过 `session.messages` 的记账，收益远小于风险 —— 所以只借"能拿到会话"
这一点，不借"能改结果"。

## 3. 改了什么

### 3.1 `src/orchestrator.js`：after-tool 补 `session`

```js
// src/orchestrator.js:1682
await this.hookBus.emit('after-tool', {
  toolName: name,
  argsRaw,
  result: result?.content,
  isError: !!result?.isError,
  session: { chatKey, sent: ctx.session.sent },   // ← 新增
});
```

`before-tool` 一直有 `session`，`after-tool` 没有。这个不对称就是 bug 的土壤：
钩子在"结果"这一侧看不见"属于哪个会话"，只能靠猜或者干脆不判断成功与否。

### 3.2 `plugins/复读拦截/index.js`：记账挪到 after-tool

- `before-tool` 只做**判重 + 登记待记账**（`pushPending(chatKey, texts)`），不再直接写 `history`。
- `after-tool` 才真正 `remember()`，且**先看 `isError`**：

```js
// plugins/复读拦截/index.js:219
if (isError) return;              // 失败 = 没发出去 = 不该记成"说过"
const sent = sentCountOf(result);
const texts = sent >= 0 ? item.texts.slice(0, sent) : item.texts;
for (const t of texts) if (t) remember(item.chatKey, t);
```

`sentCountOf()` 读工具结果里的 `{"sent": N}`：分条发送时第 2、3 条可能被节奏省掉，
只记真的出去的那几条（见 §4 的坑）。

### 3.3 `textsOf()`：摊平双重编码

```js
// plugins/复读拦截/index.js:129
if (typeof raw === 'string') {
  const t = raw.trim();
  if (t.startsWith('[')) { try { const p = JSON.parse(t); if (Array.isArray(p)) raw = p; } catch {} }
  else if (t.startsWith('"')) { try { const p = JSON.parse(t); if (typeof p === 'string') raw = p; } catch {} }
}
```

### 3.4 `popPending()`：拿不到会话就**不记账**

第一版写了个"FIFO 兜底"：`after-tool` 没带 `chatKey` 就取最早入队的那条。
这是错的 —— 猜错会话会把 A 群的话记到 B 群头上，然后 B 群里一句全新的话被莫名拦下。

改成只认带 `chatKey` 的，拿不到就跳过：

```js
// plugins/复读拦截/index.js:36
if (!chatKey) return null;
```

**方向性理由**：记账失败只会让复读拦截**少拦一次**（放行，安全方向）；
记错群会让用户莫名其妙说不出话（危险方向）。宁可不拦。

## 4. 踩到的坑

### 4.1 测试用 FIFO 掩盖了"没传 session"的缺陷

写完 `popPending` 的 FIFO 兜底后跑变异检查：把 `after-tool` 的
`session: { chatKey, ... }` 删掉，**10 项测试照样全绿**。
因为钩子自己"猜"对了会话——测试环境里只有一个群，猜必然猜对。

这就是为什么必须有 `test/test-echo-guard-e2e.mjs`：它跑真实 `wake()`，
并直接断言 `afterSessions[0].chatKey === GROUP`。删掉 session 之后它立刻红：

```
AssertionError: after-tool 必须拿到 chatKey，实际 undefined
```

**教训（第 2 轮踩过同一个坑）**：接线测试测不到接线。
凡是"某个字段有没有被传下去"，必须有一个能直接看见那个字段的用例。

### 4.2 `sent=1` 只记第一条——分条发送的真实形状

第一版 `remember()` 无条件记全部 `pass`，但 `sendTextBatch` 在额度紧张时会
**只发前 N 条、把后面的省掉**（第 3 轮改的 `LONG_TEXT_ALWAYS_SEND` 逻辑）。
被省掉的那条如果记进 history，下一轮想补发就会被拦——**又是一种"话被吞掉"**。

修法：`sentCountOf(result)` 读 `{"sent": N}`，只 `slice(0, N)`。
单测里 `sent=1` 的用例专门钉这个。

### 4.3 变异脚本没还原，污染了后续测试

做变异 2 时忘了 `cp` 回去，`src/orchestrator.js` 里留着
`}); // MUTATED: 去掉 session`。后面跑 e2e 得到 `sendCalls=4`，
排查了半天以为是编排器并行调用，其实是变异体还在。

**教训**：每次变异都要 `cp` 还原 + `grep -c MUTATED` 确认归零，
再往下走。这一轮最后统一用 `grep -c MUTATED` 收尾。

### 4.4 `python3` 是 Microsoft Store 的假壳

老问题（第 3 轮记过）。`python3 - <<PY` 退出码 0、什么都不做，
变异脚本静默没生效，测试"通过"得毫无意义。必须用 `python`（3.12）。

## 6. 残留问题

1. **插件状态不落盘**。`history` 在内存里，重启就空。重启后 20 分钟窗口内的
   复读拦不住了——方向是"少拦"（安全），但行为不一致。要不要落盘取决于
   重启频率；目前先不做。

2. **窗口边界是"记录时刻"，不是"发送时刻"**。`remember()` 里 `Date.now()` 是
   `after-tool` 的时刻。一次慢发送（等额度等了 12 秒）会把时间戳推后 12 秒，
   20 分钟窗口因此整体后移。影响极小，但严格说是偏差。

3. **并行工具调用的顺序假设**。`pending` 按 `chatKey` 排队，隐含"同一会话的
   工具调用是顺序的"。当前 orchestrator 确实是 `for (const call of toolCalls)`
   顺序执行，所以成立；但如果将来改成并行执行，`after-tool` 会配错 pending。
   届时需要 `toolCallId`（`after-tool` 目前不带）。

4. **`sentCountOf` 只认 JSON**。如果工具结果不是 `{"sent": N}` 形状（比如未来
   改了 `ok()` 的封装），会退回"全记"。方向仍是安全，但会重新引入本条 bug 的
   弱化版。

5. **没有"这次拦截对不对"的反馈**。`feedbacks` 字段在 1000 个会话里全空
   （第 6 轮实测），所以无法从数据上验证拦截的准确率有没有提升。
   只能等新流量积累后再测。

6. **`maxPerRun` 计数用的是 `session.sent`**，而 `session.sent` 只记成功的。
   这是对的（失败不该占名额），但也意味着**一直失败时上限永远不触发**——
   靠额度闸门兜底，不是靠这里。
